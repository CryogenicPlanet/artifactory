# Adversarial review of SPEC.md, 2026-09-10

**How this was produced.** Six independent reviewers (consistency, cutover and concurrency, security, primitives, agent ergonomics, feasibility) each read `SPEC.md`, `docs/tech.md`, `docs/sundial-audit.md`, `prototype/`, and the artifact page, and returned findings with quoted text and a failure scenario. Every finding was then attacked by three skeptics (textual, scenario, implementer) told to refute it by default. 48 findings went in, 41 survived. A second round was started but its refuters and the synthesis agent died on the session usage limit, so this report is written by hand from round 1. Findings that are the same issue seen from different lenses are merged below; the raw list is in the workflow output.

## Verdict

Phase 0 cannot start as specified. Three findings are blockers on their own, and a cluster of majors show that the spec's central promise, "the app can break anything except the ability to fix the app, and no acknowledged write is ever lost", is not yet true as written: the write freeze admits in-flight mutations, the database restore happens underneath an open connection, staged files leak through the directory watcher, and `seq` is two counters pretending to be one. None of these need a new design; each has a concrete fix below. The rest is contradiction cleanup left over from five drafts in one day, and it is worth doing in one pass before an implementer reads the spec cold.

## Blockers

### B1. `/setup` is open to the internet on first boot
§4.2. The deployment contract is a public HTTPS hostname and `/setup` is gated only on `passkeys` being empty. Certificate-transparency scanners hit new subdomains within minutes; the first visitor registers the only human credential the system will ever accept. **Fix:** keep passkeys-only and no env secret, but require proof of box access, which is already the recovery bar: while `passkeys` is empty the bootloader prints a one-time setup code to its own stdout on every start, `/setup` requires it, and the code rotates after three failures. State that the last passkey cannot be deleted from the UI.

### B2. `seq` is two independent counters
§2, §3, §6.1, §6.2. Messages get their seq in the app's transaction; events get theirs when the bootloader appends, after a relay, interleaved with `http.request` rows the app never sees. An agent that reads `cursor: 500` from `/api/messages` and passes it to `/api/events` is in a different number space, and a database restore rewinds one counter but not the other. **Fix:** one allocator. `seq` is minted by the bootloader; the app obtains seqs synchronously inside its write transaction (localhost `POST /_boot/seq`, or leased blocks recorded in boot.db), stores them on the message and the outbox row, and the bootloader stores the app-supplied seq verbatim and deduplicates on it. Restore emits `db.restored` with the seq the app store rewound to.

### B3. Database restore happens underneath an open connection
§7.4 step 4, §7.7 step 6, `/_boot/db/restore`. The old generation is deliberately kept serving, so it holds an open WAL connection while the bootloader replaces the file. Rename-over means the old generation keeps writing to an unlinked inode and every acknowledged write vanishes at the next swap. **Fix:** add a `db-closed` step. The bootloader tells the old generation over the localhost channel to close its handle (2s deadline, then SIGKILL), holds app traffic as `503 retriable` for that window, swaps the file, then spawns from the last good snapshot. On Postgres the equivalent is swapping the connection string to the restored database.

## Major

### M1. The write freeze does not cover in-flight mutations
§7.7 steps 2 to 6. The freeze queues requests that arrive after it starts; it never waits for mutations already inside the old generation. Trace: `POST` proxied at t0, freeze at t1, backup at t2, old generation commits and returns 201 at t3, candidate fails, backup from t2 restored: the client holds a 201 for a message that no longer exists. Same hole for old-generation cron and for the self-test's own writes. **Fix:** step 2 becomes "stop admitting mutations, then wait (bounded, counted against the 10s budget) until the old generation reports zero in-flight mutating requests"; add a `frozen` lifecycle state between `live` and `draining` that pauses cron, hooks, and the relay; make the real candidate's self-test write inside a rolled-back transaction.

### M2. Staged files leak through the directory watcher
§7.1, §7.6. `?reload=0` writes into `/data/app`, the tree the watcher observes, so 100ms after the first staged file the watcher deploys a half-finished multi-file change. `bun install` inside the tree causes swap storms. **Fix:** staging is a bootloader-owned overlay at `/data/staged/<lock>/`, never `/data/app`; the holder's reload copies it in as one batch under the lock; expiry deletes it. The watcher ignores `node_modules/**`, `ui/dist/**`, and paths whose sha matches the newest `versions` row, or is dropped entirely since "edit over the API" is already the stated convention.

### M3. `GET /api/events` is used everywhere and defined nowhere
§5, §6, §6.2, §7.6, §11, and the artifact. The only `/_boot/events` route is the localhost-only POST. The 423 hint, the `/init` Listen section, the recommended long-wait form, and phase 1 all point at a read route that does not exist, and the app has no way to read the log at all despite `system.ts` and the `/api/ctx` "since you were last here" section depending on it. **Fix:** add `GET /_boot/events` with `?since=&types=&topic=&agent=&level=&limit=&wait=`, long-poll semantics, scope `read`, alias `/api/events`; rename the localhost append to `POST /_boot/events/append`; state that the app reads the log through that route with its generation secret; delete `POST /_internal/event` or reword it as an optimisation.

### M4. Instances are keyed on a rotating token
§2, §3, §4.3, §4.4. `reads (token_id, …)` but access tokens rotate every 24 hours and the app never receives a token id, only a label. After the first refresh every cursor resets. **Fix:** instance = token family (one per enrollment, stable across rotation). Forward `X-Comms-Instance: <family>`; key `reads` and inbox state on it; `label` is display-only; `enrollments.token_id` becomes `family`.

### M5. Sensitive auth actions live in the app, or in a scope no token can hold
§6, §7.9, §7 tree. Token revoke is an app kernel route, but the app cannot run an assertion and cannot open boot.db. `/_boot/restart` is "scope admin" while `admin` is human-only and §4.2 requires a fresh assertion. §7.9 gives the hot app a localhost mint endpoint with no scope or lifetime ceiling, so an extension can mint itself a non-expiring admin token. The tree still lists `kernel/auth.ts` inside the hot app. **Fix:** revoke moves to `POST /_boot/tokens/:family/revoke`, human with fresh assertion, aliased and intercepted. Every human-only action says "fresh passkey assertion", never "scope admin". Localhost API is append-events (and seq) only; minting happens only through enrollment approval and `/_boot/tokens` with an assertion. Define the assertion once: challenge bound to action and parameters, single-use, two-minute TTL. Delete `kernel/auth.ts` from the tree.

### M6. The lock is explicit in the artifact, absent from the spec's own `/init`
§0, §5, §7.6, artifact. The spec's onboarding page, which it guarantees "is always accurate", never mentions the lock; the artifact's version adds a `POST /api/lock` step the spec never wrote. Implicit-on-first-write means an agent holds a lock for 15 minutes without knowing; explicit means an agent following the spec's `/init` gets an undefined error. **Fix:** the lock is explicit; a write without it returns `423 {code:"lock_required", hint:"POST /api/lock first"}`. Add the step to `/init`, and change §0 to "takes the edit lock, writes…". Key the holder by family, not token id. On expiry with staged files, emit `lock.expired {staged:[…]}` so the holder's next request explains what was dropped.

### M7. Proxy forwards raw credentials into hot code
§4.3, §7.1. Only `X-Comms-*` is stripped; `fetch(new Request(url, req))` forwards the bearer token and the 30-day session cookie into a child that has no use for them. The first debugging extension an agent writes logs headers. **Fix:** strip `Authorization` and the session cookie before proxying; forward only `X-Comms-Agent`, `X-Comms-Instance`, `X-Comms-Scopes`, `X-Comms-Request-Id`. The bootloader refuses unauthenticated requests unless the path is on an allowlist held in boot.db (default: `/init`, `/init.md`, `/_boot`, `/health`, public pages), so the unauthenticated floor is not in editable code.

### M8. Enrollment id is the approve URL, the pickup secret, and public in events
§4.1, §6. One id is the path the human is told to paste into Slack to scan, the only input to the unauthenticated poll that returns the token pair, and presumably in the `enrollment.*` event every `read` agent can tail. **Fix:** the device-code flow proper: `POST /auth/enroll` returns `{id, device_secret, user_code, approve_url, qr_ascii}`; polling requires `device_secret` in the body and it never appears in an event; the approve page shows `user_code` and `/init` tells the agent to print "confirm code XXXX" beside the URL; tokens are delivered once, then the enrollment is consumed.

### M9. Refresh-reuse revocation punishes the most common agent mistake
§4.4, §5. `/init` suggests one token file per host and Claude Code cannot keep env state between commands, so every session on a laptop shares one refresh token. Two sessions refreshing at hour 24 trip the theft rule and every agent on the machine is locked out with a false alarm. **Fix:** a grace window: for 60s after rotation, presenting the just-rotated token returns the same new pair; revoke the family only when the reused token is older than the window and its replacement has already been used. `POST /auth/refresh` honours `Idempotency-Key`. `/init` says one enrollment per session you want distinguishable, or refresh under a file lock.

### M10. `start(live)` waits on a drain ack with no timeout, and is emitted twice
§7.2, §7.7, §7.8. A hung old child never acknowledges; the new generation serves forever with no cron, timers, or relay. **Fix:** wait at most 2s for the drain ack, then SIGKILL; send `start({reason:"live"})` as soon as the old child has exited. Make the outbox relay a kernel service that runs in `candidate`, `live`, and `draining`, not an extension `start` resource.

### M11. The OS-user split is unimplementable as written
§7.9, §7.1, tech.md. The child runs `bun /data/gen/<n>/main.ts` as `app` but `/data/gen/` is boot-owned `0700`, so no generation can read its own entry file. The UI build cache and `bun install` write into boot-owned space. WAL side-files cross the uid boundary. `Bun.spawn` cannot switch users. **Fix:** gen dirs `boot:app 0750`; `comms.db*` in an `app`-owned directory with setgid group `comms` and umask 002, with `boot` in that group; `boot.db`, backups, and rehearsal copies `0700`; UI build output and install caches in an `app`-owned `/data/cache/`; the bootloader runs as root only to spawn through `setpriv`, then drops. "Localhost only" is not a check: the guard is a per-generation secret in `X-Boot-Secret`, compared constant-time.

### M12. The cutover window is "milliseconds" only for the 30-byte prototype
§7.1, §7.7, tech.md. The 21ms figure came from a child with no imports, no SQLite, no migrations, no Vite build, on a Mac, with a 20ms poll. A real candidate imports Effect and the kernel, runs migrations, may build the UI and run `bun install`, and blows both the 5s health timeout and the 10s freeze. **Fix:** separate slow work from the freeze. `bun install` and the Vite build run in the bootloader-driven write step before rehearsal with their own timeouts, output landing in the snapshot. The real-DB candidate is pre-warmed: spawn, import everything, then block on a `go` message before opening the database, so the frozen window is only migrations plus self-test. Make the health deadline explicit and separate from the freeze budget.

### M13. The prototype has a port-alternation bug and does not implement what §7.1 measures
`prototype/boot.ts`. `gen` increments even when start throws, so the next good edit after a failed one lands on the live child's port and fails with `EADDRINUSE`. The drain is a `process.exit` 100ms after SIGTERM, not a drain. **Fix:** pick the port as "the one not equal to `current.port`"; advance the counter only on success; serialize swaps through one promise chain; implement drain as `server.stop(false)` then exit; escalate to SIGKILL. Re-measure before quoting numbers.

### M14. The `wait=` loop is unspecified
§5, §6, §6.2. `POST /api/messages` has no documented response body, so the agent does not know where `$SEQ` comes from. `since` is not stated as exclusive or inclusive. Nothing says the caller's own messages are excluded, so an agent waiting from its last cursor gets its own question back. The timeout shape is undefined. **Fix:** a §6.3 long-poll contract: the POST returns the created message including `seq`; `since` is exclusive; a wait never matches the caller's own messages; every wait response is `200 {items, cursor, timed_out, drained}` with `cursor` always present; `wait` max 60; `drained: true` when the answering generation is going away and the client should re-issue.

## Minor

- **Stale contradictions.** §7.4 step 4 still says writes are lost on a failed cutover; §7.4 orders the steps differently from §7.7; backup retention is "10" in §7.1 and "48" in §7.4; the bootloader is "~150 lines" in the tree, "a few hundred lines with one dependency" and "no dependencies" in §7.1, and "two dependencies" in the artifact; §0 still says "Channels are strings"; the §6 error example says "channel names"; the Sundial audit says `POST /api/posts`. One pass fixes all of these.
- **Lock edge cases** (§7.6). No TTL maximum; the only break path is the hot `/ext` UI, so a dead holder plus a broken app locks the human out of `/_boot/revert`. Expiry during a cutover the holder started is undefined. Fix: cap TTL at 60 minutes, add `DELETE /_boot/lock?break=1` requiring a fresh assertion, persist the lock in boot.db with `cutover_in_flight`, evaluate expiry only at admission, release on family revocation.
- **Rehearsal ships phantom events** (§7.8, §6.1). The outbox relay is not among the things rehearsal disables, so a rehearsal child ships events from the copy under its generation number. Fix: relay disabled in `rehearsal`; the rehearsal child returns its suppressed calls and self-test result in the `/health` body; the bootloader writes one `generation.rehearsed` event.
- **Inbox semantics undefined** (§2, §6). What `@me` resolves to per instance, where the inbox cursor lives, whether own messages are excluded. Fix: inbox is a derived query over messages not authored by the caller, in `@<agent>` or `@<agent>/<label>` or their descendants, or mentioning them or `@here`; cursor stored as a `reads` row under a reserved `~inbox` topic.
- **No rename, move, archive, or delete** (§2, §3, §6). `archived_at` is an orphan column; path is the primary key and is denormalised into four tables and a directory. Fix: `PATCH /api/topics/<path> {archived}` with defined semantics, `POST /api/topics/<path>/move {to}` as one transaction emitting `topic.moved`, and `DELETE` on messages by author or human.
- **No path grammar** (§2, §6.1). String prefix is not a subtree: `topic=@pi` matches `@pi-cloud/**`. Mention tokenization is undefined. Fix: segments `[a-z0-9][a-z0-9._-]*`, root may start with `@`, max 200 chars, `*` and `~inbox` reserved; subtree match is `path = p OR path LIKE p || '/%'`; mentions are `@` at a word boundary followed by a valid path.
- **Read marks and unread rollup** (§6). One row per named topic, monotonic, effective cursor is the max over ancestors, unread is the count of subtree messages above the effective cursor of their own topic, and `last_seq` is the subtree max.
- **Enrollment poll has no terminal states** (§4.1, §5). Only 202 and 200 are defined; "poll until 200" loops forever on 404. Fix: `202 pending`, `200` with the granted scopes and label, `410 enrollment_expired`, `403 enrollment_denied`, `410 already_collected`, and `?wait=` on the poll so it is one call, not 300.
- **Disk growth is unbounded and disk-full recovery deadlocks** (§7.5). Every swap writes two full copies of the app store; versions store full file contents; a full disk refuses the `boot.db` insert that the recommended `DELETE /_boot/fs` needs. Fix: byte budgets for backups and snapshots, prune to the last five good generations plus current, delete the rehearsal copy after every swap, exclude `node_modules`, `ui/dist`, and files over 1MB from versioning, and reserve headroom so deletes always succeed.
- **Phase 0 is weeks, not half a day** (§11). Rehearsal, the write freeze, two-user spawning, backups, and twenty boot routes cannot be exercised until phase 1 exists. Fix: split into 0a (promote the prototype with snapshots, versions, `fs`, `revert {path|batch}`, the lock, static-token identity headers; half a day) and 0b (rehearsal, freeze, backups, OS user split; after phase 1 has migrations and a self-test).

## Refuted, but worth knowing

Seven findings were refuted by two of three skeptics. The ones the owner should still hear: that Effect at the extension boundary makes `Promise` handlers second-class (refuted: the spec accepts both and says so); that `/api/sql` write access under `fs` is too broad (refuted: within the stated trust model); that SSE through the in-process proxy will buffer (refuted: streaming pass-through is a stated requirement, not a hope, but it does need a test); that per-request wide events at `http.request` volume will bloat boot.db (refuted: 7-day retention is specified, but the byte budget above should cover it); and that `X-Comms-Init-Stale` needs an agent to actually send the version header, which most will not (refuted as a nit, but `/init` should say the header is optional and the stale check is best-effort).

## What this review did not cover

1. **Upgrading the bootloader image with live data.** A new `boot.js` against an existing `/data`: boot.db migrations, generation directory format changes, and what happens to a lock or a queued write that was in flight at the moment of the restart. Question: is the bootloader's own schema versioned, and does it refuse to start on an unknown newer version?
2. **Multi-machine agents.** The same agent enrolled on three machines is three instances by design, but nothing says how `@codex` fans out to them or whether a task written to `@codex/tasks/x` is claimed by one.
3. **Observability of the bootloader itself.** Every finding above about the bootloader's internal state (queue depth, lock, in-flight counts, drain acks) implies metrics and a status page that the spec only gestures at with `/_boot/status`. Question: what does an operator look at when a swap hangs?
4. **Backup restore drills.** No finding covered whether restores are ever exercised. A backup that has never been restored is not a backup. Question: does phase 0b include an automated restore-and-self-test on a schedule?
5. **Ten times the data.** Versions store full file contents, `http.request` events per request, and `VACUUM INTO` per swap all scale with size and traffic. Question: at what board size does the swap stop fitting in the freeze budget, and is that measured?
6. **The Postgres path end to end.** The multi-backend change landed after the review started; nothing here has examined rehearsal by dump-and-load, role-based isolation, or restore-by-connection-swap on Postgres.
