# Adversarial review findings for PR #1

Produced by a workflow of seven Opus finders, one per dimension, each followed by an Opus skeptic that re-read every cited line and either confirmed, downgraded or refuted the finding. Review head: `b9d6f28`. Findings are listed as the finder wrote them; the verdict line under each is the skeptic's. A refuted finding is kept for the record.


## server spec conformance

**Summary.** Route-level conformance is surprisingly complete: every §6 app and extension route exists except `POST /api/topics/<path>/move` (acknowledged pending), `/api/sql` writes (501), and the `system` event mirror. The §6.3 long-poll contract (`{items,cursor,timed_out,drained}`, exclusive `since`, omitted-since = published fence, own-instance exclusion while waiting, 10s heartbeats, `drained` on draining) is implemented faithfully on `/api/messages` and `/api/inbox`, the §2 path grammar and segment-boundary subtree match are enforced everywhere, and the §6 unread rule (max over own topic + ancestors + root) is exactly what the SQL computes. Health is the real §7.4 self-test through the assembled router inside a rolled-back transaction. Where it diverges from the spec is structural, not route-by-route: the entire §6 "extension routes shipped in app/ext/core.ts" table is hard-wired into kernel `HttpApi` groups, `app/ext/` is a single 29-line read-only example, and the extension `Api` has no way to write sequenced domain data at all, so the spec's own named extensions (`system`, subscriptions, a kanban) cannot be written against it. The `Api` surface itself (`route`/`page`/`cron`/`on`) is pi-sized, but the context it hands out is a raw `SqlClient` plus a publication-fence protocol that a correct read must reproduce by hand, which is the opposite of pi's "here is a small API". Secondary issues: a third boot→app channel operation (`/_boot/agents`), one generic error message/hint for every failure code, a 200 long-poll whose body can end with no JSON, and several unbounded scans (never-pruned `outbox`, JS-side inbox scan, per-topic correlated subqueries) that make write and read cost grow with total board history.

**Owner question.**

Missing/different vs §6: `POST /api/topics/<path>/move` absent (SPEC §14 marks it pending); `POST /api/sql` is read-only and returns 501 on writes, so §7.4's "data surgery over HTTP" and the `sql.write` event do not exist; the `system` view extension (§6.1) and `/api/subscriptions` (§6.2) are absent; `GET /api` and `/.well-known/agent.json` list only app routes, never the boot aliases. Everything else in the §6 tables is present, including `/api/ctx`, `/api/inbox` both modes, `/api/read`, `/api/search`, `/api/reactions`, `/api/me`, `/api/agents`, archive and delete.

Would /init let a fresh curl-only agent enroll, post and long-poll? Mechanically yes — every documented call is real, bodies are parsed without content-type checks, and the enroll/poll/bearer/refresh sequence in pages/init.md matches boot — but it contains zero `curl` lines (spec §5 requires them: `grep -c curl pages/init.md` = 0), never shows the `Authorization` header in context, omits `DELETE /api/lock` and the `423` wait recipe, omits `POST /api/fs/edit`, and leaks build trivia ("Built seeds use `app/server.js`").

Is the extension API small and pi-like, or a second framework? The surface is pi-sized (4 methods: route/page/cron/on) but it is not usable like pi's: the context is `{db, publishedThrough, publicationFence, params, query, kv, log}` with no mutation verbs, so a correct message read requires the extension author to reimplement the kernel's snapshot protocol (`withTransaction` → `SELECT epoch FROM kernel_writer` → `publicationFence` → `publishedMessages` CTE), and a write of any sequenced data is impossible. pages/docs/extensions.md is 107 lines of that contract; pi's equivalent is "register a tool".

Does the kernel/extension split match "minimal core"? No. src/kernel + src/*-http is 4365 lines; src/ext is 29. The spec's test ("can this be an extension? if yes it is not in app/kernel/") fails for messages, topics, inbox, ctx, search, reactions, read marks, profiles and sql — all are kernel `HttpApi` groups.

Long-poll/SSE vs §6.3: conformant in shape and semantics, with one breach — a store failure after the stream headers are sent produces a 200 whose body is only whitespace, contradicting "always valid JSON when it completes". SSE/`/api/stream` is boot-owned as specified; the app only advertises it.

App doing boot's job or vice versa: the app correctly owns `/init`, `/api`, `/p/*`, `/health`; boot correctly owns fs/lock/reload/revert/events/stream/tokens and is not shadowable (`reserved()` in kernel/ext.ts:51). The one boundary violation is the app calling `GET /_boot/agents` (kernel/boot-channel.ts:110), an operation outside the channel surface §7.9 enumerates, together with moving §3's `agents(kind, created_at, last_seen_at)` out of comms.db into boot.

### SRV-1 [major] The whole §6 "extension routes" table is hard-wired into the kernel; app/ext/ is one 29-line example

`packages/server/src/conversation.ts:37`

SPEC §6 assigns messages, topics, inbox, read marks, ctx, search, reactions, me and agents to `app/ext/core.ts` ("the first thing an agent will extend"), and §0 states the test for every feature: "can this be an extension? If yes, it's not in the bootloader, and probably not in app/kernel/ either." In this implementation all of those routes are compiled into kernel `HttpApi` groups and there is no `core.ts` at all.

**Evidence.** conversation.ts:37-45 builds the single API from kernel groups: `HttpApi.make("comms").add(sqlGroup).add(profilesGroup).add(topicsGroup).add(topicManagementGroup).add(messageGroup).add(searchGroup).add(reactionGroup)`. `ls src/ext` contains only `README.md` and `standup.ts` (29 lines, a read-only GET). Measured: src/kernel/*.ts + src/*.ts = 4365 non-test lines, src/ext = 29.

**Scenario.** An agent asked to change how posting works (say, add a `thread_root` field or reject messages over N tags) cannot write one file in `app/ext/`. It must edit the group declaration (conversation.ts:46-66), the handler (conversation.ts:68-92), the Schema (kernel/messages.ts:14-40), the transaction (kernel/messages.ts:100-215) and a migration — five kernel files under the edit lock, each of which can reject the candidate at health. The spec's promise "ask any agent on it for a feature; it takes the edit lock, writes app/ext/foo.ts, and it's live after one swap" (SPEC.md:20) does not hold for anything the board already does.

**Spec.** SPEC.md:23 (§0 "The test for every feature"), SPEC.md:306-325 (§6 "Extension routes, shipped in app/ext/core.ts")

**Suggestion.** Move the conversation/topic/reaction/search/profile HTTP surface into `ext/core.ts` registered through the same `api.route` the extension loader already supports (override precedence and guarded health already work, per kernel/ext.ts:300-320), leaving only db/seq/outbox/identity/router in `kernel/`. That is also what makes the "override a core route" story real rather than theoretical.

**Verdict:** confirmed, severity major. Confirmed. conversation.ts:37-44 builds one HttpApi from kernel groups (sqlGroup, profilesGroup, topicsGroup, topicManagementGroup, messageGroup, searchGroup, reactionGroup) plus an inline "conversation" group with POST/GET /api/messages and /api/ctx (conversation.ts:46-66); handlers live in kernel/messages.ts (create at :98-228). packages/server/src/ext contains only README.md and standup.ts (29 lines, read-only GET /api/standup). SPEC.md:306 puts exactly these routes in app/ext/core.ts and SPEC.md:23 states the test ("can this be an extension?"). No doc claims this as a deliberate deviation — packages/server/docs/README.md only says ext/standup.ts is "the shipped SQL-read example". The cost in the scenario is real: changing posting means editing conversation.ts + kernel/messages.ts + a migration, all health-gated kernel files.

### SRV-2 [major] Extensions cannot write any sequenced domain data, so the spec's own example extensions are impossible

`packages/server/src/kernel/extension-api.ts:10`

The extension context exposes only `db` (raw SqlClient), `publishedThrough`, `publicationFence`, `params`, `query`, plus `kv` and `log`. There is no `emit`, no `notify`, and no kernel mutation verb (create message, set topic meta, mark read). SPEC §6.1 and §6.2 name two extensions that must write messages — the `system` view that "mirrors warn and error events ... into messages" and the `subscriptions` reference implementation — and §7.3's example calls `ctx.notify.phone`. None can be written against this API.

**Evidence.** extension-api.ts:10-16 `interface RequestContext extends Identity, ExtensionData { db; publishedThrough; publicationFence; params; query }`; extension-data.ts:35-37 returns exactly `{ log, kv }`. The only sequenced-write primitive, `record(type,payload,change)` (extension-data.ts:25-34), is kept private and used solely by `kv`. pages/docs/extensions.md tells authors to "use kernel mutation operations for sequenced changes, preserving writer fencing, transaction/outbox and idempotency rules" — but no such operation is reachable from `ctx`. The only remaining write path, `POST /api/sql`, answers 501: sql-http.ts:43 `code: "sql_unsupported"` with hint "SQL writes are not implemented."

**Scenario.** Claude is asked on the box to "mirror extension errors into the `system` topic", the spec's flagship extension. It writes `app/ext/system.ts`, discovers `ctx` has no way to create a message, and its only options are (a) raw `INSERT INTO messages` via `ctx.db`, which skips `boot.reserve`, `mutation_batches`, `outbox` and the writer-epoch gate and therefore corrupts the single-seq/publication-fence invariant of §6.3, or (b) re-enter its own process over loopback using the `BOOT_SECRET` and forged `X-Chirp-*` headers. Both are worse than having no extension system. The same gap means no agent can repair a bad row at all: extensions cannot write, and `/api/sql` writes are 501, so §7.4's "this is how an agent fixes a bad row ... without writing an extension" has no implementation and the only recovery left is a human database restore.

**Spec.** SPEC.md:343 (§6.1 `system` as an extension), SPEC.md:351 (§6.2 subscriptions extension), SPEC.md:477-491 (§7.3 ctx.emit/ctx.notify), SPEC.md:510 (§7.4 POST /api/sql writes with fs)

**Suggestion.** Expose the kernel's existing serialized mutation helpers on the extension context (`ctx.messages.create`, `ctx.topics.meta`, `ctx.emit`) — they already take an `Identity` and run under the single `mutex` in kernel/messages.ts:318-336, so this is plumbing, not new machinery. Until then, say in pages/docs/extensions.md that extensions are read-only, rather than pointing at mutation operations that are not exported.

**Verdict:** confirmed, severity major. Mostly confirmed, with one correction. kernel/extension-api.ts:10-16 exposes only db/publishedThrough/publicationFence/params/query, and extension-data.ts:35-80 adds exactly {log, kv}; there is no message/topic/read mutation verb, and messages.recordEvent's `change` callback (extension-data.ts:15-34) is private to kv. So SPEC.md:343 (`system` mirrors events into messages) and SPEC.md:351 (subscriptions) cannot be written, and sql-http.ts:39-50 returns 501 sql_unsupported so /api/sql writes (SPEC.md:510) are also unavailable. Correction: ctx.log IS a sequenced emit through the kernel outbox (extension-data.ts:36), so "no emit" overstates it; kv writes are also properly fenced. The doc contradiction is real: pages/docs/extensions.md:75 tells authors to "use kernel mutation operations for sequenced changes" while docs/README.md says "there is no automatic mutation wrapper yet" — neither exposes one. Partially documented as pending, but the gap defeats the extension model, so major stands.

### SRV-3 [major] `GET /_boot/agents` is a third boot→app channel operation, and §3's agents columns left comms.db to get there

`packages/server/src/kernel/boot-channel.ts:110`

The app calls a boot endpoint outside the surface the spec enumerates for the localhost channel, and moves identity metadata the spec puts in `comms.db` into `boot.db`.

**Evidence.** boot-channel.ts:110 `agents: request("/_boot/agents", AgentRoster)`, consumed by `GET /api/agents` (profiles-http.ts:27). SPEC.md:613 (§7.9): "The channel exposes only event append/read and transaction sequence reserve/abort/fence operations." SPEC.md:304 (§6): "there is no second channel from the bootloader into the app." Meanwhile §3 specifies `agents (id, name UNIQUE, kind, emoji, color, status, created_at, last_seen_at)` in comms.db; kernel/database.ts:168 creates only `CREATE TABLE agents(name TEXT PRIMARY KEY,emoji TEXT,color TEXT,status TEXT NOT NULL)`. packages/server/docs/README.md concedes the point: "Boot supplies it through child-only /_boot/agents ... This is a narrow read-only extension to the channel operations listed in SPEC §7.9."

**Scenario.** Two concrete consequences. (1) `GET /api/agents` now fails whenever boot's SQL is slow or the 1500ms channel deadline (boot-channel.ts:105) is exceeded, returning 503 `store_unavailable` for a request that touches no app data — and in `rehearsal` state the same call is a hard failure (`rehearsal_identity_forbidden`, boot-channel.ts:63), so any future health probe or extension that lists agents breaks the candidate. (2) The trust-boundary argument in §7.9 is "the channel cannot do anything but events and seq"; each added verb weakens the thing the spec keeps deliberately tiny, and there is now precedent for a fourth.

**Spec.** SPEC.md:102 (§3 agents schema), SPEC.md:304, SPEC.md:613

**Suggestion.** Either keep `agents`/`instances` projection in comms.db (the app already receives `X-Chirp-Agent`, `X-Chirp-Instance`, `X-Chirp-Label` on every request, which is enough to maintain the roster the spec describes), or amend SPEC §7.9's enumerated channel surface explicitly rather than in a package README.

**Verdict:** confirmed, severity note. Code confirmed but it is a documented, reasoned deviation. boot-channel.ts:110 `agents: request("/_boot/agents", AgentRoster)`, served by boot at event-http.ts:147-151 (GET only, read-only, behind the same attempt/Host/secret guard), consumed by profiles-http.ts:78-89. kernel/database.ts:66 creates `agents(name PRIMARY KEY,emoji,color,status)` only, against SPEC.md:102's `agents(id,name,kind,emoji,color,status,created_at,last_seen_at)`. packages/server/docs/README.md:42 states it explicitly: "Boot supplies it through child-only /_boot/agents ... a narrow read-only extension to the channel operations listed in SPEC §7.9; it avoids copying authentication state into the app database." The rationale arguably strengthens invariant 6 (identity untouchable by the app) rather than weakening the boundary, and the channel stays read-only. Worth a note (SPEC §7.9 should be amended), not a major.

### SRV-4 [major] Every error carries the same message and one of two hints, defeating §6's LLM-readable error contract

`packages/server/src/conversation-request.ts:57`

SPEC §6 requires `{error:{code,message,hint,retriable}}` "with `hint` written for an LLM reader" and gives the example hint "topic paths may only contain a-z0-9._- and /, with a leading @ for home topics". The implementation emits one constant message and one of exactly two constant hints for every code.

**Evidence.** conversation-request.ts:60-70: `message: "Conversation request failed."`, `hint: status === 503 ? "Retry using the same Idempotency-Key; inspect authenticated boot status if failure persists." : "Check the documented request shape and required scope at /api."` — applied identically to `input_invalid`, `query_invalid`, `topic_not_found`, `topic_archived`, `author_required`, `scope_required` and `idempotency_conflict`.

**Scenario.** An agent posts `{"topic":"Scalar/Auth","body":"..."}` (uppercase, which validTopic rejects at kernel/messages.ts:50) and receives `400 {"error":{"code":"input_invalid","message":"Conversation request failed.","hint":"Check the documented request shape and required scope at /api."}}`. Nothing distinguishes a bad topic from an oversized body, a bad tag, a malformed `Idempotency-Key` or unparsable JSON — all five paths fail with `input_invalid` from different lines of kernel/messages.ts:104-110. The agent's only recovery is to re-read /api and guess, which is exactly the loop §6 wrote the hint field to prevent. Worse, any unexpected defect maps to `store_unavailable` with `retriable: true` (conversation-request.ts:68), so a genuine handler bug tells the agent to retry an unchanged request forever.

**Spec.** SPEC.md:261 (§6 error shape and hint), SPEC.md:27 (§1 "Agents are the primary users")

**Suggestion.** Attach a per-code hint table (and a `field` where validation knows it) next to `KernelError`, and stop marking unclassified defects retriable.

**Verdict:** confirmed, severity minor. Confirmed verbatim: conversation-request.ts:60-70 emits message "Conversation request failed." and exactly two hints keyed only on status===503, for every code in the 42-57 table (input_invalid, query_invalid, topic_not_found, topic_archived, author_required, scope_required, idempotency_conflict). SPEC.md:261 requires a hint "written for an LLM reader". Downgraded to minor because the machine-readable `code` and HTTP status do discriminate, and /api carries per-route shape descriptions (conversation.ts:47-65). The sharper defect inside this finding is line 48/68: any unclassified defect becomes code "store_unavailable" with retriable:true, so a genuine handler bug instructs the agent to retry unchanged forever.

### SRV-5 [major] A long-poll can return 200 with a body that is not JSON, breaking the §6.3 guarantee

`packages/server/src/conversation.ts:144`

§6.3 states "While blocked, the body streams whitespace heartbeats every 10s, so it is always valid JSON when it completes" and "Every response is 200 {items,…}". Because the 200 and its headers are emitted before the waiting effect runs, any failure inside the wait loop terminates the stream with no JSON at all.

**Evidence.** conversation.ts:144-152 returns `HttpServerResponse.stream(Stream.merge(Stream.fromEffect(result.pipe(Effect.flatMap(Schema.encodeEffect(...)))), Stream.tick("10 seconds")...), { contentType: "application/json" })`, where `result` (conversation.ts:134-142) re-runs `messages.list(input)` every 100ms; `list` can fail with `KernelError` (kernel/messages.ts:240 `query_invalid`, or any SQL error surfacing as a failure). The enclosing `failure()` wrapper has already returned by then, so it cannot convert the failure into an error envelope. topics-http.ts:126-134 has the identical shape for `/api/inbox`.

**Scenario.** An agent runs the documented `GET /api/messages?topic=scalar/q-auth-500&since=$SEQ&wait=60` as a background task. 20 seconds in, a concurrent cutover or a busy SQLite writer makes one of the ~600 polling transactions fail. The agent's harness gets HTTP 200 with body `"\n\n"` — `JSON.parse` throws, there is no `cursor` to resume from and no `retriable` flag, and the agent has no way to distinguish this from a malformed response. Over a 60s window with a poll every 100ms, the exposure is 600 transactions per wait.

**Spec.** SPEC.md:369-370 (§6.3 long-poll contract)

**Suggestion.** Run one probe list before emitting headers (already done) and then make the stream failure-proof: catch inside `result` and emit `{items:[],cursor:since,timed_out:false,drained:true}` (or an error envelope before any heartbeat byte has been written) rather than letting the stream fail.

**Verdict:** confirmed, severity major. Confirmed, and the failure path is more reachable than the finder argued. conversation.ts:144-151 emits status/headers before `result` runs, and `result` (134-142) re-runs messages.list every 100ms; messages.ts:244-249 list() calls `fence`, which at boot-channel.ts:114 is an uncached HTTP GET /_boot/seq with a 1500ms timeout mapping to KernelError boot_unavailable (boot-channel.ts:103-107). So a slow/restarting boot during a 60s wait fails the stream after the 200 and after whitespace heartbeats have been written: the client gets 200 with a body that is not JSON and no cursor. topics-http.ts:125-132 is identical for /api/inbox. Directly breaks SPEC.md:369-370 ("always valid JSON when it completes", "Every response is 200 {items,cursor,timed_out,drained}").

### SRV-6 [major] `outbox` and the four idempotency tables are never pruned, and every mutation scans them unindexed

`packages/server/src/kernel/messages.ts:83`

The transactional outbox retains every event forever with no index on the columns it is queried by, and the relay scan runs twice per mutation, so the cost of posting a message grows linearly with the lifetime message count.

**Evidence.** kernel/messages.ts:83 `SELECT DISTINCT transaction_id FROM outbox WHERE shipped_at IS NULL ORDER BY seq` — executed once before the transaction and once after commit for every create/edit/delete/read-mark/reaction (messages.ts:113 `if (!probe) yield* relay`, messages.ts:220 `if (!probe) yield* relay`). messages.ts:70 `SELECT event FROM outbox WHERE transaction_id=${id}` and operational-events.ts:47 `SELECT event FROM outbox WHERE substr(transaction_id,1,${prefix.length})=${prefix}` are likewise unindexed. The table is created as `CREATE TABLE IF NOT EXISTS outbox (seq INTEGER PRIMARY KEY,transaction_id TEXT NOT NULL,event TEXT NOT NULL,shipped_at INTEGER)` (packages/boot/src/app-recovery.ts:29) — no secondary index — and `grep -rn "outbox"` across both packages finds no DELETE/prune anywhere. `idempotency`, `read_idempotency`, `topic_idempotency` and `reaction_idempotency` (kernel/database.ts:149-181) likewise have no expiry, unlike boot's own `refresh_idempotency`, which the spec gives a deadline.

**Scenario.** Boot prunes its own `events` after 30 days, but the app's copy of every event body stays in comms.db forever. After a year of a few thousand messages a day (~1M rows, each holding the full message JSON twice — the `event` blob plus the `previous` image written by message-operations.ts:95), every single `POST /api/messages` performs two full scans of that million-row table inside the serialized mutation mutex before it can reserve a sequence, and `batch()` does a third to assemble a 1–2 event payload. Throughput degrades monotonically with board age, and the store grows without bound even though the authoritative log is pruned.

**Spec.** SPEC.md:109 (§3 outbox), SPEC.md:335 (§6.1 relay), SPEC.md:339 (§6.1 retention: http.request 7 days, everything else 30)

**Suggestion.** Add `CREATE INDEX outbox_unshipped ON outbox(shipped_at, seq)` (or a partial index) plus `CREATE INDEX outbox_transaction ON outbox(transaction_id)`, delete shipped rows once boot has acknowledged and the fence has advanced past them, and give the idempotency tables the same bounded lifetime boot gives `refresh_idempotency`.

**Verdict:** confirmed, severity major. Confirmed. outbox is created only as `CREATE TABLE IF NOT EXISTS outbox (seq INTEGER PRIMARY KEY,transaction_id TEXT NOT NULL,event TEXT NOT NULL,shipped_at INTEGER)` (packages/boot/src/app-recovery.ts:29); CREATE INDEX exists only for topics(parent) and messages(topic,seq) in kernel/database.ts:32,34. A full grep of packages/server/src and packages/boot/src for "outbox" shows no DELETE/prune at all. messages.ts:83 `SELECT DISTINCT transaction_id FROM outbox WHERE shipped_at IS NULL ORDER BY seq` runs at messages.ts:111 (before the transaction) and messages.ts:225 (after commit) for every mutation, inside the serialized mutex, plus messages.ts:70 and operational-events.ts:47 scanning by transaction_id. Cost grows linearly with lifetime message count while boot prunes its own events at 30 days (SPEC.md:339); idempotency/read_idempotency/topic_idempotency/reaction_idempotency (database.ts:35,40,55,57) likewise have no expiry.

### SRV-7 [major] `/api/inbox` scans the whole message table in JS, and re-scans it every 100ms while waiting

`packages/server/src/kernel/topics.ts:141`

The derived inbox is implemented as an unbounded application-side loop over every published message above the cursor, and the HTTP layer passes no scan bound, so an immediate read starts a full-history scan and a long-poll repeats it ten times a second.

**Evidence.** kernel/topics.ts:141-160 loops `while (items.length < limit && scannedRows < maxScan)` pulling 200-row batches and applying the `mentionMatches` regex (topics.ts:31-38) per row in JavaScript; `maxScan` defaults to `Number.POSITIVE_INFINITY` (topics.ts:123). topics-http.ts:112 and topics-http.ts:120 call `topics.inbox(who, cursor, limit, mode)` with no `maxScan`, the latter inside `while (now < deadline) { sleep 100ms; ... }` (topics-http.ts:116-124). onboarding.ts:35 also calls it unbounded (`topics.inbox(who, yield* topics.cursor(who), 201)`) on every `/init` fetch. Only `/api/ctx` passes a bound (context.ts:36, `2000`).

**Scenario.** An instance that has never marked `~inbox` (cursor 0) calls the documented `GET /api/inbox?since=0&wait=60` on a board with 200k messages. Each poll walks all 200k rows through the `publishedMessages` projection and the per-row mention regex; the wait loop does that up to 600 times in one request, holding a SQL transaction each time. `GET /init` with a bearer token does one such full scan per session start, which is the single most-called route in the system.

**Spec.** SPEC.md:318 (§6 inbox as a derived query), SPEC.md:349 (§6.2 same wait= on /api/inbox)

**Suggestion.** Push the match into SQL (a topic-prefix predicate ORed with an FTS/LIKE mention predicate, both indexable) or at minimum apply the same 2000-row bound `/api/ctx` uses, and compute the first page once before the wait loop rather than re-scanning from the original cursor on every tick.

**Verdict:** confirmed, severity major. Confirmed. kernel/topics.ts:141-157 loops 200-row batches over publishedMessages applying mentionMatches (topics.ts:31-38) in JS, bounded only by maxScan, which defaults to Number.POSITIVE_INFINITY (topics.ts:123). topics-http.ts:112 and :120 call topics.inbox(who, cursor, limit, mode) with no bound, the latter every 100ms inside the wait loop re-scanning from the same `cursor`; onboarding.ts:35 calls it unbounded with limit 201 on every /init with read scope. Only context.ts:36 passes 2000. Each tick also pays the uncached boot fence round trip (messages.ts:229, boot-channel.ts:114).

### SRV-8 [minor] Topic listing recomputes subtree activity and unread per topic with non-indexable subqueries, ignoring the `last_seq` it maintains

`packages/server/src/kernel/topics.ts:53`

§6 states "`topics.last_seq` is the subtree maximum and is maintained on write" so listings are cheap. The column is maintained but never read; the listing recomputes it, plus unread, with correlated `substr()` subqueries over a projected CTE for every topic row.

**Evidence.** kernel/topics.ts:53 `COALESCE((SELECT MAX(m.seq) FROM visible_messages m WHERE m.seq<=${ceiling} AND (m.topic=t.path OR substr(m.topic,1,length(t.path)+1)=t.path||'/')),0) AS last_seq` and topics.ts:54-56 the matching `COUNT(*)` with a nested `reads` lookup per message, both evaluated for each row of `visible_topics`. The maintained column is written on every create (kernel/messages.ts:196-197 `UPDATE topics SET last_seq=... WHERE path=...` for every ancestor) and then shadowed by the computed alias. `visible_messages`/`visible_topics` are CASE-projections (published-messages.ts:7-17), so no index on `messages(topic,seq)` can serve the `substr` prefix predicate.

**Scenario.** `GET /api/topics` (the board home, also hit by `/init`'s root detail at onboarding.ts:36) is O(topics × messages): with 500 topics and 100k messages that is 500 correlated scans of a 100k-row projection, twice per topic, on every page load, and the already-maintained `last_seq` write work is wasted.

**Spec.** SPEC.md:326 (§6 "Unread, stated once")

**Suggestion.** Read `t.last_seq` for activity ordering as the spec intends, and maintain a per-(instance,topic) unread counter or at least restrict the unread recomputation to the requested subtree and depth.

**Verdict:** confirmed, severity minor. Confirmed as written. topics.ts:52-59 recomputes `last_seq` with a correlated MAX over the visible_messages CTE and unread with a correlated COUNT plus a nested reads MAX, per row of visible_topics, and then orders by the computed alias; the maintained column written at messages.ts:163,193 is read nowhere except published-topics.ts:5's projection and context.ts:83's fallback, so SPEC.md:326 ("topics.last_seq is the subtree maximum and is maintained on write") buys nothing. substr() prefix predicates over the CASE projection cannot use messages_topic_seq (database.ts:34). Minor is right for current board scale; it is a latent cost on the most-hit route, not a bug.

### SRV-9 [minor] `GET /api` and `/.well-known/agent.json` omit every boot route, though /init calls /api the full live route table

## bootloader code quality

**Summary.** The bootloader is competently written Effect v4 — services are `Context.Service` with colocated layers, state lives in `Ref`/`Scope` rather than module globals, errors are `Schema.TaggedError`, and the durability reasoning (fences, receipts, journals) is genuinely careful and well-commented. Where it falls down is shape, not correctness: 7,147 lines across 61 files for what SPEC:404 budgets as "a few hundred lines", with ~700 lines of mechanical duplication (four copies of `hash`/`random`/`refuse`, eight copies of the redaction regex, two verbatim copies of the commit-time authority check, four copies of the child-process IPC schema across the process boundary, ~100 lines of HTTP status tables written as nested ternaries) and seven near-identical `*-http.ts` route modules whose only shared abstraction is a naming convention. The `*-schema.ts` family exists mostly to break import cycles created by `AuthError` living in `auth.ts`, not to separate concepts — `lock-break-schema.ts` is 7 lines and contains no schema. One real blocker: if a keeper receipt is lost on the same kernel boot (container SIGKILL/OOM) while a cutover was pinned, `ChildAttempts.recover` fails first, so `EditLock.recover` and `cutover.recover` never run, and the board is permanently unfixable in-band — `/api/lock` returns `cutover_in_flight` forever, a passkey-authorized lock break only defers, and `/api/reload` returns `cutover_recovery_required` forever. For a core whose stated job is "very hard to break, and an agent recovers from a bad edit by editing again", that is the one state worth engineering an escape hatch for.

**Owner question.**

"There seems to be a lot in the bootloader, why so much?" — 7,147 non-test lines / 61 files (measured). Two honest reasons, then the breakdown.

### F1 [blocker] Lost keeper receipt plus a pinned cutover is permanently unrecoverable in-band

`packages/boot/src/index.ts:62`

When ChildAttempts.recover fails (keeper killed without writing its closure receipt, same kernel boot id), boot skips EditLock.recover and cutover.recover. An interrupted pin therefore survives forever, and neither an agent nor the human can clear it: /api/lock returns cutover_in_flight, a passkey-authorized lock break only defers, and /api/reload returns cutover_recovery_required. The owner's fixed principle that "an agent must be able to recover from a bad edit by editing again" is violated by a state that a single SIGKILL can produce.

**Evidence.** index.ts:62-69 chains them so the first failure skips the rest: `const recovered = yield* (yield* ChildAttempts).recover.pipe(Effect.andThen(coordinator.recover), Effect.andThen(source._tag === "Success" ? (yield* EditLock).recover : Effect.void), Effect.exit); if (recovered._tag === "Failure") { ... yield* fail(recovered.cause); }`. child-attempts.ts:54-58 is the fail-closed loop: `for (let attempt = 0; attempt < 60 && !verified; attempt++) { verified = yield* closed(owner.id, owner.receipt); ... } if (!verified) return yield* new ChildError({ code: "child_closure_unproven" });` — and boot_id only helps across kernels (:49 `if (bootId !== null && priorBootId !== null && bootId !== priorBootId)`). cutover.ts:90 is the only place `ready` becomes true, inside `recover`, so cutover.ts:99-100 `if (!(yield* Ref.get(ready)) || (yield* read)) return yield* new ChildError({ code: "cutover_recovery_required" })` refuses every reload thereafter. edit-lock.ts:315-322 `recover` is the only code that drops an interrupted pin (`if (lock?.cutover_in_flight) transitions.push(yield* drop(lock, "interrupted"))`); edit-lock.ts:220 `if (lock?.cutover_in_flight) return reject("cutover_in_flight", lock, transitions)` blocks acquire; and edit-lock.ts:330-341 (`releaseTrusted`) only sets `pending_release` when pinned, keeping the lock. test/child-attempts.test.ts:55-59 asserts this is intentional fail-closed behaviour, and SPEC:427 does say "fail closed with boot diagnostics" — but the route table's human escape hatch (/_boot/db/restore, SPEC:277) returns 501 at edit-http.ts:97.

**Scenario.** Docker OOM-kills the container (or `docker kill`) while `POST /api/reload` is between `lock.pin` and `lock.finish`. The keeper dies without writing `<attempt>.closed`; the container restarts on the same host, so /proc/sys/kernel/random/boot_id is unchanged. Boot comes up, serves /health, /setup and /_boot/status, and every single recovery action is refused forever: POST /api/lock -> 423 cutover_in_flight, DELETE /api/lock?break=1 with a fresh passkey assertion -> lock retained with pending_release, POST /api/reload -> cutover_recovery_required, POST /_boot/db/restore -> 501. The only fix is manual surgery on the volume (delete the child_attempts row or touch the receipt file), which is exactly what a no-git Docker-on-a-volume deployment cannot do.

**Suggestion.** Add one human-only, assertion-bound escape: POST /_boot/db/force-close (or extend the existing break-lock action with a `force` param) that, with a fresh passkey assertion, marks the unproven attempts closed, emits a loud `child.closure_forced` event, and then runs cutover.recover + EditLock.recover. Separately, decouple the chain at index.ts:62 so that cutover.recover and EditLock.recover still run (and `ready` still gets set) when only the closure proof is missing — closure evidence gates *starting a new database owner*, not clearing a pinned lock.

**Verdict:** REFUTED, severity note. Code facts check out (index.ts:62-69 chains ChildAttempts.recover before coordinator.recover/EditLock.recover; child-attempts.ts:49-58 only closes attempts across a changed kernel boot_id else returns child_closure_unproven; cutover.ts:90 sets ready only in recover and :99-100 refuses reload; edit-lock.ts:220 blocks acquire on cutover_in_flight and :330-341 only defers a break; edit-http.ts:97 returns 501 for withDb). But the behaviour is exactly what SPEC.md:427 mandates: "If the keeper itself dies before recording closure, fail closed with boot diagnostics; machine-reboot/process-lifetime proof is a separate production hardening requirement." So this is an explicitly deferred hardening item, not a spec violation or a broken guarantee. Note also that clearing the pin alone would not restore recovery: without closure evidence boot still refuses to start any database owner, so the proposed decoupling would not change the outcome. Worth a note that kernel boot_id is too coarse evidence for a container restart (same kernel, fresh PID namespace), which is the practical gap.

### BOOT-2 [major] Crash-retry budget is per generation for the whole boot process lifetime and never reset, so three lifetime crashes permanently demote the newest good generation

`packages/boot/src/supervisor.ts:186`

`tried` counts start attempts per generation and is only ever incremented; a successful start does not clear it. After three crashes of the live generation over the life of one boot process — however far apart, and even though every restart succeeded — `recover` skips that generation entirely and starts an older `good` snapshot, then the next older, until none are left and boot serves 503s.

**Evidence.** supervisor.ts:65 `const tried = yield* Ref.make<Readonly<Record<number, number>>>({});`; :186 `for (let attempt = ((yield* Ref.get(tried))[generation.n] ?? 0) + 1; attempt <= 3; attempt++)`; :187 `Ref.update(tried, (values) => ({ ...values, [generation.n]: attempt }))`; on success `start` returns and nothing resets the map. The crash loop at :225-248 calls `recover` again after every child exit. SPEC §7.1 invariant 4: "A crashed child is respawned from its own snapshot, not from the live edit dir, with backoff. After three failures the bootloader falls back to the newest generation tagged `good`."

**Scenario.** An always-on box runs generation 12 (the agents' current code). It is OOM-killed on Monday, again on Thursday, again two weeks later — each time boot restarts it successfully. On the third crash `tried[12] === 3`, so boot never retries generation 12 and silently starts generation 11's snapshot: every extension and kernel edit made in generation 12 disappears from the running server while `/data/app` still contains it, with no event emitted (see BOOT-1). Three more transient crashes walk it back to 10, 9, ... and finally to 503s on a box whose code was never broken.

**Spec.** SPEC.md §7.1 invariant 4

**Suggestion.** Reset the counter for a generation once its child has been healthy (e.g. clear `tried` in `activate`, or count consecutive failures since the last healthy start rather than lifetime attempts), and emit a `generation.failed`/fallback event when boot demotes a generation so the regression is visible.

**Verdict:** confirmed, severity major. Confirmed by reading supervisor.ts whole. `tried` (supervisor.ts:65) is written only at :187 inside recover's attempt loop and read at :155/:186/:244; no code path clears or decrements it, and `start` succeeding (:176-181) leaves the count where it is. The loop bound is `for (let attempt = (tried[generation.n] ?? 0) + 1; attempt <= 3; attempt++)` (:186), so after three *lifetime* starts of one generation the body never executes and recover falls through to the next entry of `choices`. `choices` = `prepareGeneration` (application.ts:55 `if (good.length > 0) return good;`) ordered `n DESC` (generations.ts:20), and `good` is never cleared by a failure (generations.ts:51-54, :58 comment), so the fallback is silently to the next-older good snapshot and eventually to the `state:"failed"` 503 path at :210. The crash loop at :218-248 re-enters recover after every child exit, so three unrelated crashes weeks apart (OOM kills) demote the newest good generation even though every restart succeeded. SPEC.md §7.1 invariant 4 means three *failures* of a start, not three lifetime crashes. Aggravated by the missing generation.* event (BOOT-1): nothing records the demotion. Major stands.

### BOOT-3 [major] No disk budgets, no headroom reservation, and no pruning of backups or generation snapshots

**Summary.** Measured, comms is not bigger than pi: 14,339 non-test TS lines in 134 files (boot 7,239/61, server 4,423/48, ui 2,528/21, root scripts 149/5) plus 918 CSS, against pi-mono's coding-agent/src at 70,052 lines in 258 files — 0.20x. In every feature pi and comms share, comms is smaller, often by 5-10x (extension loading 793 vs 4,130; dependency preparation 485 vs 4,933; UI 2,528 vs 38,769 for interactive-mode + tui). The owner's instinct is right about something else: the ratio of infrastructure to product, and the size of the *immutable* half. SPEC.md:377 budgets boot at "a few hundred lines, two deps"; it is 7,239 lines, 61 files, 5 deps, and 50% of the non-test tree — so half the codebase is the part an agent cannot repair by editing, which is the inverse of pi's shape (one immutable binary, ~26-line extensions). Inside the hot half, three mechanisms are paid for twice: the durable mutation protocol is hand-copied into 7 files while operational-events.ts already is the generic combinator; HttpApi is declared for 19 endpoints and then bypassed by handleRaw in all 19; and the UI re-declares server schemas across 7 hand-rolled fetch clients while HttpApiClient ships unused in the pinned effect rc. Removing/merging those plus the four parallel idempotency tables and the six boot *-schema.ts files cuts ~950-1,000 lines (~7%) and ~15 files without touching a single SPEC guarantee. The remaining ~6,400 lines (durable cutover 2,670, passkeys/enrollment/refresh 2,265, boot event log + SSE 942, preparation 485) are irreducible because SPEC §4.4, §6.1, §6.3 and §7.7 specify them almost line by line.

COULD IT BE MATERIALLY SMALLER?

Reducible, ~950-1,000 lines (~7%) and ~15 files, no SPEC guarantee touched:
  • One `mutate()` combinator instead of 7 copies of the durability protocol (operational-events.ts:20-104 already is it) — ~400 lines, and 1 implementation instead of 7.
  • Use HttpApi's `.handle()` (or drop HttpApi and generate /api from a route table, as ext.ts:353 already does) — deletes 7 copies of the byte-capped body reader and 13 hand-rolled query parsers — ~250 lines.
  • Derive the UI client from the HttpApi with HttpApiClient (present at node_modules/effect/dist/unstable/httpapi/HttpApiClient.js, imported nowhere) — ~250 lines of ui/*-api.ts plus the schema-drift hazard.
  • One idempotency table instead of 4 — ~80 lines of schema + per-feature receipt decoding.
  • Fold the six boot *-schema.ts files into their owners and table-drive auth.ts's 5 signed actions (auth.ts:270-313) — ~100 lines, 5 files.

Irreducible (~6,400 lines, 45% of the tree) because SPEC specifies the mechanism, not just the behaviour: durable cutover + edit lock + source journal 2,670 (§7.1, §7.6, §7.7); passkeys + enrollment + encrypted refresh receipts 2,265 (§4.1-4.4); boot-side event log, retention and SSE 942 (§6.1-6.3); dependency/UI preparation before rehearsal 485 (§7.1). The honest conclusion: the code is not bloated relative to its spec; the spec is bloated relative to pi's "minimal immutable core" principle, and the 20x overrun on boot's own stated budget (SPEC.md:377) is where that shows up.

### SZ2 [major] The durable mutation protocol is hand-copied into 7 files while operational-events.ts already is the generic combinator

`packages/server/src/kernel/read-marks.ts:39`

Seven files independently re-implement the same 12-step protocol: random transaction id → `relay` → `sql.withTransaction` → `writerGate(sql, boot.epoch)` → idempotency row read/decode/compare → `boot.reserve(transaction, n)` → domain write → `INSERT INTO mutation_batches` → `INSERT INTO outbox` → idempotency insert → on failure `boot.reserve` + `boot.abort` → `relay` → `Effect.uninterruptible`. recordOperationalEvent (operational-events.ts:20-104) is already that protocol parameterised by a `change: (seq) => Effect` callback, and extension-data.ts:51 uses it exactly that way — but none of the six domain operations do.

**Evidence.** `grep -c` across packages/server/src/kernel: 7 sites of `INSERT INTO mutation_batches` (messages.ts:207, message-operations.ts:113, operational-events.ts:88, read-marks.ts:87, reaction-operations.ts:103, topic-operations.ts:127, topic-delete.ts:104); 7 of `INSERT INTO outbox`; 14 `boot.reserve(transaction` calls (7 write + 7 abort paths); 7 `boot.abort(transaction)`; 11 `writerGate(sql` callers. read-marks.ts:39-103 and reaction-operations.ts:41-122 are line-for-line the same shape differing only in the domain SQL. operational-events.ts:24 already takes `change: (seq: number) => Effect.Effect<void, E2> = () => Effect.void`, and extension-data.ts:51-56 passes a KV upsert through it.

**Scenario.** An agent (or the author) fixes a bug in the abort path — say, reserve-before-abort ordering under a lost reserve response, which SPEC.md:363 makes load-bearing — and fixes it in 1 of 7 places. The other six silently keep the old behaviour, and the failure mode is a permanently stuck reservation that blocks every subsequent mutation, visible only under crash-during-rollback. This is the single highest-consequence protocol in the spec (§6.3 "never abort on timeout") and it has the widest blast radius in the codebase.

**Spec.** SPEC §6.3 (one allocator, reserve/abort evidence rules); AGENTS.md "Extract an abstraction only for a concrete shared need or a safety boundary"

**Suggestion.** Promote recordOperationalEvent into `mutate({ events: n, idempotency?, body: (range, sql) => Effect })` in one file, have messages.create / mutateMessage / mutateTopic / deleteTopic / toggleReaction / markRead / recordOperationalEvent all call it, and keep only the domain SQL and the event payload in each. Measured bodies today: read-marks 106, reaction-operations 144, message-operations 131, topic-delete 124, topic-operations 150, operational-events 104 plus ~130 lines inside messages.ts = 889 lines; a ~90-line combinator plus seven ~55-line bodies is ~475. Savings ≈ 400 lines and, more importantly, one implementation of the durability contract instead of seven.

**Verdict:** confirmed, severity major. Confirmed. `grep INSERT INTO mutation_batches` returns exactly 7 kernel sites (messages.ts:207, message-operations.ts:113, read-marks.ts:87, topic-delete.ts:104, operational-events.ts:88, reaction-operations.ts:103, topic-operations.ts:127). read-marks.ts:40-105 and operational-events.ts:40-103 are the same skeleton line for line: `let reserved = false` / `sql.withTransaction(writerGate(sql, boot.epoch) → receipt read → boot.reserve(transaction,n) → domain write → INSERT INTO mutation_batches → INSERT INTO outbox)` / `.pipe(Effect.result)` / `if (reserved) { boot.reserve; boot.abort }` / trailing `relay` / `Effect.uninterruptible`. The failure scenario is real: the reserve-before-abort ordering at read-marks.ts:98-100 and operational-events.ts:96-98 implements SPEC.md:363/§6.3's evidence rule seven separate times, and a fix applied once leaves six stale copies. One overstatement: recordOperationalEvent is not already the drop-in combinator — its receipt is an outbox transaction-prefix scan (operational-events.ts:47) rather than an idempotency table, and it additionally refuses an enclosing transaction and validates type/payload, so extracting `mutate()` is real work, not a mechanical re-call. Severity major is right: highest-consequence protocol, widest blast radius, ~400 lines of duplicated durability code.

### SZ3 [major] HttpApi is declared for 19 endpoints and bypassed by handleRaw in all 19, so every payload and query is parsed twice by hand

`packages/server/src/reaction-http.ts:10`

Every server endpoint declares an HttpApiEndpoint with `payload`, `query` and `success` schemas plus a mandatory OpenApi.Description, and then implements it with `handleRaw`, which hands the handler the raw request and discards all of that decoding. `grep -c handleRaw` over packages/server/src/*.ts returns 19; `grep -c '\.handle('` returns 0. The declarations' only live consumer is the OpenAPI document at GET /api (conversation.ts:180) — which ext.ts:353 already shows can be produced from a plain route table.

**Evidence.** reaction-http.ts:10-20 declares `payload: ReactionInput, success: ReactionResult` and `query: { message: Schema.String }`; reaction-http.ts:26-45 then re-reads the body by hand with a byte cap and `Schema.decodeEffect(Schema.fromJsonString(ReactionInput))`, and :48-62 re-parses the query with `new URL(request.url, "http://localhost").searchParams` and a hand-written allowed-keys check. **Spec.** SPEC §6 ("/api Self-describing route table"); AGENTS.md "Do not add speculative abstractions… Every HttpApi endpoint needs a description"

### SZ4 [major] Four parallel idempotency tables with four bespoke receipt shapes for one concept

**Scenario.** An agent asked to add one endpoint that honours Idempotency-Key (SPEC §6: "Every POST endpoint honours Idempotency-Key") must first decide which of four tables to extend or whether to create a fifth, then hand-write a fifth compare block. ## server and UI code quality

**Summary.** The server is real Effect v4 code — Context.Service + Layer per concept, typed `KernelError`, no module-level mutable state, no `any`, no casts — and the durability machinery (epoch writer gate, reserve/abort, outbox, published-image SQL views) is carefully thought through. But it declares an Effect `HttpApi` and then bypasses it entirely: all 19 endpoints use `handleRaw`, so every declared payload/query/success schema is decorative and each handler re-implements body reading, size caps, JSON decoding and query validation by hand — seven near-identical copies of one 16-line block and five hand-maintained query-key allowlists that must track the declared schemas. The same copy-paste applies to the durability path: the reserve → write → outbox → re-reserve/abort envelope is duplicated across six kernel files, which is the worst place in the repo for a fix to have to land six times. What is avoidable is that the deployed unit is stitched together from two workspace packages at build time: that is the only reason `stage-runtime.ts` and the second manifest exist, and nothing verifies the manifest against the workspace ones (scripts/check-invariants.ts only checks import boundaries), so the two can drift silently. It is also why the production image must carry a full frontend build toolchain and the live server must spawn `vite build` — including Tailwind, which the board does not use. If the board source lived in the server package with `runtime/package.json` as its single source of truth (or if the built board were treated as a prebuilt asset), both `stage-runtime.ts` and the duplicate manifest would disappear without losing any recovery property.

## data layer

**Summary.** The data layer is SQLite-only by construction, not by accident of a few statements. There is no dialect seam anywhere: `DATABASE_URL` and `BOOT_DATABASE_URL` are read by zero lines of code, the `DbOps` service that docs/tech.md §4 designed does not exist, `@effect/sql-pg`/`@effect/sql-mysql2` are not dependencies, five sites hardcode `SqliteClient.layer`, and the child receives its store as `APP_DATABASE: <file path>` (boot/src/supervisor.ts:115), so a URL is not even expressible. Across ~350 sql-tagged statements there are 18 PRAGMAs, 19 statements using json_extract, an FTS5 virtual table with three rowid triggers, VACUUM INTO, 2 AUTOINCREMENT, 6 INSERT OR IGNORE/REPLACE, 5 RETURNING, a 2-argument scalar MAX, 13 bare-parameter `IS NULL` predicates and a bare `AND 1` fragment — maybe a third gratuitous, two thirds load-bearing design choices. Zero uses of `sql.onDialect`/`sql.onDialectOrElse` appear, even though Effect's own Migrator uses them. Critically, the features that make the system recoverable — rehearsal on a DB copy, pre-flip backup, restore — are `VACUUM INTO` plus file copy/rename plus handing the candidate a different filename; on a remote DB they have no implementation at all, so SPEC §7.4's "a bad migration is caught on the copy, the live DB is never touched" guarantee would be gone. SPEC is itself inconsistent here: §3/§9 promise three backends while §3:111 and §6.3:363 specify the writer fence as "SQLite writer lock". Raw SQL is the right call for this codebase — but it should have been raw SQL behind the DbOps seam tech.md specified, not raw SQL welded to SqliteClient.layer.

**2. "Why not Effect+drizzle or another query builder?" — Keeping raw SQL is right, but not for the reason you'd guess, and the execution is still wrong.** The real argument is that the live box has no type checker. The image is `oven/bun` and Bun strips types without checking them; tsc/tsgo only runs in `bun run check` in the repo. A query builder's entire value is compile-time schema types, and that value is unavailable precisely where the code is edited — an agent editing `/data/app/kernel/messages.ts` over `/api/fs` gets zero feedback from drizzle's types, and a drizzle schema object becomes a *second* place that must be edited in lockstep with every migration (two edits that can silently drift, versus one with raw SQL). Second: extension-api.ts:11,23,28 hands every extension a bare `SqlClient` as `ctx.db`, and SPEC §7.4:509 says "extensions get `ctx.db`, a raw SQL handle. No ORM, no repository layer to fight." A drizzle kernel next to raw-SQL extensions would be two idioms in one editable tree — the thing tech.md §11 warns against. So: do not adopt drizzle or kysely.

**3. "Is this because the DB may be dynamic?" — Partly, and only for the app store.** `comms.db` is genuinely dynamic (agents add tables/columns via `src/migrations/*.ts`, and SPEC §7.4 wants write access over `POST /api/sql`), which does justify raw SQL there. But `boot.db` is explicitly *not* dynamic — SPEC §3:76 says its "schema fixed in the image" — so dynamism is no excuse for boot's ~90 hand-written statements being SQLite-welded. And dynamism argues against a *typed builder*, not against a *dialect seam*: `sql.onDialectOrElse` costs nothing at runtime and is what Effect's own Migrator uses (repos/effect/.../Migrator.ts:115-144, :225-228).

**Recommendation: raw `sql` tags + `sql.onDialect*` + the DbOps service from tech.md §4, in four steps.** (i) Introduce `DbOps` with `snapshot`, `cloneForRehearsal`, `restore`, `dropClone`, `schemaVersion`/`setSchemaVersion`, `searchIndex`, `readOnlySession`, and make `APP_DATABASE` a URL so rehearsal hands the child a clone *locator* instead of a filename — the cutover plumbing then generalizes for free. (ii) Delete the gratuitous non-portability now, while it is ~20 lines: `GREATEST` for read-marks.ts:72, `sql`TRUE`` for messages.ts:255, `ON CONFLICT ... DO NOTHING/DO UPDATE` for the six `INSERT OR ...`, and build optional-filter WHERE clauses with `sql.and([...])` over conditionally-pushed fragments instead of 13 `$n IS NULL` guards — that last one is better code on SQLite too, because today every list query ships up to six dead predicates the planner evaluates per row. (iii) Give `events` real columns (SPEC §3:95 already specifies them), which removes 19 of the 24 `json_extract` uses and makes `WHERE transaction_id=?` indexable. (iv) Confine the residue — PRAGMA/WAL/FTS5/VACUUM INTO/sqlite_master — behind `onDialectOrElse` with an honest `backend_unsupported` failure on branches you have not written, so a Postgres URL fails loudly at startup instead of being ignored. Steps (ii) and (iii) are worth doing even if Postgres never ships.

### DB-7 [major] The publication-fence read protocol depends on SQLite WAL snapshot isolation and sets no isolation level

### SEC-3 [major] Event long-poll/SSE re-scans the whole event log every 100ms behind the single channel gate, starving message publication

`packages/boot/src/events.ts:184`

`events` stores everything in one JSON TEXT column with no index on the filtered fields (SPEC §6.1 promises `topic`/`message_id`/`request_id` as indexed columns), every `query` is a `json_extract` scan of `(since, fence]`, the cursor does not advance past non-matching rows, pollers re-issue every 100ms, and both the poller and the child's `/_boot/events/append` serialize on the same one-permit semaphore. There is no cap on concurrent streams.

**Evidence.** events.ts:43 creates `CREATE TABLE events (seq INTEGER PRIMARY KEY, transaction_id TEXT, event TEXT NOT NULL)` — no topic/actor/type columns and no index beyond the PK. events.ts:184-192 filters with `json_extract(event,'$.topic')`, `json_extract(event,'$.type')`, etc. over `seq>${since} AND seq<=${fence}`. events.ts:215 returns `cursor: items.at(-1)?.seq ?? since` — when the SQL matches nothing, the cursor stays at `since`, so the next poll rescans the identical (and growing) range. public-event-http.ts:73-79 (SSE) and :90-95 (long-poll) loop `yield* Effect.sleep("100 millis"); query({...input, since: page.cursor})`. event-http.ts:100 wraps every such read in `gate.withPermit(...)` and event-http.ts:134 wraps the child's `/_boot/seq/reserve` and `/_boot/events/append` in the same `gate`; that gate is `Semaphore.make(1)` (supervisor.ts:46). Per SPEC §6.1 a mutation may only return success after its batch is appended, so appends are on the write path. `http.request` is written for every proxied request (request-events.ts:33-54) and kept 7 days (event-retention.ts:18), so the table is large by construction.

**Scenario.** A single `read`-scope agent follows the /init advice `curl -N .../api/stream?topic=scalar&since=0` on a box with a week of traffic (say 2M rows). Because no `message.*` row matches `topic=scalar` yet, the cursor never leaves 0 and every 100ms the gate is held for a full 2M-row `json_extract` scan. Message posts, whose publication needs the same gate, now queue behind ~10 scans/second. Open 50 such streams — no cap exists anywhere — and the gate is saturated: every `POST /api/messages` blocks, and the supervisor's own `admit`/`retire` (supervisor.ts:124, 132) queue with them during a cutover.

**Spec.** SPEC §6.1 ("topic/message_id/request_id are indexed columns so the common filters are cheap"), §6.3

**Suggestion.** Store `type`, `actor`, `instance`, `topic`, `level` as real indexed columns as §6.1 specifies and keep `payload` as the only JSON; advance the returned cursor to `fence` (or the highest scanned seq) when the page is empty so a poller cannot re-walk the same prefix; serve reads from a separate read-only connection outside the child channel gate; and cap concurrent streams per instance.

**Verdict:** confirmed, severity major. Confirmed. events.ts:45 `CREATE TABLE events (seq INTEGER PRIMARY KEY, transaction_id TEXT, event TEXT NOT NULL)` — no topic/actor/type columns, no secondary index, against SPEC.md:337 "`topic`/`message_id`/`request_id` are indexed columns so the common filters are cheap". events.ts:186-194 filters exclusively through `json_extract(event,'$.topic')` etc. over `seq>${since} AND seq<=${fence}`, and events.ts:215 returns `cursor: items.at(-1)?.seq ?? since`, so an empty page leaves the cursor at `since` and the next poll rescans the same growing prefix (public-event-http.ts:73-79 SSE and :89-95 long-poll both re-query after `Effect.sleep("100 millis")`). event-http.ts:100 wraps the read in `gate.withPermit`, the same semaphore event-http.ts:132-145 uses for `/_boot/seq/reserve` and `/_boot/events/append`, and supervisor.ts:46 makes it `Semaphore.make(1)`. Partial mitigation the finder omitted: event-http.ts:110-114 caps each read at 2 seconds, and there is a per-read `LIMIT`, so a matching-row stream is fine — but a non-matching filter still holds the single gate for up to 2s per poll with no cap on concurrent streams, so the starvation of `POST /api/messages` publication stands. Not listed as an open item in docs/build-plan.md:16 (which lists byte budgets, not event indexing).

### SEC-4 [major] Unauthenticated POST /auth/enroll writes permanent boot.db rows with no rate limit, no cap and no retention

`packages/boot/src/enrollment.ts:104`

Enrollment creation is unauthenticated by design, but each call durably inserts a row that is never deleted, nothing rate-limits it, and no disk budget exists anywhere in boot — so an internet caller can grow the credential store until the volume is full, taking authentication and the app store down with it.

**Evidence.** enrollment-http.ts:64-73 handles `POST /auth/enroll` with no credential and no throttle, then enrollment.ts:104-105 executes `INSERT INTO enrollments(...) VALUES(...)`. Across the whole boot package the only deletions are `auth_challenges`, `cutover`, `staging`/`edit_lock`, `events`, `refresh_receipts`, `refresh_idempotency`, `mint_receipts`, `source_changes` and `DELETE FROM sessions WHERE hash=` (auth.ts:328, logout only) — `enrollments` and `tokens` are never pruned and expired sessions accumulate forever. event-retention.ts is the only retention loop and it touches `events` alone. Grepping boot/src for `headroom|statfs|diskUsage|budget` returns nothing, so SPEC §7.5's "refuses any write that would leave less than 5% headroom" and the 10%/20% caps are unimplemented (docs/build-plan.md lists "physical byte budgets" and "disk headroom/budgets" as remaining work, but not the unbounded enrollment row growth itself).

**Scenario.** `while true; do curl -X POST https://comms.host/auth/enroll -d '{"name":"x","kind":"x","host":"x"}'; done` from a few hosts. At ~1k req/s each row (id, secret hash, user_code, family, timestamps ≈ 300B plus index) adds ~25 GB/day to `/data/boot.db`. When the volume fills, SQLite writes to boot.db fail, so `authenticateSession`'s `UPDATE sessions SET last_seen_at` (auth.ts:321) and `authenticateAccess`'s `UPDATE tokens SET last_used_at` (enrollment.ts:216) fail — every request, including the human's login and `/api/fs` recovery, degrades to `boot_unavailable`. Secondary effect: each poll of a pending enrollment re-enters the single global auth mutex every 100ms (enrollment-http.ts:84-89 around `mutex.withPermit` in enrollment.ts:156), which is the same `Semaphore.make(1)` used by `startLogin`/`finishLogin` (auth.ts:66, 192-237), so a thousand parked polls also contend with human sign-in.

**Spec.** SPEC §7.5 ("refuses any write that would leave less than 5% headroom"), §4.1

**Suggestion.** Expire-and-delete terminal/expired `enrollments` rows and expired `sessions` in the existing hourly retention loop; cap pending enrollments (globally and per source) and reject beyond it with a retriable error; add the §7.5 free-space floor check before any boot.db-growing insert. Make the enrollment poll wait on a Deferred signalled by `decideEnrollment` rather than a 100ms re-poll under the shared auth mutex.

**Verdict:** confirmed, severity minor. Facts confirmed: enrollment-http.ts:64-74 handles create with no credential and no throttle; enrollment.ts:104-105 `INSERT INTO enrollments(...)`; a full `grep "DELETE FROM" packages/boot/src` shows deletions only for refresh_receipts/refresh_idempotency/auth_challenges/passkeys/cutover/events/source_changes/staging/edit_lock/mint_receipts and `DELETE FROM sessions WHERE hash=` (auth.ts:328, logout only) — `enrollments` and expired `sessions` are never pruned, and event-retention.ts touches `events` alone. No free-space check exists, against SPEC.md:555 "refuses any write that would leave less than 5% headroom". The poll loop (enrollment-http.ts:82-89 calling `collectEnrollment`, which is wrapped in `mutex.withPermit` at enrollment.ts:156) does re-enter the shared auth mutex every 100ms as claimed. Severity down to minor because the byte-budget/headroom half is an acknowledged open item (docs/build-plan.md:19 "disk headroom/budgets", :87 "pruning and physical headroom remain unfinished"); the genuinely undocumented parts are the absent enrollment/session row retention and the absent rate limit on an unauthenticated insert.

### SEC-5 [major] A single read-scope /api/sql query can wedge the app process permanently; nothing restarts a live-but-hung child

`packages/server/src/kernel/sql-read.ts:36`

The read-only SQL route executes a synchronous bun:sqlite statement with no deadline, and the supervisor only replaces a child that *exits*. An unbounded recursive CTE therefore blocks the single-threaded app process forever, and the board stays down until a human kills the container.

**Evidence.** sql-read.ts:36-41 runs `sql.unsafe(\`SELECT * FROM (${input.sql}\n) LIMIT 201\`, params)` with no `Effect.timeout`; the connection is `SqliteClient.layer({ filename: boot.filename, readonly: true, disableWAL: true, busyTimeout: "100 millis" })` (sql-read.ts:71) — `busyTimeout` bounds lock waits, not computation, and bun:sqlite execution is synchronous so the Bun event loop cannot interleave. sql-http.ts:21 requires only `yield* identity("read")`; the endpoint's own description at sql-http.ts:12 concedes "Queries are synchronous; these limits do not bound computation or intermediate allocation." The wrapper's `LIMIT 201` cannot help an aggregate. supervisor.ts:218-249 is the only restart path and it waits on `yield* active.process.exited` (supervisor.ts:224); there is no periodic liveness probe of a live child (child-process.ts:89-104's `health` is called only during start/cutover, supervisor.ts:172).

**Scenario.** `curl -H "Authorization: Bearer $READ_ONLY_TOKEN" -X POST $HOST/api/sql -d '{"sql":"WITH RECURSIVE n(v) AS (SELECT 1 UNION ALL SELECT v+1 FROM n) SELECT count(*) FROM n"}'` — the statement never returns. The app process stops answering `/api/messages`, `/p/**` and `/health`; boot keeps proxying into a dead end and `POST /api/reload` cannot complete a cutover because the freeze drain (traffic.ts:54-56) waits on an admitted request that never finishes. The existing test suite covers every *statement-shape* escape (test/sql-http.test.ts:76-93) but the bounded-CTE case at test/sql-http.test.ts:107 uses `WHERE v<1000`, so the unbounded case is untested.

**Spec.** SPEC §7.4 (POST /api/sql), §7.1

**Suggestion.** Give the statement a wall-clock bound that actually fires: run it through bun:sqlite's interrupt/progress-handler or in a worker so `Effect.timeout` can cancel it, and reject `WITH RECURSIVE` without a bounding predicate as a cheap interim guard. Separately, add a periodic `/health` probe of the live child with a bounded deadline so a wedged-but-alive generation is retired like a crashed one — that is the difference between "an agent broke it and recovered by editing again" and "shell into the box".

**Verdict:** confirmed, severity major. Confirmed on both halves. sql-read.ts:34-40 runs `sql.unsafe(`SELECT * FROM (${input.sql}\n) LIMIT 201`, params)` with no `Effect.timeout`; the layer at sql-read.ts:70-72 sets only `busyTimeout: "100 millis"` (lock waits, not computation) and bun:sqlite execution is synchronous. The route (the finder's path is wrong — it is packages/server/src/sql-http.ts, not kernel/sql-http.ts) requires only `yield* identity("read")` at sql-http.ts:21, times out the *body read* at :33 but never the query at :38, and its own OpenAPI text at sql-http.ts:12 concedes "Queries are synchronous; these limits do not bound computation or intermediate allocation." supervisor.ts:212-249 is the only restart path and it blocks on `yield* active.process.exited` (:224); `health` (child-process.ts:89-103) is invoked only from `start` (supervisor.ts:172), so a live-but-wedged child is never retired. traffic.ts:53-56 `drained` spins while `admitted > 0`, so a never-finishing admitted mutation also blocks the freeze — the wedge is unrecoverable without killing the container, which is exactly the recovery property the design rests on. Only correction: the citation for the route file.

### SEC-6 [minor] Unauthenticated /p/** requests take the supervisor's single operation gate before any authentication

`packages/boot/src/public-pages.ts:101`

The public-page policy check acquires both the supervisor `operationGate` and the child `channelGate`, opens a SQLite connection and stats every path segment — all before the request is authenticated and regardless of whether the page is actually public. Anonymous traffic therefore serializes against cutover, page publication and crash recovery.

**Evidence.** proxy.ts:136-144: for any `GET`/`HEAD` under `/p/` without an explicit credential the proxy calls `policy.check(path)`. public-pages.ts:100-104 is `operationGate.withPermit(channelGate.withPermit(...))`, and inside it does a `fs.realPath` per segment (public-pages.ts:111-120), an `events.state` read, and a fresh `SqliteClient.layer({filename: .../comms.db, readonly: true})` open/close (public-pages.ts:128-143). `operationGate` is `Semaphore.make(1)` (supervisor.ts:47) and is the same permit held by initial recovery (supervisor.ts:217) and by the crash-restart path `operationGate.withPermit(... retire(active) ... recover)` (supervisor.ts:225-247), and by page publication's `withWrite` (public-pages.ts:51-99, which itself spins up to 1s).

**Scenario.** A few hundred concurrent `GET /p/x` from the internet (no credential needed) keep the single permit busy; each waiter self-cancels after the 1s timeout (public-pages.ts:174) and returns `503 boot_unavailable`, so anonymous page reads fail under trivial load, and a child crash occurring during the flood waits for the queue ahead of it before `recover` can start. Because the check runs before authentication, there is no credential to rate-limit on.

**Spec.** SPEC §4.3 (unauthenticated allowlist), §7.7

**Suggestion.** Do the read-side policy check on its own read-only connection outside `operationGate`/`channelGate` (it already re-validates under the gate for writes), or cache the `meta.public` set and invalidate it on `topic.meta`/`topic.archived` events. Keep the operation gate for things that actually mutate the generation.

**Verdict:** confirmed, severity minor. Confirmed. proxy.ts:136-144 calls `policy.check(path)` for any unauthenticated GET/HEAD under `/p/`; public-pages.ts:100-103 is `operationGate.withPermit(channelGate.withPermit(...))` and inside does a `fs.realPath` per segment (:113-121), an `events.state` read (:125) and a fresh `SqliteClient.layer({filename: .../comms.db, readonly:true})` open/close (:128-144), with `Effect.timeout("1 second")` at :174. supervisor.ts:47 makes `operationGate` `Semaphore.make(1)`, and it is the permit held by `recover` (supervisor.ts:217) and by the crash-restart block (supervisor.ts:225-247) and by `withWrite` (public-pages.ts:51). So unauthenticated traffic does serialize against crash recovery and page publication. Note the author states this gating is deliberate (packages/boot/docs/README.md:61 "Boot holds the existing operation gate and channel gate while reading") — the deliberate part is consistency, not doing it on the unauthenticated read path, so the finding stands at minor.

### SEC-7 [minor] The child-only sequence/event channel is served on the public listener instead of a loopback-bound socket

`packages/boot/src/supervisor.ts:44`

SPEC §7.9 and §6 require `/_boot/events/append` and `/_boot/seq/*` to be "bound to `127.0.0.1`". They are served by the public proxy on `0.0.0.0:8080`, dispatched before authentication whenever an `x-boot-secret` header is present. The compensating checks are correct, but the network-level boundary the spec asks for is absent, so the 256-bit secret is the only thing between the internet and the sequence allocator.

**Evidence.** supervisor.ts:44 sets the child's callback to the public listener: `const callback = \`http://127.0.0.1:${http.address.port}\`` where `http` is the one `HttpServer.HttpServer` that index.ts:109-113 serves all public traffic on (the image sets `HOST=0.0.0.0`, Dockerfile:33). proxy.ts:103-118 dispatches `eventRoute` ahead of `authRoute` when `request.headers["x-boot-secret"] !== undefined` or the path is `/_boot/seq*`, `/_boot/events/append`, `/_boot/agents`. The guard is event-http.ts:71-88: constant-time compare against the live attempts, `request.headers.host !== attempt.host` (i.e. the caller must send `Host: 127.0.0.1:<port>`), and refusal when any `x-forwarded-*`/`forwarded` header is present — all attacker-controllable except the secret. Redaction of `[a-f0-9]{64}` in stderr/status (supervisor.ts:76, proxy.ts:188) exists precisely because that 64-hex secret must not leak.

**Scenario.** No working exploit without the secret — fails closed (403 `child_forbidden`). The cost is blast radius: any single leak of a per-attempt secret (a stderr path that escapes the 64-hex redaction, an extension that logs its own request headers — the proxy hands `x-boot-secret` to the child on every forwarded request, proxy.ts:279) becomes remotely exploitable against the sequence allocator and event log rather than requiring local access, e.g. `curl -H 'x-boot-secret: <leaked>' -H 'Host: 127.0.0.1:8080' https://comms.host/_boot/seq/reserve -d '{"transaction":"x","count":1}'`.

**Spec.** SPEC §7.9 ("The child binds 127.0.0.1 on its internal port"), §6 route table ("Child-only: bound to 127.0.0.1")

**Suggestion.** Open a second listener bound to `127.0.0.1` for the child channel and serve `/_boot/seq*`, `/_boot/events/append`, `/_boot/agents` only there; have the public proxy 404 those paths unconditionally. That is a few lines given `callback` is already a distinct URL, and it restores the property the spec asks for.

**Verdict:** confirmed, severity minor. Confirmed as a spec deviation with working compensating controls. supervisor.ts:44 `const callback = `http://127.0.0.1:${http.address.port}`` uses the single public listener (Dockerfile:33 sets `HOST=0.0.0.0`), and proxy.ts:103-118 dispatches `eventRoute` before `authRoute` whenever `x-boot-secret` is present or the path is `/_boot/seq*`, `/_boot/events/append`, `/_boot/agents`. SPEC.md:287 says these are "Child-only: bound to `127.0.0.1`" and SPEC.md:613 repeats the localhost binding, so the network boundary is genuinely absent. event-http.ts:72-88 does constant-time compare, require `request.headers.host === attempt.host`, and refuse any `x-forwarded-*`/`forwarded` header — all attacker-settable except the 256-bit secret, so it fails closed (403 child_forbidden) and there is no exploit without a leak. Blast-radius-only cost, and not documented as an open deviation anywhere I found → minor, worth fixing since `callback` is already a separate URL.

### SEC-8 [minor] Mint receipts keep an encrypted plaintext token pair for the full 30-day session lifetime

`packages/boot/src/token-mint.ts:158`

SPEC §4.4 requires replay receipts to be short-lived and to "Store no plaintext token or permanent encryption key". The refresh receipt honours that (60s, keyed by the raw predecessor). The mint receipt instead lives until the session expires — up to 30 days — and is decryptable by the session cookie value alone.

**Evidence.** token-mint.ts:148-162 seals the pair with `sealMintReceipt(sessionSecret, { ..., expires_at: session.expires_at }, pair)` and inserts it into `mint_receipts`; the KDF input is the session cookie secret (`key(secret, salt, "mint")` at refresh-receipt.ts:24-25, called with `sessionSecret` from token-mint-http.ts:27-32). Sessions are 30 days (auth.ts:125: `now + 30 * 24 * 60 * 60 * 1000`). Cleanup is only `DELETE FROM mint_receipts WHERE expires_at<=${now}` on the next mint (token-mint.ts:69), so a single minted family leaves a decryptable blob for a month. Compare tokens.ts:250 for refresh: `const deadline = now + 60_000`.

**Scenario.** An attacker who obtains the human's session cookie (see SEC-2 for one route that does not even need to read it, plus ordinary device compromise) can decrypt every token pair minted during that session's life straight out of `boot.db` — including pairs the human minted for other machines and has since stored elsewhere — rather than only being able to mint new ones that show up as `token.minted` events.

**Spec.** SPEC §4.4 ("short-lived encrypted receipt … Store no plaintext token or permanent encryption key")

**Suggestion.** Bound the mint receipt the way the refresh receipt is bounded: a fixed short deadline (minutes) independent of session lifetime, deleted on the next token operation. Idempotent retry of a lost mint response only needs to survive seconds, not a month.

**Verdict:** confirmed, severity minor. Confirmed. token-mint.ts:148-161 seals with `expires_at: session.expires_at` and inserts into `mint_receipts`; refresh-receipt.ts:24-25 derives the key as `hkdfSync("sha256", Buffer.from(secret,"base64url"), salt, "comms-mint-receipt-v1", 32)` where `secret` is the session cookie value; auth.ts:125 sets sessions to 30 days; the only cleanup is `DELETE FROM mint_receipts WHERE expires_at<=${now}` at token-mint.ts:69, i.e. lazily on the next mint. Contrast tokens.ts:250's fixed 60s refresh deadline. SPEC.md:178 requires a "short-lived ... receipt" with a "fixed deadline", written about refresh but the same intent clearly covers mint. Real but contained: the attacker already needs the session cookie, which already permits minting new families; the marginal loss is decryptability of previously minted pairs for up to a month → minor.

### SEC-9 [note] Failed logins, setup-code guesses and enrollment creation leave no record in the event log

`packages/boot/src/proxy.ts:299`

`http.request` is emitted only for requests that reach the proxy-to-child path, so every boot-owned auth surface — `/setup`, `/auth/login`, `/auth/enroll`, `/auth/refresh`, `/_boot/enroll/:id/approve`, token revoke — produces no event at all on failure. The event log is the system's only audit surface, and the surfaces most worth auditing are invisible in it.

**Evidence.** proxy.ts:299-306 calls `requests({...})` only after all boot routes have declined and a child destination has been chosen; `authRoute`/`enrollmentRoute`/`tokenRoute`/`tokenMintRoute` all return early (proxy.ts:112-133). **Scenario.** An attacker rotates the `/setup` code out from under the human by failing three times repeatedly (auth.ts:136: three failures call `rotateSetup`, printing a new code to stdout), or grinds at `/auth/refresh` with captured tokens. The human has no way to see from the board, `/api/events` or `/_boot/status` that any of it happened — the only trace is the stdout code churn.

**Spec.** SPEC §6.1 ("The bootloader writes … plus enrollment.*, token.refreshed, token.family_revoked")

**Suggestion.** Emit a dedicated low-cardinality `auth.failed {route, code}` boot event (no secrets, no bodies) from `authFailure` in auth-http.ts:62-91. That avoids self-logging the event feed while giving the `system` view something to mirror, and it is one call at a single choke point.

**Verdict:** confirmed, severity note. Confirmed. proxy.ts:269-275 calls `requests({started, method, path, identity, generation, requestId})` only after every boot route has declined and a child destination is chosen (proxy.ts:112-133 return early), so no event is written for `/setup`, `/auth/login`, `/auth/enroll`, `/auth/refresh` or the approve routes. Grep for `auth.failed|setup_code_invalid|authentication_invalid` finds only refusal codes (auth.ts:138, :212, :229) and UI strings (auth-page.ts:24) — no event write. auth.ts:136-138 does rotate the setup code after three failures, so the grind is silent except for stdout churn. Correctly a note: the author states the exclusion is deliberate (docs/build-plan.md:88 "boot-owned routes are excluded to avoid feed self-logging") and SPEC.md:337-339 does not enumerate an auth-failure event, so this is a missing feature, not a violation.


## What the skeptics found that the finders missed

- Every published-fence read is an uncached localhost HTTP round trip to boot, and the long-poll loops make one per 100ms per waiting client. kernel/messages.ts:229-232 `fence` calls boot.fence, which is boot-channel.ts:114 `request("/_boot/seq", ...)` — a fresh HttpClient GET with a 1500ms timeout (boot-channel.ts:103-107), with no caching or subscription. messages.ts:247 calls it inside every list() transaction, topics.ts:128 inside every inbox(), topics.ts:50 inside every topic detail, extension-data.ts:64 inside every kv.get. Since conversation.ts:138 and topics-http.ts:120 re-run list/inbox every 100 millis for the whole wait, each waiting agent generates ~10 boot HTTP requests per second (~600 per 60s wait), and each one is executed while the SQL transaction is open (messages.ts:244-247), i.e. network I/O inside a SQLite read transaction — exactly what SPEC.md:393 bounds for write paths. Ten agents idling on `wait=60` put 100 req/s of pure fence traffic on the bootloader that also serves auth, the edit loop and SSE, and any 1.5s blip there turns into the truncated-JSON failure of SRV-5. A cached fence advanced by the relay/append response (boot already returns published_through from /_boot/events/append, boot-channel.ts:115) would remove essentially all of it.

- packages/boot/src/cutover.ts:105-299 — the single most review-hostile code in boot and it is the path that must never break. `reload` is one ~185-line closure holding three mutable lets (`let candidate: ActiveChild | null = null` :105, `let generation: Generation | null = null` :106, `let priorClosed = false` :109) assigned inside a nested `perform` generator, then read back after failure through two IIFE casts written purely to defeat TS narrowing: `const failedGeneration = ((): Generation | null => generation)();` (:225) and `const failedCandidate = ((): ActiveChild | null => candidate)();` (:232). Three distinct outcomes (success, post-acceptance retain-and-restart at :242-259, pre-acceptance restore at :261-270) share that mutable state, so whether a failure restores the pre-flip backup or keeps the accepted store depends on assignments invisible from any signature — and `acceptedGeneration` (:240) is derived partly from `failedGeneration`, i.e. from whether a `let` happened to be set before the throw. This conflicts with AGENTS.md's no-mutable-state / one-concept guidance and with the owner's "hard to break, easy to reason about" requirement far more than any of the duplication findings above; splitting the accepted-rollback and pre-acceptance-restore branches into named effects that take explicit `{candidate, generation}` arguments would remove the lets and the casts.

- The finder never looks at test mass, which is the strongest size-vs-pi fact in the tree and the reason none of its refactors are cheap. `wc -l` over every test file under packages/*/test gives 15,226 lines in 132 files — larger than the entire 14,202-line source tree — with packages/boot/test at 8,307 lines (e.g. packages/boot/test/generations.test.ts:1, 479 lines; source-files.test.ts:1, 349) against boot's 7,248-line src, and packages/server/test at 6,919 against server's 4,452. AGENTS.md does demand strong boot hardening tests, so this is not a violation, but it is the load-bearing cost the size findings omit: SZ1's "move ~450 lines out of the immutable core", SZ2's `mutate()` extraction and SZ4's single idempotency table each require rewriting a comparable or larger volume of tests pinned to the current file layout (boot tests even import boot internals per AGENTS.md's packages/server/test/fixtures exception). Any size remediation plan that does not count the test side will be abandoned halfway, which is exactly the state the 7,248-line core is already in.

- A failed source-publication replay wedges the entire edit path with no HTTP remedy, which is the one guarantee the owner named ("an agent must be able to recover from a bad edit by editing again"). source-journal.ts:21-24 `ready` fails with `SourceRejected{code:"publication_pending"}` whenever a `source_batches` row is still `state='publishing'`, and source-files.ts:32-33 `guard = semaphore.withPermit(Effect.andThen(journal.ready, effect))` wraps *every* public operation — read, edit, stage, prepare, prepareUndo, preparePages, publish, materialize, withCommitted (source-files.ts:196-285). The only thing that clears that row is `journal.recover` (source-journal.ts:59-88), which is reachable from exactly two places: index.ts:56 at process start, and cutover.ts:280 in the reload *failure* path. If recover throws `external_conflict` (source-journal.ts:67/72 — the on-disk file matches neither the before nor the desired image, e.g. a crash mid-`io.replace` or any edit made on the volume), index.ts:57-58 records it in `child.sourceError` and continues, and from then on every `/api/fs/*`, `/api/fs/edit`, `/api/reload` and `/api/revert` call returns 503 `publication_pending` (edit-http.ts:226-232 maps it to 503) — including page writes, which have no lock requirement. Reload can never reach cutover.ts:280 because `sources.prepare` is itself guarded and fails first (cutover.ts:102-104). So the state is only clearable by a process restart, and boot implements no `POST /_boot/restart` (proxy.ts:193-211 returns 501 for it) and no watcher (BOOT-10) to pick up the manual repair. Net effect: one interrupted publication plus one out-of-band byte makes the board permanently unable to edit itself, recoverable only by shelling into the container — contradicting SPEC §4.2's "the only recovery path that requires infrastructure access is losing every passkey". packages/boot/docs/README.md:31 discloses only the mild half ("new source snapshots stay blocked"), not that page writes, source reads and reload all 503 and that nothing short of a restart retries the replay.

- The long-poll loop makes one boot HTTP fence call plus one SQLite transaction every 100 ms per waiting client, for up to 60 s — the same inefficiency as SRV-4 but an order of magnitude larger and on the endpoint the spec expects every agent to camp on. packages/server/src/conversation.ts:134-142: `while (… < deadline) { … yield* Effect.sleep("100 millis"); const next = yield* messages.list(input); … }`, and packages/server/src/kernel/messages.ts:243-246 shows every `list` opens `sql.withTransaction` and does `const ceiling = (yield* fence).published_through`, which is messages.ts:230-231 -> boot.fence -> boot-channel.ts:113 `request("/_boot/seq", …)`, an HTTP round trip to the single-threaded boot process with a 1500 ms timeout (boot-channel.ts:106). packages/server/src/topics-http.ts:116-124 has the identical loop for /api/inbox. So one agent holding a 60 s `wait=60` read costs ~600 boot requests and ~600 SQLite transactions; ten idle agents long-polling (the designed steady state per SPEC.md §6.3) put a continuous ~100 req/s on boot, competing with the 10 Hz relay loop at server.ts:159-177 and with the proxy that is forwarding those same requests. Nothing caches the fence or notifies on publication; the poll never consults the already-relayed outbox or a local publication Ref. Related and also unreported: because these handlers return `HttpServerResponse.stream(...)` (conversation.ts:144, topics-http.ts:126) while `failure()` (conversation-request.ts:27-75) wraps only the effect that *produces* the response, a `boot_unavailable` raised inside the poll loop after the 200 has been sent cannot be mapped to an error body — the client gets status 200 and a body containing only heartbeat whitespace, violating the §6.3 "the body is valid JSON either way" contract.

- The app store's bookkeeping tables are append-only forever AND one of them is full-scanned 10 times a second. `outbox` is created as `outbox (seq INTEGER PRIMARY KEY, transaction_id TEXT NOT NULL, event TEXT NOT NULL, shipped_at INTEGER)` with no secondary index (packages/boot/src/app-recovery.ts:29), and `grep -rn "DELETE FROM" packages/server/src packages/boot/src` shows zero deletes against `outbox`, `mutation_batches`, `idempotency`, `read_idempotency`, `topic_idempotency` or `reaction_idempotency` — only boot's own auth/event tables are pruned (event-retention.ts:36, refresh-schema.ts:50-51, auth.ts:108). Meanwhile packages/server/src/server.ts:160-177 forks a loop that calls `messages.relay` then `Effect.sleep("100 millis")` forever, and relay's first statement is packages/server/src/kernel/messages.ts:83 `SELECT DISTINCT transaction_id FROM outbox WHERE shipped_at IS NULL ORDER BY seq` — an unindexed predicate plus DISTINCT, i.e. a full table scan and temp B-tree over the entire append-only outbox, 10x/second, even when nothing is pending. Two concrete costs today on the shipped SQLite backend: (1) every message is stored roughly three times permanently — the row, its full event JSON in `outbox`, and, with `Idempotency-Key`, the serialized input plus the whole message again as `outcome` (message-operations.ts:77,113-114) — so `comms.db` grows several times faster than the board's content, and since backups are VACUUM INTO copies capped at 20% of the volume (SPEC.md §7.5), the number of restore points a board keeps silently shrinks as it ages; (2) after a few hundred thousand writes that 100ms loop is re-reading the whole outbox continuously, burning CPU for the lifetime of the process. SPEC budgets events, backups, snapshots and versions but nothing covers these app-store tables, and no doc lists the omission — unlike every Postgres item above, this is undisclosed and affects the only backend that actually ships. A `DELETE FROM outbox WHERE shipped_at IS NOT NULL AND seq<=<published fence>` (or an index on `shipped_at`) plus a retention pass for the idempotency tables is the bounded fix.

- The child can forge boot-owned audit events, which is a trust-boundary hole the finder did not report. `/_boot/events/append` validates only sequencing and ownership — events.ts:79-87 checks the batch id/attempt/from_seq/to_seq/state and `event.seq` contiguity, event-http.ts:164-171 additionally checks `event.generation !== attempt.generation`, and then events.ts:103-104 inserts the record verbatim: `INSERT INTO events(seq,transaction_id,event) VALUES(${event.seq},${batch.transaction},${encode(event)})`. Nothing constrains the `type`, `actor`, `instance` or `level` fields of the appended `EventRecord` (schema at packages/server/src/kernel/boot-channel.ts:5-17 is free-form strings). So editable app code or any extension — which holds BOOT_SECRET in its env (supervisor.ts:112) — can append `{type:"token.minted", actor:"rahul", ...}` or `{type:"enrollment.approved"}` or `{type:"token.family_revoked"}` directly into boot.db's event log. Boot's own writes are distinguishable only by `transaction_id IS NULL` (events.ts:163), and the query path (events.ts:186-194, returning only the decoded `event` JSON) never filters on or exposes that column, so the human and the `system` extension cannot tell a boot-written security event from an app-forged one. That defeats the one audit surface SPEC §6.1 (SPEC.md:337-339) designates, and it is reachable without the §7.9 UID split being the issue — the channel itself is the gap, contradicting SPEC.md:613's framing that the channel "exposes only event append/read and transaction sequence" operations as a safe capability. Cheap fix: reject appended events whose `type` is in boot's namespace (`token.*`, `enrollment.*`, `passkey.*`, `http.request`) or whose `actor` is `boot`/`rahul`, and surface the boot/app origin in query results.
