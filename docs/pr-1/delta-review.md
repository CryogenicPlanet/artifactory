## B. Finding-by-finding status

**SRV-7, `/api/inbox` scans the whole message table in JS and re-scans every 100 ms — partly fixed.** The re-scan half is fixed: `topics-http.ts:111-123` now reads `messages.fence` each tick and calls `topics.inbox` only when `published_through` moved. The scan half is not. `maxScan` defaults to `Infinity`; only the `/init` page passes a budget (`onboarding.ts:35`), so `GET /api/inbox` still walks every published message in JavaScript (`kernel/topics.ts:141-156`). Worse, the fix only covers a *silent* board: `cursor` is still `items.at(-1)?.seq ?? since` (`topics.ts:160`), so on a filtered page the waiter's `since` never advances and every publication anywhere on the board triggers a fresh full scan from that waiter's original cursor. Ten waiters on a busy board still full-scan per publication.

**The API report's idle-inbox rescan — fixed.** As above. Note what it costs: the tick still calls `messages.fence`, which is an HTTP `GET /_boot/seq` (`kernel/boot-channel.ts:114`). Item 10's fence traffic is unchanged, not worsened: the old loop made the same call *plus* the SQL scan.

**Item 17 / the public-pages flaky test / BOOT-9 — unchanged in code, and the test now tolerates the bug.** `760154a` added a `readPage` helper that re-fetches for up to 3 seconds while the status is 503, with the comment "Anonymous policy deliberately returns 503 while unrelated publication/recovery is pending". The read path in `public-pages.ts` still fails instead of waiting like the write path in the same file. `181939b` then made the surface area larger, not smaller: `proxy.ts:261-262` adds a *new* deliberate 503 for anonymous page reads whenever the request gate's revision changed during admission, and `proxy.ts:259-260` routes every proxied request through a gate that refuses rather than queues (§D.2). So: not fixed, the symptom is now masked in the test suite, and any future regression on the anonymous read path will be silently retried for three seconds.

**BOOT-5, no route to list or restore a backup — fixed, both halves.** Listing is `4246e30` (`backup-http.ts:10`, `backup-inventory.ts:15-35`), human session only, keyset paginated, metadata only. Restore is `181939b` (`database-restore.ts`, 306 lines) with a six-phase durable journal (`authorized → restoring → working → rollback → restored|failed`), a pre-restore safety backup taken under freeze and drain (`:246-271`), closure evidence required before replacement (`:276`), a fresh writer epoch per install (`:120-121`), and interrupted-restore resume (`:169-194`). This is the most careful code in the delta and it implements §7.5 as written. It also carries the batch's worst defect (§D.1).

**SRV-10, `/init` has no curl lines and omits lock release and the 423 wait recipe — partly fixed.** `9dc0848` and `181939b` together deliver four of the six gaps item 22 names: scope names, the error envelope, the JSON body requirement on `/api/reload` (with the batch's one curl line), and `id` plus `expires_at` on the enrol response. The version-stamp header is still unmentioned. No `recipes.md` or `editing.md` split.

## C. The subscriptions extension

`packages/server/src/ext/subscriptions/`: `contract.ts` 71, `store.ts` 104, `delivery.ts` 84, `index.ts` 130, plus `migrations/001_webhook_subscriptions.ts` 14 and `pages/docs/subscriptions.md` 27. **403 lines of code.** It is well-built — durable cursors, capped exponential backoff, bounded response bytes and a two-second request budget, manual redirect handling, no credential forwarding, an `X-Comms-Delivery-Id` stable across retries, and a documented at-least-once contract. SPEC §6.2 promises exactly this as "the reference implementation", and it delivers.

It also answers item 7's question empirically, and the answer is that the small API cannot carry a mutation. Against the four tests:

**Does it use the fence ritual by hand?** Yes, twice. `store.ts:21-29` opens `sql.withTransaction`, touches `SELECT epoch FROM kernel_writer` to take the writer gate, reads `messages.fence` for `published_through`, and only then queries its own table. That is the nine-line ritual `extensions.md` documents and item 7 says `ctx.read(effect)` should delete. `store.ts:48` repeats the gate as a standalone `admit`.

**Does it write through the raw SQL handle or a kernel verb?** Both, which is the interesting part. The domain write is raw SQL (`store.ts:71`, `:86`, `:100`), but it is wrapped in `messages.recordEvent(event, run)` — the generic combinator item 9 identifies as already being `mutate()`. So the extension found the right helper and could only reach it by importing `Messages` from `../../kernel/messages.ts`. It imports five kernel services this way (`BootChannel`, `KernelError`, `Lifecycle`, `Messages`, `writerGate`) and ignores the `ctx.db` and `ctx.publicationFence` the `Api` actually hands it, building its own `SqlClient` from the layer instead. `kernel/extension-api.ts` is unchanged by this commit: no `messages.create`, no `emit`, no `read`, no `migrate`.

**Does it own tables, and how?** Through `src/migrations/001_webhook_subscriptions.ts`, the kernel's own app-wide migration ladder, not an extension-scoped mechanism. The consequences are documented rather than fixed: `subscriptions.md:3` tells the agent "Keep that applied migration unchanged; removing the extension stops delivery without erasing its records." An `api.migrate(name, sql)` scoped to the extension would own the table's lifecycle with it.

**What it would look like with the five verbs.** `store.ts` loses the ritual wrapper, the `live` guard, the hand-built `recordEvent` envelope and the `writerGate` import — roughly 104 → 55. `index.ts` loses its `body()` reader (see below) and the manual scope re-check, 130 → ~95. `delivery.ts` keeps its retry logic, which is genuinely its own. `contract.ts` is unchanged. Call it **403 → ~230**, with zero kernel imports and the table owned by `api.migrate`. That is still not pi's twenty lines, because durable webhook delivery is not a twenty-line feature — but it stops being a kernel module that happens to live under `ext/`.

Two specific conflicts with confirmed items. `index.ts:38-55` is an **eleventh copy of the hand-rolled body reader** that items 5 and 19.1 delete ten copies of, with its own byte cap and its own timeout. And `delivery.ts:82` is a `while(true) … Effect.sleep("100 millis")` poll that fetches **one event at a time** (`limit: 1`, `delivery.ts:47`) from boot's event route: idle delivery costs ten boot event queries per second per subscription, 32 subscriptions are allowed, and maximum throughput is ten events per second per subscription regardless of backlog. Item 8 and SEC-3 are about exactly this loop shape, on exactly this gate.

**The docs page.** `pages/docs/subscriptions.md` is written for an agent but leaks the PR's internal vocabulary: "this slice" (twice), "freeze/drain aborts in-flight **Effect** HTTP work" (line 25 names the library), "Rehearsal, candidate and accepted generations do not send", "boot's existing close-handle restore". Line 3 is the sharpest problem, because it is an instruction an agent cannot act on: "This reference intentionally imports existing kernel services. Ordinary extension handlers can continue to use the small `Api` interface." The page's purpose is to be the example, and it opens by telling the reader the example is not followable.

## D. New defects, ranked

### D.1 A failed database restore or topic move leaves the proxy frozen forever

`database-restore.ts:89-92` defines `release`, and it is reached from exactly two places: `:289` (one narrow preparation-failure path) and `:293` (success). Two reachable failure paths skip it. `:283` returns `Effect.failCause` when preparation failed *after* a replacement store was selected. `:292` calls `resume`, which propagates `installed.cause` at `:184`. The outer pipe at `:295-302` has `Effect.uninterruptible` and `Effect.tapCause`, and no `Effect.ensuring`.

`topic-move.ts` has the same shape: `requests.release` is the last statement at `:172`, and four statements before it can fail past the freeze — `recovery.prepare` at `:152-161`, `assertClosure` at `:162`, `supervisor.start` at `:163`, and the `control("live")` fallback at `:165-171`.

Both gates were frozen with `rejectFrozen = true` (`traffic.ts:19`, `:35`, `:70`), so while frozen the gate does not queue, it **refuses**. `proxy.ts:259-260` takes that gate for every proxied request.

Failure scenario: an agent with ordinary `write` scope calls `POST /api/topics/project/move {"to":"archive/project"}`. Boot freezes the request gate (`topic-move.ts:80`), drains, coordinates the move, and then `recovery.prepare` at `:152` fails — `SQLITE_BUSY` past its 2 s `busy_timeout` (`app-recovery.ts:34`) is enough, and so is any `app_evidence_invalid`. The agent gets a 503. Every subsequent request to the board — authenticated reads, writes, anonymous `/p/**` pages, the UI — returns 503 for the remaining lifetime of the boot process. Nothing else in boot calls `requests.release`; `supervisor.start` does not. `/_boot/*` still answers because it is handled before `:259`, so the edit loop survives, but no edit can clear the gate. `POST /_boot/restart` is the documented recovery and still returns 501. This is one HTTP call from an ordinary agent to a permanent board outage, and it is the clearest violation of the "no acknowledged write is lost, and an agent can always recover by editing" standard in the delta. Fix: `Effect.ensuring(release)` around both operations.

### D.2 Every topic move makes the whole board unavailable for up to 20 seconds

Independent of D.1, and by construction. `traffic.ts:35` refuses instead of queueing when the request gate is frozen, `proxy.ts:259-260` maps that refusal to 503, and `topic-move.ts:80` freezes it for the duration of a block bounded at 20 s (`:149`) plus retire-and-restart. SPEC §7.7 step 4 is explicit that during a freeze "Reads keep flowing to the live child", and §7.1 invariant 5 says a 503 while the app is down carries recovery instructions; this one carries `unavailable()`. The mutation gate (`traffic.ts:19` default, queue of 128 with a 10 s wait) is the behaviour the spec describes, and the new gate is its opposite. Database restore freezing reads is defensible — §7.5 says "hold app traffic as `503 retriable`" — but a topic move is an ordinary product write.

Second-order: `topic-move.ts:83` sends the live child `draining` to terminate its long-polls, so every agent waiting on `/api/messages?wait=60` receives `drained: true` during a topic move. §6.3 defines `drained` as "the answering generation is going away", and it is not. Every waiter re-issues into a gate that refuses them.

### D.3 A pending page-move intent blocks every `/_boot/fs` read and write, and source recovery with them

`source-files.ts:38-49` adds `pageMoveReady()` to `guard`, which wraps *every* source operation including `read` and `browse` (`:177-179`). Any row in `topic_page_moves` whose state is not `completed` fails them all with `publication_pending`. `:404` puts the same check in front of `journal.recover`, so source publication recovery is blocked by the same condition, and `index.ts:78-83` responds to that failure by recording `sourceError` and skipping `EditLock.recover` — across restarts.

Failure scenario: `moveRecovery.afterResolve` (`topic-move-recovery.ts:31-41`) fails with `topic_move_publication_missing` for any row that is neither `completed` nor `prepared`. A `pages_published` row with no committed app batch reaches that branch — restore an app-store backup taken before a completed move and you have one. From then on, every `AppRecovery.prepare` fails, which means every cutover, every restore and every move fails, `SourceFiles.recover` is skipped at startup, and `GET /_boot/fs/app/main.ts` returns `publication_pending`. The way in when everything else is broken is gone, and it does not heal on restart. Narrow trigger, terminal consequence.

### D.4 The watcher reads and hashes the entire app tree every second, holding the edit gate

`source-watcher.ts:64` merges `fs.watch` notifications with `Stream.tick("1 second")` and runs `reconcile` on both. `reconcile` calls `source.observe` (`:18`), which is `guard(observer.capture)` — so it takes the single `SourceFiles` semaphore that also serialises every `/_boot/fs` read, write and `POST /api/reload`. Inside, `source-observation.ts:40` runs `readSourceInventory`, which reads the **full bytes of every file** under `/data/app` (`source-tree.ts:29`) and SHA-256-hashes each one, and `:42` and `:54` each run a correlated `MAX(id)` subquery over the whole `versions` table.

Failure scenario: a normal-sized app — the server package plus a UI source tree, a few hundred files — means boot reads and hashes that tree once per second forever, and `versions` grows with every edit, so the two correlated scans degrade as edit history accumulates. Edit-loop latency becomes a function of source size and edit count. SPEC §7.1 describes a notification-driven watcher with a 100 ms debounce that skips paths whose sha matches the newest `versions` row; the 1-second full-tree poll is not in the spec, and the audit's reason for deleting the watcher family (−295) is stronger after reading it than before.

### D.5 `Effect.die("Conflicting recovery intents")` can make boot refuse to start

`index.ts:72`: if more than one of the four recovery intents is set, boot dies. The die is caught at `:133-137`, which sets `auth` to `null` — so boot answers 503 to everything including the authenticated edit routes, with no way in. I could not construct the state from a single crash: `cutover.ts:170` publishes source before inserting the `cutover` row at `:203`, `database-restore.ts:209` refuses to authorise while any other intent is pending, and the topic move, the cutover and the restore all hold `supervisor.operationGate`. So the mutual exclusion appears to hold today. But it is an invariant across four independently-written tables, enforced by a `die` whose consequence is the one outcome §7.1 invariant 1 forbids, and the comment at `:73` ("No recovery path may select or mutate an authoritative store before this global check") is not what the code does: `:76` calls `AppRecovery.prepare`, which installs an epoch and publishes or aborts the pending batch, *before* `SourceFiles.recover` runs at `:79`. §6.3 and §7.5 both require source publication recovery first. The ordering is only safe because `count > 1` dies.

### D.6 `topic-move-http.ts` is the fifth nested-ternary status table, with one hint for twelve codes

`topic-move-http.ts:45-68` is the pattern item 6 and item 19.2 replace with a `Record<code, {status, hint}>`, and the audit counted it as one of four at `:45-68` (it was new in this delta). Every code gets the same hint: "Retry unavailable operations; inspect /_boot/status if recovery is needed." `retriable: status === 503` then marks `topic_move_recovery_required`, `topic_move_evidence_invalid` and `topic_move_unavailable` as retriable, which is item 6's exact prohibition: these are the codes that mean a human has to look at the box, and an agent will retry them in a loop. `topic-move-schema.ts` declares `code: Schema.String`, so a new code still compiles.

### D.7 Extension route handlers returning a Promise are now uninterruptible

`kernel/ext.ts:398-414` passes `drainPromise = true` to `work()`, which makes a Promise-returning extension route handler `Effect.uninterruptible` (`extension-work.ts:23`). Combined with `server.ts:245-250`, where the drain loop now waits for `lifecycle.requests` to reach zero as well as `lifecycle.mutations`, a hung Promise in any extension route blocks `control("draining")`. The 5-second timeout in `child-process.ts:88` bounds the damage, but the consequence of hitting it during a topic move is `stable === false` at `topic-move.ts:151`, which retires and restarts the live child. One slow extension route turns a topic move into a generation restart. `extensions.md` already warns that a hung Promise can prevent a safe freeze; this extends that from hooks to every extension HTTP route.

## E. What should change in `pr-comments.md`
