### api-surface

I ran the whole agent-facing surface live: built the worktree, enrolled two agents through the real passkey/enrollment ceremony, and walked the golden path from /init with curl (plus three extension install/reload cycles). Items 1, 2, 3, 4 and 22 are substantially implemented and most sub-claims verify exactly: POST /api/read, /api/inbox, /api/ctx, /api/search, /api/agents, PATCH /api/me, GET /api/messages/:id, PATCH and DELETE /api/topics/* all 404; marks now happen on view with mark=0 peeking and provably reserve no sequence and emit no event; extension routes are top level with the collision rule working end-to-end (a duplicate claim fails only the later extension with ext.failed naming the conflict, and a core override loads and is logged in ext.loaded overrides); the cursor contract, the fence rename, cursor_ahead on both rails, the one envelope, the boot-merged manifest with no dangling $refs, and the init.md-only version stamp all behave as decided; the digest installs from examples/extensions/digest.ts and works. Five gaps. The most consequential is in the new notification primitive itself: the mention parser keeps a sentence-final period inside the target, so "over to you @codex." is stored as mention @codex. and is silently invisible to the recipe /init and recipes.md tell every agent to use. Second, enrolment still accepts an uppercase host, producing a label that can never be used as a home topic or a mention target - the exact failure item 22's lowercase-host rule was written to prevent, and contradicted by boot's own published route descriptor. Third, an extension registering a single-segment :param route under a prefix core owns as a terminal wildcard passes validation and the collision rule, then throws inside OpenAPI assembly and fails the whole reload with health_failed instead of failing that one extension. Fourth, the repo README still documents six deleted routes as live API. Fifth, a fresh database still gets the reactions table and the kernel still carries reaction/read idempotency families.

### A-1 [major] A mention ending a sentence is stored with its period and never matches mentions=

`packages/server/src/ext/core/message-mentions.ts:6` (api-surface)

- **C-1 The kernel health probe hard-codes the core extension's product routes, so the one removable extension cannot actually be removed or replaced**: The code is as quoted (kernel/health.ts:67-93 POSTs /api/messages, GETs /api/messages and /api/topics/:path and decodes @comms/protocol Message; :49 fails health_route_failed on non-200; conversation.ts:9-52 has no fallback), but this is exactly what the spec mandates, not a defect. ## Findings

### 1. Major — automatic read marks turn every authenticated read into a writer-gated mutation, and make reads fail 503 once the writer is poisoned (item 1)

`packages/server/src/ext/core/read-marks.ts:16-23` marks by calling the full durable combinator:

```ts
export const markRead = (sql, mutate, identity, input) =>
  mutate({ body: () => Effect.gen(function* () {
    yield* sql`INSERT INTO reads(...) ON CONFLICT(instance,topic) DO UPDATE SET seq=excluded.seq WHERE reads.seq<excluded.seq`;
    return { outcome: undefined, events: [] }; }) });
```

`mutate` (`packages/server/src/kernel/mutate.ts:41-46`) takes the single global writer permit, runs `assertWriterHealthy`, then `relay`, then a `sql.withTransaction` with `writerGate`. There is no "would this mark move?" pre-check anywhere on the path (`api.ts:59`, `topics-http.ts:36` → `read-view.ts:13` → `capabilities.ts:103-114`, which only guards lifecycle state, path validity and `seq > fence`). Item 1 asked for "a plain upsert with no `seq` and no event unless it moves" and the checklist row says "Avoid work/events for unchanged marks".

Concrete failure: `assertWriterHealthy` (`kernel/lifecycle.ts:25-32`) fails with `boot_unavailable` whenever `lifecycle.healthy` is false, and `poisonUncertainWriter` (same file, :35-42) sets it false on any non-`Fail` cause from a mutation or an outbox relay pass (`outbox.ts:93` `Effect.tapCause(poisonUncertainWriter)`). `boot_unavailable` maps to **503** (`packages/protocol/src/errors.ts:146-149`), and `markView`'s error is not caught at `ext/core/api.ts:59` (`markView(...).pipe(Effect.as(result))`) or `topics-http.ts:36` (`yield* markView(...)`). So after one uncertain writer transaction, a plain `GET /api/messages` or `GET /api/topics/:path` — which returned its rows successfully a line earlier — is converted into a 503, even though `build-plan.md` states the contract as "Uncertainty refuses mutation while authentication, status and safe source diagnostics remain available". The only escape is `?mark=0`, which agents have no reason to send. The steady-state cost is separate and also real: every authenticated read now serializes on the one writer semaphore and opens a write transaction plus a relay pass, even when `reads.seq` is already at or above the returned seq.

### 2. Major — item 21: boot still carries the topic-move coordinator and the atomic page-subtree rename, with no live producer

Item 21 and `boot-audit.md` list "atomic page-subtree rename and topic-move coordinator" for removal, and the scratchpad records the accepted consequence "Topic-page moves become re-runnable, not atomic". Moves are now app-owned (`packages/server/src/ext/core/topic-move.ts`, used by `topic-management-http.ts:14`), and `boot/src/topic-move-recovery.ts:22` says so: `if (!found) return; // New app-owned moves need no boot page intent.`

But boot retains the whole mechanism: `boot/src/topic-page-move.ts` (158 lines — a `prepared|publishing|published|completed` state machine over `topic_page_moves`, with full recursive tree hashing including dev/ino identity at :43-81 and `fs.rename` at :113), `boot/src/topic-move-recovery.ts` (43), `boot/src/topic-move-schema.ts`, both tables in `boot-schema.ts:148-155` and `topic-move-schema.ts:19-23`, the interlock that blocks source admission while a page move is pending (`boot/src/source-files.ts:50`), the recovery-intent probe (`boot/src/recovery-intents.ts:9-10`), and the legacy prepared-move check in the append path (`boot/src/events.ts:169-179`). Grepping every writer confirms nothing inserts a row any more — `INSERT INTO topic_moves` / `INSERT INTO topic_page_moves` has zero non-test hits in `boot/src` and `server/src`; only SELECT/UPDATE/DELETE remain. Cost: roughly 350–500 production lines of boot, two boot tables and a source-admission interlock kept alive for rows only a pre-cutover generation could have written, against an item whose stated purpose was cutting boot to its six jobs. `build-plan.md` says "Most requested policy removals are implemented"; this named one is not.
