### edit-loop-and-recovery

Dimension: the edit loop, cutover, restore and recovery, at 2ee17ac.

Most of what the owner asked for in this area landed and landed well. Item 28's queue-vs-freeze arithmetic is fixed properly (traffic.ts:32-53 now carries one 60-second budget over the 10+30+5 second frozen region instead of a 10-second per-wait timer), page publication and page undo now wait on `events.changed` instead of answering a retriable 503 (index.ts:204-231), item 30's `die` became a typed `RecoveryRejected` refusal (index.ts:129-131) with lock and revert kept reachable for a human in the Failed phase (edit-http.ts:51-68), and the whole `topic_page_moves` recovery intent that item 30 worried about is simply gone from the live path (recovery-intents.ts:14-17). Reader retirement and the relay wake both check out.

Three defects, all majors:

D-1. Item 28's edit-lock half is not done. cutover.ts:350-352 still runs `sources.recover` → `sources.discard` → `finish(owner,false)` as bare statements with no finalizer anywhere in the file, so an `external_conflict` or ENOSPC inside the journal replay leaves `edit_lock.cutover_in_flight = 1` for the life of the process. `acquire`, `stage`, `release` and `pin` all refuse a pinned lock, and `breakLock` on a pinned lock only records `pending_release` — so a human passkey cannot clear it either. The only exit is a signed `/_boot/restart`, and even that skips `EditLock.recover` when `SourceFiles.recover` is still failing (index.ts:155). The borrowed-lock paths already have exactly the `Effect.ensuring` this needs, at cutover.ts:388-398.

D-2. `supervisor.run` only re-enters `recover` after it observes a child exit; with `current` null it spins in a 100 ms idle loop forever (supervisor.ts:326-331). Every rollback path therefore has to restart the child itself through `supervisor.restart`, whose compensating `withdraw; release` fires only for a single-reason `ChildError` (supervisor.ts:269). One non-`ChildError` restart failure on the cutover rollback, the hourly backup or a restore leaves boot with no child, a still-frozen mutation gate, and no retry — 503 for everything until a human signs a restart, even though a known-good generation is sitting right there. This is also where the hourly-backup half of item 28 still bites: the `addFinalizer` that commit 4147a1a put in database-backup.ts was later removed, leaving `Effect.scoped` at :124 with nothing registered in it.

D-3. Commit ba5866b deleted `POST /api/fs/edit` (now 405, edit-http.ts:280) and the boot README calls it an "owner-approved scope change [that] supersedes SPEC §§6/7.5". SPEC.md:250/274/568/705 all still declare the route, and `docs/pr-1/pr-comments.md` items 1-31 say nothing about it. The conditional-write replacement itself is correct — it cannot publish a partial tree and cannot bypass the lock — but the removal is an unrecorded spec deviation asserted as an owner decision. This is the clearest instance of the reframing the brief asked me to watch for; the scratchpad's "raw line count is irrelevant to acceptance" framing is honest about what it drops, but this README line invents an approval.

Three riskiest changes I could not find a defect in: (1) the `traffic.ts` admission rewrite — the `uninterruptibleMask` with `restore` only around `Deferred.await`, the `Effect.ensuring` decrement of `waiting`, and the `Effect.addFinalizer` decrement of `admitted` in the request scope are all correctly placed, and no interleaving I could construct leaks or double-counts a slot. (2) `legacy-topic-moves.ts` — 282 lines of one-shot startup reconciliation that dual-opens the app store, cross-checks `topic_moves`, `topic_page_moves`, `event_batches`, the allocator and a filesystem tree fingerprint before renaming anything, and drops both tables in one transaction only after every row has terminal evidence; the refusal has no in-band clear, which I flagged as "partly", but I could not find a state where it retires a row it should have preserved. (3) `source-revert.ts`'s keyed idempotent revert receipts — the interaction between `reconcilePage`, the cutover check at :219 and `prune`'s refusal to infer a terminal outcome from age is subtle and, as far as I could follow it, correct.

packages/server/src/kernel/extension-routes.ts:1-19 — reserved() covers /_boot, /_kernel, /api/fs|lock|reload|revert|generations|tokens, /auth, /approve, /setup and the exact set /health, /api, /api/ext, /init, /init.md, /.well-known/agent.json. /api/events and /api/stream appear nowhere, which was harmless while boot's proxy intercepted them.

packages/server/src/ext/core.ts:9-13 — `export default function core(api: Api) { api.mount(CoreApi, coreHandlers(api)...) }`: core is itself a loaded extension. packages/server/src/kernel/ext.ts:180-183 — inside `mount`, `for (const route of mounted.routes) { validateRoute(...); pending.push({ extension: name, ...route }); }`, so GET /api/events and GET /api/stream (registered via ext/core/api.ts:103-104) land in `registrations` owned by "core.ts". packages/server/src/kernel/ext.ts:243-257 then permits a later extension to take them: the conflict only fails when `!/^core\.(ts|js)$/.test(existing.extension) || pattern(existing.path) !== pattern(route.path)`; otherwise it records `overrides.push(...)` and the extension wins.

Concrete failure: an agent writes app/ext/quiet.ts registering `GET /api/events` with `scope: "fs"` (or a handler that returns an empty page). Reload succeeds — kernel/health.ts:66-92 probes only /api/messages and /api/topics, never the event routes, so the health gate does not catch it. Every read-scope agent's event rail now 403s or silently returns nothing, and the recovery instructions in /init and the edit-lock refusal point at exactly that route. SPEC.md:413 invariant 2 says of /api/events and /api/stream: "No edit to the app can remove, break, or re-auth the routes used to edit the app." That guarantee is now false in code, and unlike C-1 it is not merely a relocation — it is an app-editable kill switch on the recovery rail, which is the class SPEC.md:696 and pr-comments.md:145 explicitly did not accept as a weakening. Minimum fix if the move stands: add "/api/events" and "/api/stream" to reserved(), or exclude them from the core-override allowance at ext.ts:247-252.


### edit-loop-and-recovery

**Item 30's "way in" is itself gated on recovery succeeding, so a deterministic recovery failure still leaves no in-band HTTP route back into the edit loop.** `writable` is `phase === "Ready"` (proxy.ts:212). In the Failed phase, edit-http.ts:52-62 is the whole escape hatch:

```
if (!writable && identity.kind === "human" && ((route === "/_boot/lock" && ["POST","DELETE"].includes(request.method)) || (route === "/_boot/revert" && request.method === "POST"))) {
  yield* humanSession(auth, request);
  yield* editing.retryRecovery(Effect.asVoid(humanSession(auth, request)));
  yield* humanSession(auth, request);
  writable = true;
}
```

`retryRecovery` is `index.ts:118-175`, which re-runs the identical sequence and, on failure, re-sets the phase to Failed and `return yield* Effect.failCause(recovered.cause)` (index.ts:158-164). So `writable = true` is never reached and the request answers with the recovery failure. Every repeat call repeats it, and `POST /_boot/restart` only restarts the process into the same deterministic failure.

The failures that are deterministic by construction:
- `retireLegacyTopicMoves` refusing (legacy-topic-moves.ts:150, :158, :167, :169, :250, and the blanket `Effect.mapError(refused)` at :282), which the reviewer already noted "sets the phase to Failed permanently ... there is no route that can clear or acknowledge the condition" — but filed as a status, not as the item-30 gap it is;
- `coordinator.recover` (index.ts:152) → `restore(record)` failing `cutover_backup_missing` / `cutover_backup_invalid` (cutover.ts:66, :72) when the pre-flip backup row or file is gone;
- any `restore.recover` / `reverts.recover` failure at index.ts:153-154.

Failure scenario, and it composes with D-1 and D-2: a reload fails, `sources.recover` fails, the lock stays pinned and the batch stays `state='publishing'` (D-1). An operator restarts the box to clear the pin. Startup recovery now hits the still-broken condition (say the legacy refusal, or a missing cutover backup), the phase goes Failed, and the human's `POST /api/lock` and `POST /api/revert` — the two routes item 30 named — each re-run the same recovery and return the same failure. `GET /_boot/recovery` renders, `GET /_boot/fs/**` reads, `POST /_boot/restart` restarts into the same state; nothing writes. Item 30's line is "keep the lock and revert pair writable in the Failed phase so a human can always get back in", and the pair is writable only when the failure was transient — the case the item was not about. Fix: attempt `retryRecovery`, but fall through to `writable = true` on its failure (the routes already re-verify the human session at edit-http.ts:58/:60 and revert already runs through `withBorrowedLock`), instead of propagating the recovery cause to the caller.
