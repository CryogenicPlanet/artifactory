## A. Inventory of SQLite-specific dependencies

### A.1 Dialect-level SQL

**PRAGMA and `user_version` as the migration ledger.** Three separate bootstraps use `PRAGMA user_version` as the schema version and a hand-written `if (version < n)` ladder.

| Site | What it does | Postgres | MySQL |
| --- | --- | --- | --- |
| `packages/boot/src/boot-schema.ts:24` read, `:30-31` `journal_mode`/`synchronous`, `:72` `PRAGMA user_version = 12` | boot schema v0 to v12 ladder, lines 35-71 | no equivalent; use a ledger table. `journal_mode` has no analogue; `synchronous=FULL` maps to `synchronous_commit=on`, the default | same; `innodb_flush_log_at_trx_commit=1` is the default |
| `packages/server/src/kernel/database.ts:13-20`, `:41`, `:50`, `:63`, `:68`, `:72` | app schema v0 to v6 ladder | as above | as above |
| `packages/boot/src/app-backup.ts:21` `busy_timeout`, `:33` `user_version` | probe a clone to decide the rehearsal sequence floor | `lock_timeout` / `statement_timeout` | `innodb_lock_wait_timeout` |
| `packages/boot/src/app-recovery.ts:22-23` | `busy_timeout`, `synchronous=FULL` on the app store before reading recovery evidence | as above | as above |
| `packages/boot/src/public-pages.ts:66` | `user_version` used to distinguish "boot-only store, app has not created its schema yet" from "store is broken" | needs a ledger query, and `to_regclass` for the table probe | `information_schema.tables` |

Effect v4 has a real `Migrator` at `repos/effect/packages/effect/src/unstable/sql/Migrator.ts`. `Migrator.make({})({loader, table})` creates the ledger with per-dialect DDL at lines 120-151, takes `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE` on Postgres at line 222, and classifies a concurrent run as `Locked` through `UniqueViolation`/`ConstraintError` at line 326. `packages/server/src/kernel/migrations.ts:48` already uses it for app-owned migrations with `table: "migrations"`. The two `user_version` ladders are the parts that predate it.

**`sqlite_master`.** `packages/boot/src/public-pages.ts:64` probes `SELECT name FROM sqlite_master WHERE type='table' AND name='topics'`. Postgres: `to_regclass('comms.topics') IS NOT NULL`. MySQL: `information_schema.TABLES`.

**`AUTOINCREMENT`.** `packages/boot/src/boot-schema.ts:37` `n INTEGER PRIMARY KEY AUTOINCREMENT` for `generations`, and `packages/boot/src/source-schema.ts:68` for `versions.id`. Postgres: `GENERATED BY DEFAULT AS IDENTITY`. MySQL: `AUTO_INCREMENT`. Both are DDL-only, so they live in per-dialect migrations and never touch query code.

**`INSERT OR REPLACE` and `INSERT OR IGNORE`.** Six sites: `packages/boot/src/edit-lock.ts:233` combines `INSERT OR REPLACE` with the v4 `sql.insert()` helper; `packages/boot/src/application.ts:108` and `:117`; `packages/boot/src/generations.ts:32`; `packages/boot/src/app-recovery.ts:30` and `:97`. Postgres: `ON CONFLICT ... DO UPDATE` or `DO NOTHING`. MySQL: `INSERT ... ON DUPLICATE KEY UPDATE` or `INSERT IGNORE`. Note that `INSERT OR REPLACE` deletes then inserts in SQLite, so it drops unmentioned columns to their defaults; on the `edit_lock` singleton every column is supplied, so the rewrite to an upsert is behaviour-preserving.

**`ON CONFLICT ... DO UPDATE` with `excluded`.** Seven sites: `packages/boot/src/tokens.ts:137` `DO NOTHING`; `packages/boot/src/storage-maintenance.ts:22`; `packages/boot/src/edit-lock.ts:193`; `packages/server/src/kernel/profiles.ts:59`; `packages/server/src/kernel/extension-data.ts:53`; `packages/server/src/kernel/reaction-operations.ts:88`; `packages/server/src/kernel/read-marks.ts:72`. Postgres accepts all of these verbatim, `excluded` included. MySQL needs `ON DUPLICATE KEY UPDATE` and the 8.0.19 row-alias form `AS new` instead of `excluded`.

One of these is worse than the rest. `packages/server/src/kernel/read-marks.ts:72` does `DO UPDATE SET seq=MAX(reads.seq,excluded.seq)`. Two-argument `MAX` is a scalar function in SQLite and an aggregate in Postgres and MySQL, so this is a silent semantic change, not a syntax error. Both need `GREATEST(...)`.

**FTS5.** The whole search path is SQLite-only.

| Site | Content |
| --- | --- |
| `packages/server/src/kernel/database.ts:58` | `CREATE VIRTUAL TABLE messages_fts USING fts5(message_id UNINDEXED, body, previous_body, tokenize='unicode61 remove_diacritics 2')` |
| `:59` | backfill via `INSERT INTO messages_fts(rowid,...) SELECT rowid,...` |
| `:60-62` | three triggers keyed on `new.rowid` / `old.rowid` |
| `:79` | a startup shape probe against `messages_fts` |
| `packages/server/src/kernel/messages.ts:270-276` | `messages_fts MATCH 'body : ("a" AND "b")'`, unioned with a `previous_body` match for the unpublished image |

Postgres: a `tsvector` column with a GIN index, `to_tsvector('simple', body)` maintained by a generated column or a trigger, and `@@ websearch_to_tsquery` or `plainto_tsquery`. The `unicode61 remove_diacritics 2` tokenizer maps onto `unaccent` plus the `simple` configuration. The two-column trick at `messages.ts:270-276`, which indexes both the current and the previous body so a published read never sees an unpublished edit, becomes two `tsvector` columns or one index on a `CASE` expression. MySQL: `FULLTEXT KEY` with `MATCH ... AGAINST (... IN BOOLEAN MODE)`, which cannot express per-column matching in a multi-column index, so it needs two separate `FULLTEXT` indexes, and its default minimum token length of 3 will silently drop short terms that SQLite matches today.

The quoting discipline at `packages/server/src/kernel/messages.ts:257-268` is per-engine too. It quotes every caller term so text cannot become FTS syntax. The equivalent safety for Postgres is `websearch_to_tsquery`, and for MySQL it is stripping the boolean operators `+ - > < ( ) ~ * " @`.

**`json_extract`, `json_each`, `json_object`.** 24 and 2 and 1 occurrences.

| Site | Use |
| --- | --- |
| `packages/boot/src/events.ts:185-191` | the entire `/_boot/events` filter: topic prefix, actor, instance, level, and a `json_each` over the requested type list with a trailing-`*` prefix rule |
| `packages/boot/src/event-retention.ts:37-38` | retention reads `$.at` and `$.type` out of the stored event JSON |
| `packages/server/src/kernel/published-messages.ts:8-12` | five `CASE WHEN updated_seq>ceiling THEN json_extract(previous,'$.x') ELSE x END` columns |
| `packages/server/src/kernel/published-topics.ts:6-8` | three more |
| `packages/server/src/kernel/messages.ts:283` | `EXISTS (SELECT 1 FROM json_each(visible_messages.tags) WHERE value=?)` for tag filtering |
| `packages/server/src/kernel/database.ts:49` | a one-time backfill using `json_object(...)` and `json(...)` |
| `packages/server/src/kernel/database.ts:59-61` | `json_extract(new.previous,'$.body')` inside the FTS triggers |

Postgres: `jsonb` columns with `->>`, `#>>`, and `jsonb_array_elements_text`. MySQL: `JSON_EXTRACT`/`->>` and `JSON_TABLE` or `JSON_CONTAINS`. All three need a typed cast discipline, because `json_extract` in SQLite returns a dynamically typed value while `->>` in Postgres always returns text, and the decoders at `packages/server/src/kernel/messages.ts:46-50` expect `edited_at` and `deleted_at` to decode as `Schema.NullOr(Schema.Int)`. This is the single most invasive group: it changes the shape of the published-image views that every read path composes.

**`rowid`.** `packages/server/src/kernel/database.ts:59-62` uses `rowid` as the FTS join key in the backfill and in all three triggers. Neither Postgres nor MySQL has an implicit row identity. The replacement is `messages.id`, which is already `TEXT PRIMARY KEY` at `database.ts:33` and already carried as `message_id UNINDEXED` in the FTS table, so this is a simplification rather than a loss.

**`substr` and `length` prefix matching.** 33 occurrences implementing "is this path a descendant of that path". The canonical form is `substr(x,1,length(y)+1)=y||'/'`. Representative sites: `packages/server/src/kernel/messages.ts:144`, `:147`, `:280`; `packages/server/src/kernel/published-messages.ts:15`; `packages/server/src/kernel/topics.ts:53-58`, `:96`; `packages/server/src/kernel/topic-delete.ts:52`, `:60`, `:70`; `packages/server/src/kernel/read-marks.ts:11`, `:63`; `packages/server/src/kernel/message-operations.ts:71`, `:84`; `packages/server/src/kernel/topic-operations.ts:63`, `:72`; `packages/server/src/kernel/reaction-operations.ts:75`, `:78`; `packages/server/src/kernel/pages.ts:42`; `packages/boot/src/public-pages.ts:78`, `:81`, `:130`; `packages/boot/src/events.ts:185`, `:187`, `:191`.

`substr` and `length` exist in all three engines. The portability break is `||`, which is string concatenation in SQLite and Postgres but logical OR in MySQL unless `PIPES_AS_CONCAT` is set. MySQL needs `CONCAT(y,'/')`. Postgres also offers `starts_with(x, y || '/')`, which is index-friendly with a `text_pattern_ops` index, where the `substr` form is not. One helper fixes all 33 call sites and improves Postgres plans at the same time.

**Integer booleans.** `generations.good` at `packages/boot/src/boot-schema.ts:39`, `edit_lock.cutover_in_flight` at `:52`, `versions.versioned` at `packages/boot/src/source-schema.ts:68`, `child_attempts.opened`/`closed` at `packages/boot/src/cutover-schema.ts:6`, `reactions.active`/`previous_active` at `packages/server/src/kernel/database.ts:56`. Every one is decoded as `Schema.Literals([0, 1])`, for example `packages/boot/src/generations.ts:9`. Keep them as `SMALLINT` on Postgres and `TINYINT` on MySQL and never let them become `boolean`, or every one of those decoders breaks. This is a trap rather than a cost.

**`IS NOT` as null-safe inequality.** `packages/boot/src/events.ts:187` uses `json_extract(event,'$.instance') IS NOT ?` so that a NULL instance still passes the exclusion filter. Postgres: `IS DISTINCT FROM`. MySQL: `NOT (a <=> b)`. Exactly one site, and getting it wrong silently drops events from a long-poll rather than erroring.

**`RETURNING`.** Five statements, and they are the load-bearing ones.

| Site | Statement | Why it matters |
| --- | --- | --- |
| `packages/server/src/kernel/database.ts:7` | `UPDATE kernel_writer SET epoch=epoch WHERE singleton=1 AND epoch=? RETURNING epoch` | the writer-epoch fence; every kernel write transaction starts here |
| `packages/boot/src/app-recovery.ts:32` | `UPDATE kernel_writer SET epoch=? WHERE singleton=1 RETURNING epoch` | boot installs a fresh epoch during recovery |
| `packages/boot/src/generations.ts:35-36` | `INSERT INTO generations (...) VALUES (...) RETURNING *` | reserves the generation number |
| `packages/boot/src/auth.ts:321` | `UPDATE sessions SET last_seen_at=? WHERE hash=? AND expires_at>? RETURNING id, expires_at` | session validation and presence in one round trip |
| `packages/boot/src/event-retention.ts:36-38` | `DELETE FROM events WHERE ... RETURNING seq` | counts what retention actually pruned |

Postgres supports all five verbatim, and `repos/effect/packages/effect/src/unstable/sql/Statement.ts:995-1002` shows the compiler emits `RETURNING` for every dialect except mssql, which gets `OUTPUT`. MySQL supports none of them. The replacements are safe only because of the fence: `UPDATE` followed by `SELECT` in the same transaction is atomic given the row lock the `UPDATE` already took. For `generations` the replacement is `LAST_INSERT_ID()`. For retention it is `SELECT` the candidate `seq` values first, then `DELETE ... WHERE seq IN (...)`, which the chunking loop at `packages/boot/src/event-retention.ts:26-46` already has the shape for.

**Partial unique index.** `packages/boot/src/source-schema.ts:66` is `CREATE UNIQUE INDEX source_single_publication ON source_batches(state) WHERE state = 'publishing'`. This enforces the spec's "at most one batch publishes at a time" in the database rather than in code. Postgres supports partial indexes verbatim. MySQL has no partial index. The MySQL equivalent is a stored generated column, `publishing_singleton AS (CASE WHEN state='publishing' THEN 1 ELSE NULL END)`, with a unique index on it. That works, but it is the second MySQL-only schema contortion, after the VARCHAR keys.

**`TEXT PRIMARY KEY`.** 15 columns, 11 composite primary keys over text, 4 text UNIQUE constraints. MySQL cannot index `TEXT` without a prefix length, so every one becomes `VARCHAR(n)` with a chosen `n`. The ids are bounded in practice: `m_` plus 24 hex at `packages/server/src/kernel/messages.ts:113`, `f_` plus 43 base64url at `packages/boot/src/refresh-schema.ts:7`, 64 hex epochs and attempts at `packages/boot/src/supervisor.ts:96`. Topic paths are capped at 200 at `packages/server/src/kernel/messages.ts:52`. Idempotency keys are capped at 200 at `packages/server/src/kernel/messages.ts:107`. So `VARCHAR(256)` covers everything, and MySQL's `utf8mb4` 3072-byte index limit accommodates the composite keys. Postgres needs no change.

**Bare columns in `GROUP BY`.** `packages/boot/src/agent-roster.ts:15-25` selects `e.agent_name`, `e.kind`, `e.host`, `e.collected_at` while grouping only by `e.family`, and similarly `t.agent`, `t.label` grouped by `t.family`. SQLite permits this and picks an arbitrary row. Postgres rejects it outright. MySQL rejects it under the default `ONLY_FULL_GROUP_BY`. The fix is to wrap the bare columns in `MIN()` as `packages/boot/src/account-queries.ts:56-62` already does for the token-family listing, or to add them to the `GROUP BY` since `family` is unique in `enrollments` anyway per `packages/boot/src/enrollment-schema.ts:30`.

**`LIMIT` on `UPDATE`/`DELETE`.** I found none. Every `DELETE` is keyed or range-bounded, for example `packages/boot/src/event-retention.ts:36` bounds by `seq` range after a `SELECT ... LIMIT 256`. Nothing to port.

**BLOB columns bound from `Uint8Array`.** `staging.content` at `packages/boot/src/boot-schema.ts:56`, `source_changes.before`/`desired` at `packages/boot/src/source-schema.ts:67`, `versions.content`/`previous_content` at `:68`, bound through `sql.insert()` at `packages/boot/src/source-journal.ts:56` and `:81` and decoded as `Schema.NullOr(Schema.Uint8Array)` at `packages/boot/src/source-schema.ts:28` and `:55-58`. `repos/effect/packages/effect/src/unstable/sql/Statement.ts:1136` classifies `Uint8Array` as a primitive kind, so all three drivers bind it. Postgres wants `bytea` and returns a Buffer; MySQL wants `LONGBLOB`, because source files up to 1 MiB are stored inline per the eligibility rule at `packages/boot/src/source-journal.ts:79-81` and plain `BLOB` caps at 64 KiB.

**Raw user SQL placeholder style.** `packages/server/src/kernel/sql-read.ts:37` is `sql.unsafe(\`SELECT * FROM (${input.sql}\n) LIMIT 201\`, params)`. The params are positional. `repos/effect/packages/sql/sqlite-bun/src/SqliteClient.ts` and `repos/effect/packages/sql/mysql2/src/MysqlClient.ts:464` both use `?`; `repos/effect/packages/sql/pg/src/PgClient.ts:366-368` uses `$n`. So agent-authored SQL submitted to `POST /api/sql` with `?` placeholders works on SQLite and MySQL and fails on Postgres. The `LIMIT 201` wrapper is also not portable to mssql, which does not matter here, but the `SELECT * FROM (subquery)` form needs an alias on MySQL.

### A.3 Concurrency semantics the code relies on

**`BEGIN IMMEDIATE` as the write lock.** `repos/effect/packages/sql/sqlite-bun/src/SqliteClient.ts:238` sets `beginTransaction: options.readonly === true ? "BEGIN" : "BEGIN IMMEDIATE"`, and the module doc at `:114` states that explicit transactions on writable connections take the write lock for their whole duration even when they only read. Every `sql.withTransaction` in the app is therefore globally serialized against every other one on the same file. The code leans on this in two distinct ways.

First, as a write lock. Second, and less obviously, as a read snapshot. `packages/server/src/kernel/published-messages.ts:4-5` says "Capture a SQL snapshot before reading boot's fence", and the read paths open with a throwaway `SELECT epoch FROM kernel_writer` to take that snapshot: `packages/server/src/kernel/messages.ts:246` and `:294`, `packages/server/src/kernel/topics.ts:49` and `:127`, `packages/server/src/kernel/reaction-operations.ts:133`, `packages/server/src/kernel/extension-data.ts:63`, `packages/server/src/kernel/pages.ts:38`. On SQLite that statement acquires the write lock and pins the file for the rest of the transaction, so the multi-statement read that follows is serializable against concurrent writers.

Postgres defaults to READ COMMITTED, where each statement gets its own snapshot. The `SELECT epoch` prelude acquires no lock and pins nothing, so the published-image reads at `packages/server/src/kernel/messages.ts:279-285` and `packages/server/src/kernel/topics.ts:52-58` could observe a partially applied mutation across statements. This is the subtlest porting hazard in the whole codebase, and it is invisible in testing until there is concurrency. The fix is a real isolation level: issue `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` as the first statement of every read transaction on Postgres. MySQL InnoDB already defaults to REPEATABLE READ, so it needs nothing. SQLite needs nothing because `BEGIN IMMEDIATE` already does it. Effect's `SqlClient` fixes `beginTransaction` per client at `repos/effect/packages/effect/src/unstable/sql/SqlClient.ts:171`, so the isolation level has to be a first statement rather than a client option, or a second read-only client layer.

**Writer-epoch fencing via `UPDATE ... RETURNING`.** `packages/server/src/kernel/database.ts:5-9` is the fence, and it is invoked at the top of every kernel write transaction: `messages.ts:121`, `:92`; `message-operations.ts` inside `mutateMessage`; `topic-operations.ts`; `topic-delete.ts`; `reaction-operations.ts`; `read-marks.ts:44`; `profiles.ts:57`; `operational-events.ts:44`; `migrations.ts:47`. Boot installs a fresh epoch at `packages/boot/src/app-recovery.ts:32`.

This construct ports well, and on Postgres it is stronger than it is today. The conditional `UPDATE` takes a row lock on the `kernel_writer` singleton, so two live writers serialize on that row and the stale one sees zero affected rows and fails `stale_writer`. Postgres gets the same serialization without the file-level lock, which means better concurrency for the same guarantee. On MySQL the same holds, with the `RETURNING` replaced by a following `SELECT` under the held row lock. The fencing design turns out to be engine-neutral by construction, which is the single best piece of news in this report.

**Transactional outbox ordering.** The mutation path writes domain rows, a `mutation_batches` receipt, and one `outbox` row per event inside one transaction, then ships over HTTP and marks `shipped_at` in a second transaction: `packages/server/src/kernel/messages.ts:207-212`, the relay at `:82-97`, and the boot side at `packages/boot/src/events.ts:57-108`. Recovery reconciles the two stores at `packages/boot/src/app-recovery.ts:34-91` by matching `mutation_batches` against `outbox` rows and requiring exact contiguity. Every statement here is portable. The ordering guarantees come from the single transaction and the epoch fence, not from SQLite.

**The seq allocator lease.** `packages/boot/src/events.ts:123-156` reserves a range in one boot transaction against a `seq` singleton and an `event_batches` receipt, and `:56` publishes by setting `published_through=next-1`. All portable. The only engine coupling is that on SQLite this transaction contends with every other boot transaction on the same file, which is why `packages/boot/src/events.ts` is careful to keep the reserve path short. On Postgres the contention narrows to the `seq` row.

**Bounded network calls inside the SQL write lock.** `SPEC.md` §6.3 requires that network calls made while holding the SQL write lock are bounded, and `packages/server/src/kernel/boot-channel.ts:106` enforces a 1500 ms timeout on every boot call. `boot.reserve` is called from inside `sql.withTransaction` at `packages/server/src/kernel/messages.ts:158`. On SQLite that means the global write lock is held across an HTTP round trip. On Postgres it means one row lock is held across the same round trip, which is better. On a remote engine it means the lock is held across two network hops instead of one, and the 10-second freeze budget in `SPEC.md` §7.7 step 4 now has to absorb both. Worth measuring, not worth redesigning.

## B. The guarantees that are file-shaped

### B.1 Rehearsal on a copy

What the spec actually demands is stronger than "the migration parses". `SPEC.md` §7.4 requires a candidate process, on a scratch port, against a consistent online snapshot, invoking the real assembled `POST /api/messages`, `GET /api/messages` and `GET /api/ctx` handlers inside a rolled-back transaction. `packages/boot/src/cutover.ts:131-149` implements exactly that.

Candidate (i), Postgres transactional DDL with a rollback, does not satisfy this. A transaction lives in one connection and one process; you cannot hand an uncommitted schema to a separate child process and run its HTTP self-test against it. Taking (i) means downgrading rehearsal to "run the migration effects in-process and roll back", which drops the self-test that catches `ext/core.ts` returning 500 and the route-shape failures the spec lists explicitly. That is a guarantee the owner should not trade away, and MySQL's lack of DDL rollback is then irrelevant because nobody is rolling back DDL.

Candidate (ii), schema-per-generation with a pointer switch, does satisfy it, and it is the right mechanism. `CREATE SCHEMA comms_gen_13`, load the data, point the child at it with `search_path` or a qualified descriptor, run the self-test, drop it. The cost is the load. There are two ways to populate and they are not equivalent:

- **Logical copy of the live data.** `pg_dump --schema=comms` piped into the scratch schema, or `mysqldump --single-transaction` into a scratch database. This preserves the guarantee the spec names: "a migration that drops or renames a column" is caught because the migration runs against real rows. Cost grows with data size. At personal-board scale this is seconds; it is not seconds at a million messages.
- **Empty schema from migrations, then a sample.** Fast and constant-time, but it no longer proves the migration works against real data, which is the specific failure mode §7.4 exists to catch. Do not do this.

`CREATE DATABASE ... TEMPLATE` is tempting and is already dismissed at `docs/tech.md:126`. The dismissal is right for a subtle reason beyond connection count. Template copy needs zero connections to the source. The cutover does reach that state, but only at step 8, after the freeze. `SPEC.md` §7.7 step 2 and `docs/tech.md:134` both require rehearsal to complete before the freeze so it never extends the window where writes are queued. Template copy would move rehearsal inside the 10-second freeze budget. Rejected for the same reason slow work is pushed before the freeze in §7.1.

Recommendation: `DbOps.cloneForRehearsal()` returns an opaque store descriptor. SQLite returns a file path from `VACUUM INTO`, unchanged. Postgres and MySQL return a scratch database name populated by a logical copy. The 30-second rehearsal deadline at `packages/boot/src/cutover.ts:139` becomes configurable and, when exceeded, fails the edit with a distinct code such as `rehearsal_copy_timeout` so the agent is told "your store is too large for the configured rehearsal budget" rather than "your edit is broken". That is the honest weakening: on a remote engine, rehearsal time is a function of data volume, and past some size the owner must either raise the budget or accept a sampled rehearsal.

### B.2 Pre-flip backup

`packages/boot/src/cutover.ts:160-188` freezes, drains, installs the prior epoch, reads `published_through`, clones, and records `{id, path, reason, bytes, taken_at, published_through, generation}` plus a `backup.taken` event in one boot transaction. The guarantee that matters, stated at §7.7 step 8, is "since writes were frozen and drained before the backup, the restore loses nothing". That guarantee rests on the freeze and the drain, not on the copy mechanism.

So this one ports cleanly. `pg_dump -Fc` after the drain is exactly as consistent as `VACUUM INTO` after the drain. `mysqldump --single-transaction` on InnoDB likewise. The `backups` table needs no schema change; only the producer behind `AppBackup.clone` changes, and the `path` column becomes "path to the dump artefact" rather than "path to a database file". No guarantee weakens.

One caveat. `repos/effect/packages/sql/pg/src/PgMigrator.ts:48-64` shows Effect shelling out to `pg_dump` through `ChildProcess.make`, with credentials passed in the environment. So `pg_dump` and `pg_restore` must be present in the image, and `docs/tech.md` §10 lists only `util-linux`. The image gains `postgresql-client` and, for MySQL, `mysql-client`. That is a real but small cost, and `repos/effect/packages/sql/mysql2/src/MysqlMigrator.ts:36-60` shows the MySQL dump path is currently commented out upstream pending a Command module, so chirp would write that part itself.

### B.3 Generation plus database restore

`packages/boot/src/app-backup.ts:49-59` is the close-handle protocol: copy, fsync, remove `-wal` and `-shm`, rename, fsync the parent. The comment at `:55` is the important one: "The caller has positive closure evidence for every process that could own these handles."

On Postgres and MySQL, restoring into a fresh database and switching the connection target is structurally safer than renaming, because nothing is ever mutated under a live reader. `SPEC.md` §7.5 already anticipates this: "or, on Postgres, restore into a fresh database and swap the connection string".

But the closure evidence is not a SQLite artefact and must not be dropped. If an orphaned child still holds a connection to the abandoned database and keeps committing, those writes are acknowledged and then silently lost when the pointer moves. That violates the spec's hardest invariant. So the keeper, the receipt file, and the `child_attempts` bookkeeping at `packages/boot/src/child-attempts.ts` survive on every engine unchanged. What changes is only `AppBackup.restore`, which becomes `restoreInto(descriptor)` and returns the new descriptor for the supervisor to pass down. On Postgres you additionally get a belt-and-braces option SQLite cannot offer: `REVOKE CONNECT` plus `pg_terminate_backend` on the old database, which turns "prove it closed" into "make it closed". Use it as a second check, never as a replacement for the receipt, because a terminated backend may have committed before it died.

No guarantee weakens. One improves.

### B.4 Backup drills

`packages/boot/src/backup-drill.ts:42-64` makes a temp directory under the data directory, copies the backup file, prepares a clone epoch and sequence floor, launches a rehearsal child against it, and removes the scratch only when closure was proven. The `removable` flag at `:43` and `:49-50` exists precisely so that an unprovable launch leaves the bytes behind for diagnosis.

Engine-neutral form: `pg_restore` or `mysql` into `comms_drill_<n>`, launch a rehearsal child against that descriptor, drop it on proven closure and leave it otherwise. Same shape, same `backup.drill` event at `:69-80`, same weekly cadence from `packages/boot/src/storage-maintenance.ts:34`. The "leave the scratch behind when closure is unproven" rule becomes "leave the scratch database behind", which needs a reaper pass on the next boot so a repeatedly failing drill does not accumulate databases. That is a new, small piece of work: about 25 lines and one `settings` key.

### B.5 Disk budgets

This is where a remote engine genuinely loses something, and the report should be blunt about it.

`SPEC.md` §7.5 budgets four things against the volume: backups at 20%, snapshots to the last five good generations plus the live one, events under a 10% cap, and a refusal of any write that would leave less than 5% headroom so a delete always has room to record itself. `/_boot/status` shows usage against each budget.

With the app store on a remote engine, two of those four still work exactly as before, because they are about files on the volume: generation snapshots under `/data/gen` from `packages/boot/src/snapshots.ts`, and backup artefacts, which are now dumps but are still files catalogued in `backups` with a `bytes` column at `packages/boot/src/cutover-schema.ts:7`. The event cap still works because `packages/boot/src/event-retention.ts` prunes rows by policy, not by bytes, and the boot store's own size is whatever engine holds it.

What breaks is the 5% headroom refusal as applied to the store itself, and the honest reporting of store size. A bootloader cannot see a managed Postgres volume's free space, and `pg_database_size` tells you the database size but not the disk's capacity. So:

- Add `DbOps.capacity(): Effect<Option<{used: number; total: number}>>`. SQLite returns `Some` from a `statvfs`-equivalent. Postgres and MySQL return `Some({used: pg_database_size})` with `total: None`, or `None` entirely.
- `/_boot/status` reports "unknown" for the store budget on a remote engine rather than printing a number it cannot justify.
- The write-refusal rule keeps applying to the volume, which still holds snapshots, dumps, staging blobs in `boot.db`, and the caches. That is where the bootloader's own writes land, so the property that "a delete always has room to record itself" is preserved.

Acceptable for SPEC's goals. The three goals stated in §12 are that an agent recovers from a bad edit by editing again, that no acknowledged write is lost, and that a broken generation never becomes live. None of those depend on the bootloader knowing the store's free space. A full remote store surfaces as `SqlError` on a write, and the write response already carries the failure to the agent.

### B.6 "The child gets its own DB path"

Today the child is told an absolute path and nothing else: `APP_DATABASE: filename` at `packages/boot/src/supervisor.ts:115`, read as `filename` at `packages/server/src/kernel/boot-channel.ts:52`, and handed to `SqliteClient.layer` at `packages/server/src/server.ts:189`, `packages/server/src/kernel/sql-read.ts:71`, and `packages/boot/src/public-pages.ts:43`.

The engine-neutral form is a **store descriptor**, one opaque string the child parses into a client layer:

```
file:/data/comms.db
postgres://app:…@host:5432/comms_app?schema=public
postgres://app:…@host:5432/comms_gen_13     (rehearsal)
mysql://app:…@host:3306/comms_app
```

This is the smallest concrete change in the report and it unlocks everything else: one env var renamed, one layer factory in the server that branches on the scheme, one in boot. Roughly 60 lines plus the call-site churn. Three facts make it clean:

1. The child env is built explicitly at `packages/boot/src/supervisor.ts:111-120` and spawned with exactly that map at `packages/boot/src/child-process.ts:44` and `packages/boot/src/child-keeper.ts:30`. Nothing is inherited from boot's own environment. So a boot-only credential never reaches the child, and the app's credential is handed down deliberately per attempt.
2. Rehearsal already receives a different store than live, through the same parameter: `packages/boot/src/cutover.ts:136` passes the clone path, `packages/boot/src/backup-drill.ts:51` passes the drill clone. The descriptor slots straight into that seam.
3. Rehearsal already has no boot secret and no access to the public allocator, by construction at `packages/server/src/kernel/boot-channel.ts:55-90`. That stays true regardless of engine.

## C. Same-engine deployment shape

### C.1 Two databases, not two schemas

Recommendation: one engine instance, **two databases**, two roles. `comms_boot` owned by the `boot` role, `comms_app` owned by the `app` role.

Reasons, in order of weight:

1. The restore and drill paths want to create and drop whole databases. `pg_dump`/`pg_restore` and `mysqldump`/`mysql` are per-database tools. Per-schema dumps work but every invocation needs `--schema=` plumbing and the restore has to rewrite the schema name, which is the kind of string surgery that breaks quietly.
2. MySQL has no schema concept distinct from database, so "two databases" is the only shape that reads the same on both engines. `docs/tech.md:119` currently says "they live in separate schemas (`boot`, `app`)", which is Postgres-shaped language that does not survive MySQL.
3. You never want a transaction spanning both stores anyway. The outbox exists because you cannot have one, and keeping them in separate databases makes that impossible rather than merely discouraged, which is a better guardrail for an editing agent.

Fall back to two schemas in one database only for managed providers that hand you exactly one database. In that case the boot role owns schema `boot`, the app role owns schema `comms`, and every `DbOps` operation gains a `--schema` argument. Keep it behind the same interface so the choice is configuration, not a code path agents must reason about.

This still satisfies the owner's requirement. One engine choice per deployment, both stores on it. What it does not satisfy is a single `DATABASE_URL`, because two roles mean two credentials. The env becomes `DATABASE_URL` for the app and `BOOT_DATABASE_URL` for boot, where both point at the same server with different dbnames and roles, and where leaving both unset means SQLite files under `/data`. That is the same two variables `SPEC.md` §9 already lists, with a changed meaning: they are no longer a way to split engines, they are two roles on one engine. That change needs to be written into the spec, and I give the text in section E.

### C.2 How the §7.9 trust boundary survives

§7.9 gives two enforcements: exact file ownership, and a guarded localhost channel. The first is the one that changes.

| Property | SQLite today | Same-engine Postgres or MySQL |
| --- | --- | --- |
| The app cannot read boot tables | `boot.db` is `boot`-owned, `0700`; the child runs as `app` via `setpriv` | the `app` role has no grant on `comms_boot`; `REVOKE CONNECT ON DATABASE comms_boot FROM PUBLIC`, and on Postgres also `REVOKE ALL ON SCHEMA public FROM PUBLIC` so the app cannot create objects there |
| The app cannot read the boot credential | boot's env is never passed to the child, `packages/boot/src/supervisor.ts:111-120`, `packages/boot/src/child-process.ts:44`, `packages/boot/src/child-keeper.ts:30` | unchanged and load-bearing. `BOOT_DATABASE_URL` stays in boot's process env and is never placed in the child env map |
| Boot can read app rows while the app writes | `comms.db` in a setgid `comms` directory, umask 002, boot in group `comms`, `packages/boot/src/app-recovery.ts:92`, `packages/boot/src/public-pages.ts:42-47` | the `boot` role gets explicit `SELECT` and, for recovery, `UPDATE` on the narrow shared tables `kernel_writer`, `mutation_batches`, `outbox`, plus `SELECT` on `topics` for the page allowlist. Grant by table, not by schema, so an agent adding a table does not widen boot's access |
| Backups and rehearsal copies are boot-only | `backups/` is `boot`, `0700` | dump artefacts stay files on the volume at `0700`. Scratch rehearsal and drill databases are owned by the `boot` role and never granted to `app` |
| The app cannot escalate | trust plus recovery per §7.9 | one new hazard worth naming: on Postgres the app role must not be `SUPERUSER` or have `CREATEDB`, or the rehearsal and restore isolation is decorative. Create it as a plain login role with ownership of one database only |

Net assessment: the boundary survives, and for the specific thing §7.9 says matters, which is "the one store that matters", a role grant is at least as strong as file ownership and easier to verify. You lose the `setpriv` OS split as the enforcement for the *store*; you keep it for the *filesystem*, where snapshots and staging still live.

There is one genuinely new secret. Boot must know the app role's password to put it in the child env. Today boot knows only paths. Mitigation options, cheapest first: read it from a single env var at startup and never log it, which is what `Config.Redacted` already does for `BOOT_SECRET` at `packages/server/src/kernel/boot-channel.ts:93`; or have boot create a per-attempt role with a random password and drop it on retire, which is elegant and adds a failure mode to the hot path. Take the env var.

### C.3 The allocator lease and the outbox when both stores share an engine

The interesting question. Can the outbox be eliminated by inserting into boot's event log in the app's transaction?

**If the two stores are in separate databases, no.** Postgres and MySQL both refuse cross-database transactions without two-phase commit, and dragging `PREPARE TRANSACTION` into this design would be a much worse trade than an outbox.

**If the two stores are in one database as two schemas, technically yes, and you still should not grant it.** A direct `INSERT INTO boot.events` from the app's transaction needs `INSERT` on a boot table, which is exactly the grant §7.9 exists to withhold. The defensible version is a `SECURITY DEFINER` function owned by the boot role, `boot.append_batch(transaction, from, to, events jsonb)`, with `EXECUTE` granted to the app role and no table grant at all. Inside the app's transaction, that function validates the reservation against the `seq` singleton and appends. It is the localhost channel, expressed in SQL.

What it would buy, honestly, is large: the `outbox` table, the `relay` loop at `packages/server/src/kernel/messages.ts:82-97`, the `mutation_batches` receipts, the reconciliation at `packages/boot/src/app-recovery.ts:34-91`, the `event_batches` state machine at `packages/boot/src/events.ts:57-156`, the dedup on replay at `:87-99`, and the abort-on-typed-failure dance repeated at `messages.ts:217-224`, `read-marks.ts:97-103`, and `operational-events.ts:94-101` all collapse into one atomic insert. That is several hundred lines and most of the hardest reasoning in the codebase.

**Recommend against taking it, for three reasons.** First, it only holds in one of the three deployment shapes, so the outbox code has to exist anyway for SQLite and for two-database Postgres; you would be maintaining two publication protocols, and the spec's §12 bullet "Events are a bootloader-owned primitive with a transactional outbox" would become conditional. Second, an editing agent under the edit lock now has two mental models for how a write publishes, depending on a deployment flag it cannot see from the code. Third, the reconciliation logic is not only about the outbox; it is also how recovery decides whether an interrupted transaction committed, and §6.3 requires that decision to be made from committed evidence in the app store. An atomic append removes the ambiguity for the common case but not the crash-mid-commit case.

So: keep the outbox on every engine. If the owner later wants the simplification, it should arrive as a spec change with its own review, not as a side effect of choosing Postgres.

The **allocator lease** itself needs no change. `packages/boot/src/events.ts:123-156` is ordinary SQL over a singleton row and a receipts table. On a shared engine it gets faster, because the reserve transaction contends on one row instead of the whole boot file.

### C.4 What the localhost boot channel still needs

Even with both stores on one engine, the channel at `packages/server/src/kernel/boot-channel.ts:109-137` and `SPEC.md` §7.9 stays, because most of what it carries is not data:

- **Control transitions.** `frozen`, `go`, `live`, `draining`, sent through the process control path at `packages/boot/src/cutover.ts:163`, `:195`, `:212`, and `packages/boot/src/scheduled-backup.ts:53`, `:100`. These are lifecycle, not rows.
- **Health.** `packages/boot/src/cutover.ts:138`, `:196`. A self-test over HTTP, by design.
- **Per-attempt secret and epoch binding.** `X-Boot-Secret` compared constant-time in `packages/server/src/server.ts` and the proxy-origin refusal in §7.9. A shared database gives boot no way to authenticate which process is calling.
- **Event reads.** §6.2 and §6.3 have the app read the log through `/_boot/events`, and `packages/server/src/kernel/boot-channel.ts:115-120` implements it. With a shared engine you could grant the app `SELECT` on the events table instead, but then the published-fence rule at `packages/boot/src/events.ts:179-181`, which only exposes values at or below `published_through`, would have to be re-enforced in app code that agents can edit. Keep the read on the channel.
- **Reserve, abort, fence.** Could move into SQL functions as described above. Recommend they do not.

So the channel's surface is unchanged. What shrinks is nothing; what changes is that it now rides alongside a shared engine rather than being the only bridge between two files.

## D. The abstraction: one mechanism

**Recommendation: (a) plus (d). Raw `sql` tags with Effect's `onDialect` helpers and one small per-dialect fragment module, plus a narrow `DbOps` service for the operations that are not statements at all.** Reject (b) and (c).

### D.1 Why not a Store service per aggregate

`SPEC.md` §7.4 is explicit: "Queries in code: extensions get `ctx.db`, a raw SQL handle. No ORM, no repository layer to fight." §12 repeats it. A `TokensStore`/`EventsStore`/`MessagesStore` interface with three implementations each would take 352 statement sites to roughly 900, and it would put a repository layer between an editing agent and the only state the system has. It also fails its own premise: the hard statements are the composed published-image views at `packages/server/src/kernel/published-messages.ts:6-15` and the unread-count query at `packages/server/src/kernel/topics.ts:52-58`, which compose as SQL fragments. An interface boundary cannot compose those; it would force each of the three implementations to reimplement the composition, which is exactly the place a subtle divergence between engines would hide.

### D.2 Why not a query builder

Drizzle or Kysely over Effect SQL fails three ways here. It cannot express `messages_fts MATCH` at `packages/server/src/kernel/messages.ts:272`, `json_each` at `:283`, or the conditional published-image `CASE` columns without escape hatches, so you pay for the builder and still write raw SQL at every hard spot. It adds a second language an editing agent must learn, against §7.4. And it breaks `POST /api/sql` at `packages/server/src/sql-http.ts`, which hands agents the raw dialect, so the builder would not be the only SQL surface anyway.

### D.3 Why `DbOps` alone is not enough

`docs/tech.md:121-131` proposes `DbOps` with `snapshot`, `cloneForRehearsal`, `restore`, `dropClone`, isolation, and migrations. That table is correct and necessary; it covers section B entirely. But it says nothing about section A.1, which is roughly 95 statement sites across 14 divergence groups. tech.md's only gesture at them is "backend-specific SQL where dialects differ (FTS, JSON)", which understates the prefix-matching, upsert, `RETURNING`, and read-isolation groups. So `DbOps` is half the answer.

### D.4 The recommended shape

Two new modules plus one service.

**`packages/boot/src/dialect.ts`**, a set of fragment helpers built on `sql.onDialect` and `sql.onDialectOrElse` from `repos/effect/packages/effect/src/unstable/sql/Statement.ts:518-531`. Roughly 180 lines, and it is the whole of the A.1 surface:

| Helper | Replaces | Sites |
| --- | --- | --- |
| `isDescendant(child, ancestor)` | `substr(x,1,length(y)+1)=y||'/'` | 33 |
| `jsonText(col, path)` | `json_extract(col,'$.p')` | 24 |
| `jsonArrayHas(col, value)` | `EXISTS(SELECT 1 FROM json_each(col) WHERE value=?)` | 2 |
| `upsert(table, row, conflict, set)` | `ON CONFLICT DO UPDATE`, `INSERT OR REPLACE`, `INSERT OR IGNORE` | 13 |
| `greatest(a, b)` | two-arg `MAX` | 1, and it is a correctness bug on port |
| `distinctFrom(a, b)` | `IS NOT` | 1 |
| `returning(stmt, cols)` | `RETURNING` with a MySQL `SELECT`-after-write fallback under the held row lock | 5 |
| `readTransaction(effect)` | the `SELECT epoch FROM kernel_writer` snapshot prelude, plus `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` on Postgres | 7 |
| `tableExists(name)` | `sqlite_master` probe | 1 |

**Search stays a service, not a helper.** `packages/server/src/kernel/search.ts` already is one, delegating to `messages.list`. Move the index maintenance and the match fragment behind `Search`: FTS5 virtual table plus triggers for SQLite; a `tsvector` generated column plus GIN for Postgres; two `FULLTEXT` indexes for MySQL. The public contract documented at `packages/server/src/search-http.ts:21`, which already promises no raw FTS operators, no ranking, and no stemming, is narrow enough to hold on all three. The MySQL minimum-token-length difference is a real behavioural divergence that should be written into that description.

**`DbOps`** as tech.md describes, with `capacity()` added per B.5 and `clone`/`restore` returning descriptors rather than paths per B.3 and B.6. It absorbs `packages/boot/src/app-backup.ts` wholesale.

**The read-only SQL HTTP route.** `POST /api/sql` at `packages/server/src/sql-http.ts` and `packages/server/src/kernel/sql-read.ts` exposes raw dialect SQL by design, and that is the right call: an agent doing data surgery needs the real engine. Three changes. The endpoint description at `sql-http.ts:12`, which currently says "Readonly SQLite connection", becomes dialect-reported, and the response gains a `dialect` field so an agent can branch. The placeholder style differs, `?` on SQLite and MySQL versus `$n` on Postgres, so the description must state which, and the validation at `sql-read.ts:20-33` should reject the wrong style with a clear code rather than letting the engine produce a syntax error. The read-only enforcement changes mechanism: SQLite opens a second connection with `readonly: true` at `sql-read.ts:71`; Postgres uses `SET TRANSACTION READ ONLY` or a dedicated read-only role; MySQL uses `START TRANSACTION READ ONLY`. All three keep the `^(SELECT|WITH)` check and the semicolon and comment ban at `sql-read.ts:33`, because those bound the statement count, not the privileges.

**Migrations.** Both `user_version` ladders become `Migrator` migration modules with per-dialect DDL via `onDialect`. The app's migration contract at `packages/server/src/migrations/README.md` already requires "a default-exported Effect requiring only `SqlClient`", so agent-authored migrations gain access to `onDialect` for free and the README gains a paragraph telling them when to use it. Two notes on the Migrator. It wraps `run` in its own `sql.withTransaction` at `repos/effect/packages/effect/src/unstable/sql/Migrator.ts:308`, and `packages/server/src/kernel/migrations.ts:45` already wraps that in an outer transaction, so the inner becomes a savepoint per `SqlClient.ts:294`; that nesting is intentional and should stay. And the "refuse a boot.db from a newer bootloader" rule from `SPEC.md` §9, implemented today as `version > 12` at `packages/boot/src/boot-schema.ts:29`, becomes "max applied migration id exceeds the highest id shipped in this image", which `latestMigration` at `Migrator.ts:162` already provides.

### D.5 Testing cost in CI

Effect's own answer is directly applicable, and it is better than I expected.

- **Postgres with no Docker.** `repos/effect/packages/sql/pglite` wraps `@electric-sql/pglite`, an in-process Postgres. `repos/effect/packages/sql/pglite/test/Client.test.ts:1-14` and `Migrator.test.ts` run the full client and migrator suites against it with no container. So chirp can run its entire Postgres suite in ordinary CI. One caveat that matters here: pglite is single-connection and in-process, so it cannot exercise the writer-epoch fence with two real writers, nor the read-isolation behaviour under concurrency. Those need a container.
- **Real Postgres and MySQL.** `repos/effect/packages/sql/pg/test/utils.ts:2` and `repos/effect/packages/sql/mysql2/test/utils.ts:3` use `@testcontainers/postgresql` and `@testcontainers/mysql`, in files named `*.integration.test.ts`, excluded unless `EFFECT_INTEGRATION_TESTS=1` per `repos/effect/vitest.config.ts:11` and `:51`. Copy that pattern exactly.

Concretely for chirp: the default `bun run test` runs SQLite plus pglite. A separate job sets an env flag and runs the container suites, including the concurrency tests the fence needs. MySQL gets its own job because, as `repos/effect/vitest.config.ts:178-179` notes, MySQL starts a fresh container per suite and competes for runners.

The real cost is not the containers. It is that 28 test fixtures construct `SqliteClient.layer` directly, for example `packages/boot/test/fixtures/events-store.ts:59` and `packages/boot/test/fixtures/edit-store.ts:2`. Those should all route through one `test/fixtures/store.ts` that reads the engine from an env var, so a suite runs three times rather than being written three times.

## E. Migration path from the current PR

Ordered so the SQLite path stays green at every step. Each step is independently shippable and independently testable.

**Step 0. Decide the shape, in SPEC.** One engine per deployment, two databases, two roles. Replacement text below. Half a day of writing, and it is the only step that must come first, because steps 5 and 6 encode the decision.

**Step 1. Store descriptor.** Replace `APP_DATABASE` with `APP_STORE`, add `packages/boot/src/store.ts` that parses a descriptor and returns a client layer, and route the 6 source sites and 28 fixtures through it. The only scheme implemented is `file:`. Zero behaviour change; the suite must pass untouched except for fixture imports. About 350 lines added, 120 removed. One day.

**Step 2. Extract `DbOps`.** Move `clone`, `prepareClone`, and `restore` out of `packages/boot/src/app-backup.ts` behind an interface, with the SQLite implementation moved verbatim, and add `capacity()` returning the current `statvfs` behaviour. Change `restore` to take and return descriptors. Zero behaviour change. About 150 lines net. Half a day.

**Step 3. Extract `dialect.ts` and route the ~95 divergent sites through it.** The helpers compile to exactly today's SQLite SQL, so the suite is the proof. This is the large mechanical step and the one most worth doing before any second engine exists, because it is verifiable in isolation. Do `isDescendant` first, it is 33 of the 95 sites; then `upsert`, 13; then the JSON group, 26. The three one-site helpers, `greatest`, `distinctFrom`, and `tableExists`, are the ones that silently change meaning on port, so write a test for each that asserts the generated SQL per dialect. Two to three days.

**Step 4. Both schema bootstraps to `Migrator`.** Delete the `user_version` ladders at `packages/boot/src/boot-schema.ts:35-72` and `packages/server/src/kernel/database.ts:24-86`, turning each rung into a migration module. Two things need care. An existing `boot.db` at `user_version = 12` must not re-run migrations 1 through 12, so the first boot under the new code stamps the ledger from `user_version` and then never reads it again; that adopt step is about 30 lines and deserves its own test against a fixture database. And the "refuse a newer schema" check from `SPEC.md` §9 moves from `version > 12` to a max-applied-id comparison. The app store has the same shape at `database.ts:18`. Two days, and this is where a mistake is expensive, because it touches a user's existing volume.

**Step 5. Add Postgres.** Depend on `@effect/sql-pg`, implement `DbOps` with `pg_dump`, `pg_restore`, `CREATE DATABASE`, `DROP DATABASE`, add `postgresql-client` to the image, add the `tsvector` search implementation, add the read-isolation prelude, and stand up the pglite CI job plus a gated container job for the concurrency tests. Write the grant script as a checked-in SQL file so the boundary is reviewable. Three to four days, and the first real surprises will be in the published-image views, because the `json_extract` to `->>` change alters result types that the `Schema` decoders at `packages/server/src/kernel/messages.ts:46-50` are strict about.

**Step 6. Add MySQL, or do not.** Depend on `@effect/sql-mysql2`, implement `DbOps` with `mysqldump`, add `VARCHAR(256)` keys, the generated-column substitute for the partial index at `packages/boot/src/source-schema.ts:66`, the `SELECT`-after-write substitute for all five `RETURNING` statements, the `CONCAT` form of prefix matching, the `GROUP BY` fix at `packages/boot/src/agent-roster.ts:15-25`, and two `FULLTEXT` indexes. Gate it behind its own container job. Three to four days. See the recommendation below.

**Step 7. Retire per-store engine splitting.** Once both engines work, `BOOT_DATABASE_URL` stops meaning "put boot somewhere else" and starts meaning "boot's role on the same engine". Delete the code paths that allow mismatched engines, so there is one engine choice per deployment and the "two types of DB is weird" complaint is answered structurally rather than by convention.

Total: roughly two to three weeks of focused work for all three engines, or one and a half for SQLite plus Postgres.

### E.1 The null hypothesis: SQLite everywhere on a volume

Stated honestly, because it is a real option and the cheapest one.

Both Railway and EC2 support persistent volumes. Railway volumes attach to one service and force a single replica; EBS attaches to one instance. Docker on a VPS is a bind mount. All three satisfy the spec's deployment contract at §9 exactly as written: one container, one persistent volume at `/data`, a supervisor that restarts on exit, HTTPS in front, stdout readable once.

**What you actually lose by staying on SQLite:**

- Nothing that `SPEC.md` promises. Every guarantee in §7 is implemented today and tested.
- Provider-managed point-in-time recovery. You keep the hourly and pre-flip backups at `packages/boot/src/scheduled-backup.ts` and the weekly drill at `packages/boot/src/backup-drill.ts`, which is more verification than most managed setups actually run, but the backups live on the same volume as the data, so a volume loss loses both. The existing answer is the offsite extension mentioned in §7.5 and §9, which is a few dozen lines of cron extension against object storage.
- Multi-container hosting and horizontal scale. Irrelevant for a one-human board, and §7.1's child-process blue-green design assumes one box anyway.
- Read concurrency. `BEGIN IMMEDIATE` serializes every transaction, reads included, per `repos/effect/packages/sql/sqlite-bun/src/SqliteClient.ts:114`. On a personal board that is free. It is the thing that would bite first if this ever had many readers.

**What you pay for the pluggable version:** roughly 2,000 lines, a dialect layer that every editing agent must respect, a store whose free space the bootloader cannot see, a rehearsal whose cost grows with data volume, two more CI jobs, and two extra client binaries in the image. `SPEC.md` §9 already concedes the biggest behavioural cost: with a remote database `/_boot/*` depends on that database being reachable, so the one thing guaranteed to always answer now has a network dependency.

**My recommendation, which the owner should feel free to overrule.** Do steps 0 through 4 regardless. They pay for themselves on SQLite alone: the `user_version` ladders become a real migration ledger, the 33 hand-rolled prefix matches become one tested helper, the two silent-semantic-change sites get tests, and the store descriptor makes rehearsal and restore stop talking about filenames. That is about a week and it leaves you strictly better off with no new engine.

Then add **Postgres only**. It is the engine where almost nothing weakens: `RETURNING`, partial indexes, transactional DDL, and `tsvector` all exist, and pglite means the whole suite runs in CI without Docker. Treat **MySQL as designed-for but not shipped**. The dialect layer and `DbOps` accommodate it by construction, so adding it later is the container job plus the MySQL implementations and nothing structural. Carrying it now buys a hypothetical user and costs the three schema contortions, five `RETURNING` rewrites, and a search implementation with different tokenisation behaviour that has to be documented as a divergence in the public API description at `packages/server/src/search-http.ts:21`. `docs/tech.md:117` currently justifies MySQL as "Because someone will", which is an honest joke and a weak reason to maintain a third dialect.

### E.2 Proposed replacement text for the SPEC decisions

Replace the existing §12 bullet that reads "**A SQL database for messages, files for pages.** SQLite by default, Postgres or MySQL by config, through one Effect `SqlClient`. `GET /api/export` can dump the board to markdown if you want the ctx feel." with these three bullets:

> - **A SQL database for messages, files for pages.** `GET /api/export` can dump the board to markdown if you want the ctx feel.
> - **One database engine per deployment, for both stores.** Unset database URLs mean SQLite files under `/data`, which is the default and the reference implementation. Setting them moves both the boot store and the app store to one Postgres or one MySQL server, as two databases with two roles: boot's role owns the boot database, the app's role owns the app database and has no grant on boot's. A deployment never mixes engines, and never puts one store on a different engine from the other. The app's credential is handed to each child in its explicit per-attempt environment; boot's credential is never placed there. With a remote engine, `/_boot/*` depends on that engine being reachable, which is the durability tradeoff the deployment chooses on purpose.
> - **Every file-shaped guarantee has a named engine-neutral form.** One service owns the operations that are not statements: an online consistent copy for backups, a disposable copy for rehearsal and drills, a restore into a fresh target, dropping a copy, and reporting capacity. On SQLite these are `VACUUM INTO`, a file copy, and the close-handle replace. On Postgres and MySQL they are a logical dump and load into a scratch database, and a restore into a fresh database followed by a pointer switch, which never mutates a store under a live reader. Positive closure evidence from the child keeper is required before any restore on every engine, because an orphaned writer committing into an abandoned store loses acknowledged writes no matter how the store is addressed. Rehearsal always runs a real candidate process with the full self-test against a real copy of the data, never a rolled-back migration and never an empty schema, and its deadline is a configured budget that fails the edit with a distinct code when a copy takes too long. Store capacity is reported as unknown rather than guessed when the engine is remote; the volume's own budgets for snapshots, dumps, staging and events are unchanged.

Three further edits follow from that text:

- **§3, first paragraph.** Replace "and `BOOT_DATABASE_URL` to place the boot store separately" with "and `BOOT_DATABASE_URL` to name boot's own role and database on that same engine". The current wording licenses exactly the per-store engine split the owner has ruled out.
- **§7.5, the restore paragraph.** Replace "swap the file (or, on Postgres, restore into a fresh database and swap the connection string)" with "install the restored store: replace the file on SQLite, or restore into a fresh database and switch the child's store descriptor on Postgres and MySQL. Closure evidence is required before either."
- **§9, the env list.** Replace "optionally `DATABASE_URL` and `BOOT_DATABASE_URL` to put either store on Postgres or MySQL instead of SQLite" with "optionally `DATABASE_URL` and `BOOT_DATABASE_URL`, which together move both stores onto one Postgres or MySQL server as two databases with two roles; setting only one is a configuration error".

And one edit to `docs/tech.md`: §4's sentence at line 119, "`BOOT_DATABASE_URL` overrides the boot store alone, so a deployment can keep boot state in local SQLite and put app state in Postgres, which is the combination I'd run", and the matching §12 decision at line 228, both describe the mixed-engine shape. They should be replaced with the one-engine rule, and §4's `DbOps` table should gain the `capacity()` row and the note that `cloneForRehearsal` returns a descriptor rather than a path.

## What is not covered

`SPEC.md` §14 already lists "the Postgres path end to end" as not covered by any review, and that remains true after this study in two specific places. First, I have not measured a dump-and-load rehearsal against a realistic data volume, so the claim that it fits inside a 30-second budget is an estimate from the personal-board scale the spec assumes, not a measurement. Second, the read-isolation finding in A.3 is derived from reading `published-messages.ts:4-5` together with `SqliteClient.ts:114` and `:238`; it is a correctness argument, not an observed failure, and it deserves a concurrency test on a real Postgres before anyone trusts the port.
