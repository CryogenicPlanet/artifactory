### boot-gates-and-way-in

Item 38's core complaint is fixed. supervisor.ts's `ChildError` predicate is gone; release is now decided by the call site (`start(generation, recoverAfterFailure = true)` via `restart`, supervisor.ts:256/276-283/287) plus proven closure, and the 5 s health probe fails as `ChildError health_failed` (supervisor.ts:267-272) rather than a bare TimeoutError, so every failure type that item 38 listed — TimeoutError, SqlError from `generations.healthy`, PlatformError from `recovery.prepare`, interruption — now releases. The two paths that still return frozen (`accepted_snapshot_missing` at cutover.ts:373-379, and `database-backup.ts:64` with no finalizer) now reach `supervisor.requestRecovery`, and root recovery releases both gates at index.ts:146; the only remaining non-release is a deliberately unproven closure. `supervisor.run` no longer idles: the 100 ms poll became `Queue.take(changed)` with wakeups from `activate` and `requestRecovery`, under the unchanged three-attempts-per-generation cap, and it cannot spin. The bare `finish(owner,false)` became a retained `pendingCleanup` retried from `retryCleanup`. Item 39 is half done: POST/DELETE /_boot/lock is now admitted in the Failed phase and reports the recovery failure in the body (verified by supervisor.test.ts:173-201), but POST /_boot/revert still yields `retryRecovery` bare (edit-http.ts:58-63), so after a deterministic failure — e.g. the new legacy-store refusal — a human can take or break the lock and then gets 503 on every PUT and reload and 409 on revert; the lock buys nothing (B-1, major). Item 40's boot half is done: /_boot/events is scope `read` with a real commit-signal `wait=` through one delivery engine, and http.request visibility is clamped in boot from verified identity — by removing request rows from the child transport entirely, which leaves SPEC.md:305 wrong (B-5, declared by Codex as an intentional delta). The new cutover work correctly stops replacing a healthy accepted writer, but a failure in its metadata transaction leaves a pinned lock plus an 'accepted' cutover row whose refusal hints steer the agent away from the one request that clears it (B-2). Two notes: the `read`-only scope check drops fs-without-read tokens from the dead-app diagnostic surface (B-3), and a Failed-phase lock repair deletes an expired editor's staged overlay against the route's own comment (B-4). 8b554a0 is test-only despite its title; the auth diagnostics carry nothing secret. Riskiest changes I could not fault: 42a1a9c's narrowing of the startup intent guard to cutover/restore (source conflicts now permit saved-good selection, with `withCommitted` still blocking new source preparation); 98e5df9's `needsRestart` computation, which re-verifies current/route/epoch, `assertClosure` and the full cutover-row identity before cleaning up; and the repairLock ownership guard in edit-lock.ts:184-214, whose union query correctly tolerates a source-journal owner with a NULL family while refusing any journal that names a different lock.

### 1. MAJOR — item 39 is half implemented: `POST /_boot/revert` still requires recovery to succeed first

`a25530a` fixed exactly half of item 39. The lock half is now right: `repairLock` admits `POST`/`DELETE /_boot/lock` in the Failed phase without recovery succeeding, and reports the recovery outcome in the body (`:90-113`, `lock_committed: true` plus `recovery.status:"failed"`). Failure scenario: the store carries a historical `topic_moves` table. `index.ts:148` refuses inside the recovery permit (`hasLegacyTopicMoves` → `RecoveryRejected{topic_move_recovery_required}`), so `recover` sets `{_tag:"Failed"}` and `failCause`s (`index.ts:169-175`) on **every** call, deterministically. `GET /_boot/fs` and `GET /_boot/lock` read, `POST /_boot/lock` now commits — but the human's `POST /_boot/revert`, the one route that undoes the bad edit, fails forever, including after `POST /_boot/restart`.
