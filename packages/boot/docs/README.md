# @comms/boot

Local development bootloader imported by the server launcher. Boot owns the stable loopback listener; it never imports server/UI implementation or editable source.

Read first: `src/index.ts` (listener/store wiring), `src/supervisor.ts` (health, child lifetime, retries), `src/application.ts` (seed and snapshot selection). `src/boot-schema.ts` initializes schema once; `src/generations.ts` owns SQLite generation history; `src/proxy.ts` handles HTTP forwarding.

`GET /health` and `GET /_boot` remain public after any startup failure. `GET /_boot/status` and `GET /_boot/generations` (alias `/api/generations`) require a human session or bearer `fs` scope and remain available when the child fails. The schema is versioned; a newer boot store is refused without modification. Private routes return a sanitized 503 if authentication storage cannot open; anonymous callers never receive child diagnostics. Authenticated status/history expose attempts, bounded/redacted failures, and the last known-good generation.

On first boot, source is copied once to `DATA_DIR/app`, then snapshotted under `DATA_DIR/gen/<n>/source`. The seed-intent marker is committed before publishing the copied tree: an interrupted seed publication requires repairing the missing editable tree, never silently reseeding it. Snapshots reject source symlinks and overlapping roots. Each generation reserves its id before copying. The child runs with its snapshot as cwd, announces its port, and must pass guarded health within five seconds. The good tag is committed before routing traffic. Restarts prefer saved good snapshots even if the seed or editable tree is broken/missing. A crashing generation gets three total process attempts with 250/500ms backoff, then older good snapshots are tried. Each immutable keeper owns child cleanup with a two-second escalation; boot gives the keeper five seconds to finish.

`GenerationPreparation` runs before rehearsal and before freezing mutations, both for initial snapshots and source reload/check. Each new generation runs a fixed frozen install from the root package.json and bun.lock with lifecycle scripts disabled (60 seconds), then a fixed Vite build when UI source exists (120 seconds). It never evaluates editable code inside boot. Work happens in a fresh disposable `DATA_DIR/cache/.prepare-*` directory. Boot copies installed dependencies into `gen/<n>/source/node_modules` before running editable Vite against the disposable dependencies, then copies built UI into `gen/<n>/source.board`. Retained files share no writable inodes with the workspace or another generation. Failed preparation cannot change committed source or the serving generation; the scoped workspace is removed. Generation retention removes these artifacts with their generation. Saved generations restart without install/build; old `prepared/` artifacts remain untouched because old snapshots may still reference them.

The child receives `BOARD_DIRECTORY`; headless and saved legacy snapshots may still serve their source `board/` files. UI rebuilds require the runtime manifest declaration `comms.board_directory: "environment-v1"`. A legacy initialized app must first update its child to consume that environment path and add the declaration; unsupported rebuilds fail before publication/freeze, without reseeding source. A missing/stale root lock or failed install rejects the candidate before source publication and traffic freeze. Boot has no content-addressed build cache and does not install individual extension packages. Declare extension dependencies in the root manifest and lock, or ship bundled source; extension directories retain their fixed `index.ts` entry. Optional build caching and package bundling belong to editable app tooling or the image build, outside the bootloader.

The immutable preparation keeper receives only those two operations and explicit paths/environment, owns an ordinary descendant process group, and cleans it up when its boot pipe closes. Its error output is bounded. Commands currently run as the same OS user as boot; these process boundaries do not implement Linux privilege isolation. A future privileged launcher must use a separate build UID with access to neither boot state nor the live app store before editable Vite config runs, then preserve boot ownership during artifact promotion. Reusing the app UID would permit build code to modify the live app database before rehearsal.

Only callers explicitly supplying `dependenciesDirectory` may retain the legacy manifestless development link. New runtime launchers omit it. A partially missing manifest/lock is refused, and old initialized editable trees are never silently repaired from seed. Ownership isolation remains future work. Protected artifact retention and storage admission are described in [storage.md](storage.md); live-child hang detection is described below.

Request/response bodies stream; incoming credentials and claimed identities are stripped. Children receive only explicit environment values. Session/access-token authentication runs before child admission. Caller credentials, assertions and claimed identities are replaced with verified auth kind, agent, session id or stable token family, label, scopes, expiry and a fresh request id. The boot session cookie cannot be overwritten by a child response; other child cookies are preserved. Source lock/edit/reload routes are implemented below; unimplemented reserved routes return 501. Bind only to localhost and do not expose this development listener.

`src/edit-lock.ts` now provides the internal durable editor and SQL staging overlay. Each acquisition fences stale requests by id plus family; successful staging renews its TTL. Ordinary restart preserves the lock; explicit startup recovery clears an interrupted pin and its overlay. A pinned cutover blocks expiry and editing, with break/revocation deferred until finalization. Success consumes the pinned overlay; failure retains it for repair unless independently broken/revoked. Staging never touches editable or live snapshot files.

The lock methods commit typed transition events with holder attribution and discarded paths in the same SQL transaction. Staging emits `fs.staged`; other transitions emit `lock.*`. Repeated deferred release requests do not create another transition. Admission expiry commits even when the operation is refused. Call ordinary methods outside an enclosing SQL transaction; a caller adding one must capture `EditRejected` as a result until that outer transaction commits. `breakLock` requires the observed acquisition id. `pin`/`finish` are trusted coordinator seams: the coordinator must serialize one finalization per pin, and report success only after durable version/publication and accepted cutover. HTTP edit authorization, app-store rehearsal and cutover now use this boundary; storage admission is described in [storage.md](storage.md). Staged modes are nullable for old rows; batch staging validates and writes once under the admission transaction, so undo cannot partially stage on a SQL failure.

`src/auth.ts` provides the internal passkey setup/login/session service; `src/auth-schema.ts` is included in boot schema v5. Setup codes are service-owned and rotate after three wrong attempts and after recovery; challenges expire after two minutes. Registration and login verify RP, origin, user verification, challenge use, and counters. Session tokens are stored only as hashes. `src/auth-http.ts` and `src/auth-page.ts` provide immutable setup/login pages and JSON ceremonies. GET `/setup` closes with 404 after registration; GET `/auth/login` presents the sign-in page; POST `/_boot/auth/login/verify` issues the 30-day `__Host-comms_session` cookie after a passkey assertion. The cookie is Secure, HttpOnly, SameSite=Strict, host-only, and never returned in JSON. POST `/_boot/auth/logout` revokes and clears it. Explicit browser auth entry points are public; private requests require a session or enrolled access token, and unsafe session requests require the exact configured Origin. Auth JSON bodies are bounded to 64 KiB, errors are sanitized, and responses are not cached. Invalid explicit bearer credentials never fall back to cookies; refresh tokens cannot authenticate ordinary requests. Logout remains session-only. Auth stays alive after all child retries fail. Exact-topic public-page policy is described below; general settings-backed allowlist customization remains pending.

`src/source-files.ts` provides internal committed/holder-overlay reads, atomic anchored staging, history and first-edit undo. `source-io.ts` enforces canonical app/pages containment, rejects symlinks (including dangling/root links) and nonregular targets, and preserves file modes. One service-owned semaphore serializes source IO and same-holder read/check/stage. Ordinary reads, edits and new snapshots refuse a pending publication. Public edit routes use the same service.

`prepare(owner)` pins and captures SQL staging, returning a service-local proposal id. `materialize(id)` creates a scoped isolated app tree for rehearsal; the cutover coordinator owns database rehearsal and acceptance. `discard(id)` releases a prepared pin as failed while retaining staging. `prepareUndo(owner,batch)` stages retained before-images and modes atomically, refuses an existing overlay, then follows ordinary preparation. Trusted page changes use `preparePages` without taking the app lock; pages do not use app materialization.

Only after rehearsal should the trusted coordinator call `publish(id)`. `source-journal.ts` first commits all before/desired bytes, hashes and modes independently of staging, then replaces files using exclusive sibling temporaries, file fsync, atomic rename and ancestor-directory fsync. Recovery accepts the recorded before or desired image; any third bytes/mode state remains untouched and blocks publication. Durable completion records before/after history and clears transient bytes together. Files above 1 MiB remain writable and recoverable through the journal, but excluded history content is marked `size_limit`; absent content is distinguished by its null hash, and unavailable undo returns `version_unavailable`. SQL schema v5 migrates v4 auth, locks and staging in place.

Startup replays the journal before clearing an interrupted pin. A replay conflict leaves authentication and saved-good snapshots available; authenticated status includes `source_recovery_error`, while new source snapshots stay blocked. Publication never finishes the edit lock successfully: the coordinator calls `EditLock.finish` only after an accepted cutover. Multi-file source publication is recoverable, not an atomic filesystem transaction. Same-user adversarial filesystem races remain outside this slice; storage safeguards are described in [storage.md](storage.md).

Schema v6 adds the event allocator, batch receipts and event log. `events.ts` owns one pending app transaction range and `published_through`. Higher boot events remain invisible until that range is published or confirmed unused. Complete batches validate range/order and retained duplicate contents atomically. Finalized replays never recreate pruned event rows. Schema v14 adds indexed type, actor, instance and level projections alongside routed topic. Query pagination/filtering is bounded in SQL and returns the last included sequence while matching rows remain, otherwise the captured publication fence. GET `/_boot/events` and `/api/events` require read scope and support `since`, `limit`, `topic`, `types`, `agent`, `instance`, and `level`; non-human `http.request` visibility is restricted to the verified agent before SQL pagination; Long-poll adds `wait` up to 60 seconds, excludes the caller's own message events before pagination, advances past considered events, and streams whitespace every 10 seconds. Long-poll remains in boot independently of app swaps; each query captures the published fence and rejects a future cursor. The app owns `/api/stream` SSE and closes it on replacement or drain; clients reconnect with the last event id. Boot has no `/_boot/stream` route. Forwarded SSE bodies reauthenticate at the credential boundary before each chunk and stop at credential expiry. Event waits release admission between pages and stop waiting on disconnect. Event feeds recheck credential expiry and reauthenticate before delivering nonempty data, so revocation applies to open connections too. Query bounds, invalid filter syntax, and duplicate parameters are rejected. Age retention runs in a boot-scoped serial fiber immediately after schema initialization and then hourly. Each pass reads `settings.event_retention` (JSON `{http_request_days:7,other_days:30}`; absent uses these defaults, values must be integers from 1 to 36500 days). Invalid policy skips that pass and logs an error; the next hourly pass retries. There is no HTTP settings editor yet. Events strictly older than their cutoff and at or below the captured publication fence are removed in transactions scanning at most 256 rows, yielding between chunks. Allocation state and all batch/outbox/idempotency receipts remain untouched; finalized replays cannot resurrect pruned payloads. Retention can leave sequence gaps: readers resume at the next retained match, advancing empty results to the captured publication fence. Deletion frees SQLite pages for reuse but does not shrink the database file or enforce SPEC’s physical 10% disk budget; that physical event budget remains pending; write admission is described in [storage.md](storage.md).

`event-http.ts` guards reserve/append/abort/fence access with an exact loopback Host, no forwarding headers, constant-time per-attempt secret and live-attempt admission. A small channel gate linearizes operations with attempt retirement; body decoding is bounded outside it, then the attempt is checked again. Credentials and writer epoch rotate on every retry/fallback. Children must acknowledge kernel protocol and installed epoch before becoming routable. Old snapshots without this handshake fail closed.

`app-recovery.ts` opens a separately scoped app SQLite connection and owns only the narrow recovery-table contract. It installs a new `kernel_writer` epoch under the app writer lock, inspects authoritative batch/outbox evidence, commits the fence, then resolves boot's pending reservation. Inconsistent evidence still commits the fence but blocks publication/startup. A durable initialized marker prevents silently recreating a lost app store. Authentication and boot help survive app recovery failure. Arbitrary extension SQL must preserve these kernel invariants; this is not OS isolation.

Schema v7 adds device-code enrollments and hashed access/refresh pairs without changing source journals, locks, sessions or sequence reservations. `enrollment.ts` composes into the Auth service and shares its scoped admission mutex. Creation returns a 10-minute public id, display code and one-time device secret; only the secret hash is stored. Built-in actor names `rahul` and `boot` are reserved. Each collected pair has a stable family and pair id; approval persists access/refresh durations for future rotation.

Enrollment uses `POST /_boot/auth/challenge {action:"enrollment.decide",params:{id,decision,scopes,long_lived}}`. Canonical scope ordering, id, approve/deny decision and lifetime choice bind a two-minute SHA-256 nonce challenge. `POST /_boot/enroll/:id/approve` requires the same decision fields plus `X-Comms-Assertion` containing base64url JSON `{id,response}`. Exact Origin and a fresh verified passkey are sufficient; no prior login or new session is involved. Proof consumption, credential counter, grant/denial and the boot event commit together. A valid proof is still consumed on a terminal enrollment refusal; SQL/event failure rolls everything back. Setup challenge generation and action parameter bindings share the existing ceremony-discriminated column.

`POST /auth/enroll` and `/auth/enroll/:id` alias the boot routes. Secret-authenticated polls return 202 pending, 200 once with the generated pair, 403 denied, or 410 expired/already_collected. Collection inserts both hashes and marks collected atomically. A lost successful collection response requires re-enrollment; there is no plaintext replay receipt. Polling waits at most 60 seconds and keeps headers unsent until the final status, so it has no whitespace heartbeat. The immutable approval page lives at `/approve/:id` (also under `/_boot`). Enrollment returns the configured-origin `approve_url` and `user_code`; boot does not render QR codes. The page supports withholding fs and selecting standard 24h/30d versus long-lived 7d/90d grants. Refresh is available independently of the child; access expiry points agents to it.

Schema v8 adds short-lived refresh receipts and family-scoped idempotency bindings without changing existing credentials or recovery state. `tokens.ts` composes into Auth; `refresh-receipt.ts` wraps the native HKDF/AES-GCM primitives missing from Effect Crypto. Token rows remain hash-only. The receipt encrypts the exact random successor pair using the raw predecessor secret, random salt/nonce and authenticated family/IDs/deadline; no permanent key or plaintext token is stored.

`POST /auth/refresh {refresh}` (alias `/_boot/refresh`) rotates once and returns the same pair for a fixed 60 seconds across concurrent calls and restart, capped by predecessor expiry. Optional Idempotency-Key is 1–128 printable ASCII characters, family-scoped and bound to the predecessor. A live key bound elsewhere conflicts without marking use. Successor access admission (even a later scope refusal) or successor rotation counts as use; grace replay does not. After grace, only an unexpired predecessor whose exact successor was used revokes the family. Expired or unused predecessors refuse without theft revocation. Old access tokens remain valid until expiry or revocation. Refresh, revocation and successful access admission lazily delete expired receipts/key bindings while retaining token use evidence. Corrupt or missing replay material is a sanitized retriable 503, never a new pair.

Explicit revocation uses `POST /_boot/auth/challenge {action:"token.revoke",params:{family}}`, then `POST /_boot/tokens/:family/revoke {}` (alias `/api/tokens/:family/revoke`) with X-Comms-Assertion. Both require a human session and exact Origin. The service rechecks that session inside the signed transaction after proof verification, so logout/expiry during a held body cannot authorize revocation. Rotation, receipt, key binding and token.refreshed event commit together. Revocation commits credentials, receipt deletion, EditLock transitions and token.family_revoked together before semantic 401; pinned locks defer release, not token invalidation. These operations do not wait for unrelated app event publication. Fresh proof against an already revoked family succeeds without duplicate events; an unknown family consumes the valid proof and returns 404.

Schema v9 adds child ownership receipts, backup metadata and a singleton cutover journal. `cutover.ts` serializes edits with supervisor recovery. It materializes staged source and runs the actual HTTP create/read/context probe against an online SQLite clone with a private sequence allocator, then publishes source and prewarms a candidate before opening the live database. The 10-second freeze counts mutations before body transfer, drains child writes and immediate publication, reconciles outbox state and syncs a pre-flip backup. Candidate health runs inside a rolled-back transaction; boot commits both acceptance and the good tag before public write admission. Background relay starts only after old-child closure. Queued callers reauthenticate at dequeue; edit requests recheck the original credential and lock under SQL admission after body collection.

Before acceptance, failure requires positive closure proof for both database owners, fencing/reconciliation against failed-store evidence, and restoring the synced backup before restarting prior good code. After acceptance, recovery preserves the current database. Startup resolves cutover before interrupted-pin cleanup. Keeper stdin EOF after boot SIGKILL kills even an event-loop-hung child and writes a synced attempt-bound receipt only after observing its exit. Missing keeper proof after a same-kernel restart fails closed with authenticated diagnostics. Distinct validated Linux kernel boot identities can establish that earlier owners exited across a reboot; unsupported hosts and unknown identities still require receipts. No numeric PID or timeout is treated as proof, and an actual Linux reboot remains unverified on the current macOS host.

Implemented edit routes (also `/_boot` aliases) require fs scope: GET/POST/DELETE `/api/lock`; raw GET/PUT/DELETE `/api/fs/app/<path>`; POST `/api/fs/edit` with `{path,edits:[{old_string,new_string,replace_all?}],baseVersion?}`; and POST `/api/reload` with `{}`. GET source returns `X-Comms-Base-Version`; `?history` returns retained history. PUT is bounded to 8 MiB and five seconds. `?reload=0` stages; `?check=1` rehearses without publication; `?release=1` releases after success. Failure retains staging for repair, including when no app generation is live. Generation source restore is described below; broader boot event emission remains separate. Protocol2 rejects older snapshots without lifecycle controls; editable-source repair remains available.

Page source reads and history use `/api/fs/pages/<path>` with fs scope. PUT/DELETE publish a recoverable versioned page batch immediately without taking or renewing the app lock, rehearsing, or changing generation; success returns `{published:true,batch}`. Mutations reject staging/check/release query flags. The same 8 MiB/five-second body limit and exact-Origin rule apply, with late authentication plus session/family and original credential expiry checks inside journal admission. A pending app proposal may temporarily refuse page publication; no second publisher or staging area exists.

The launcher optionally supplies a page seed directory, copied once to `DATA_DIR/pages`; existing trees are preserved. A durable initialization intent prevents silent reseeding after deletion or interrupted seeding. Children receive `PAGES_DIRECTORY` outside application snapshots, so page changes need no reload.

Anonymous GET/HEAD pages require an exact containing-directory grant in boot schema v14's `public_paths`. Literal `meta.public:true` grants, revocations, topic moves and subtree deletions commit with first event publication; retries never reapply old grants. Public parent grants do not expose child topics or nested asset directories. Boot checks canonical containment and symlinks without opening app SQLite or taking lifecycle gates. The child chooses indexes and listings. Explicit invalid credentials still fail authentication. The proxy rechecks grants after request admission; in-flight responses are not recalled. Each physical database replacement clears grants. Before activation returns, the selected child publishes one `pages.public` snapshot through the ordinary mutation/outbox protocol; boot atomically replaces the complete grant set with event publication, including revoking topics removed by editable migrations. The snapshot is bounded to 4096 unique safe paths and 512 KiB; overflow refuses activation rather than truncating policy.

Page writes and undo are raw `fs`-scope repairs through the authenticated source journal, including the `/api/fs` and `/api/revert` aliases. They remain available when the editable app is broken and deliberately bypass archived/deleted topic policy. Boot never calls the app to authorize filesystem publication and has no policy retry loop. The existing operation/channel gates and durable recovery-intent check exclude overlapping journals/restores. App filesystem effects reserve an event range before touching pages, so a pending reservation immediately refuses raw publication with retriable `publication_pending`; no app-table lookup is involved. After reservation recovery, dead-app repair remains available; path containment, symlink refusal, late credential revalidation, synced publication and history remain enforced. App-owned operations must enforce their own domain policy before filesystem effects. There is currently no separate app page-authoring endpoint. Fixed `/page-assets/` resources have exact GET/HEAD public exceptions; no wildcard grants exist.

Directory GETs at `/api/fs/app/`, `/api/fs/pages/` and nested paths (also `/_boot/fs/`) return `{items:[{name,type:"file"|"directory"}]}` with sorted immediate entries. File GETs remain raw bytes. Listings require fs scope and share the source publication admission gate. The app lock holder sees its staged file additions/deletions and virtual parent directories; everyone else sees only committed source. Existing empty directories remain visible. Listings omit symlinks, nonregular children, generated trees and reserved `.comms-*` journal names; requesting those paths directly is refused. Responses contain relative child names only and are not cached.
`POST /api/revert` (also `/_boot/revert`) reuses the same fs-scoped edit lock, rehearsal and durable cutover. `{path:"app/server.ts"}` restores that path's most recent before-image; `{batch:"..."}` restores every before-image in that batch; `{}` selects the latest published app batch. `{version:n}` restores the after-image of the exact retained history id, including deletion. Select exactly one or none; query flags and unknown fields are rejected. Page-only paths, batches and retained version ids instead publish immediately as `{published:true,batch}` through the page journal, without an app lock, rehearsal or new generation. An app lock held by another instance and its staging remain untouched. `{}` still selects the latest app batch; use a page path or explicit page batch/version to undo pages. This follows the page-write exception in SPEC §7.6, clarifying the generic lock/cutover wording for file undo in §7.5. First-create undo deletes the new file, while omitted large-file bytes return `version_unavailable` and never mean deletion. Nonempty staging is refused intact. The original acquisition and credential are checked again at atomic staging admission; success creates a new generation and history batch, while failed rehearsal retains undo staging for repair through ordinary reload.

`POST /api/revert {generation:n}` restores the complete retained editable tree, including removed/new files, file↔directory changes, empty directories, snapshot file modes, package.json and bun.lock. Source snapshots normalize regular file permissions to 0640 or executable 0750 and directories to 0750; those retained permissions are restored. Generated node_modules, .vite and ui/dist are excluded. Boot rebuilds selected dependencies and UI before rehearsal/publication/freeze. Pages and the app database remain current. A failed self-test reports incompatible_schema with a withDb/forward-fix hint; preparation failure keeps current source and the healthy child. A generation proposal does not replace unrelated staging and can be retried with the same generation selector.

New snapshots retain source independently of generated board output and have a synced `source.editable` inventory record. The record includes every editable path, file digest, retained mode and directory identity. Missing or altered retained entries and older snapshots without this provenance return generation_unavailable; boot never guesses original files from an overwritten legacy board. Saved legacy healthy snapshots remain usable for process restart.

Boot schema v13 adds directory identity to journal and history images. Complete-tree publication validates before/desired states, removes obsolete entries deepest first using nonrecursive directory removal, creates parents before children, and syncs each transition. Unexpected children, symlinks or third-party file changes remain preserved and block replay. A batch or path/version undo involving structural history uses the same complete-tree protocol. Batch undo restores only paths/subtrees actually changed by that batch, preserving unrelated later edits and additions; unchanged checkpoint rows are not treated as mutations. Path/version undo restores its selected subtree; absent history bytes still refuse safely. An undo which would remove the entire runnable app fails materialization/rehearsal before publication.

Source-only revert leaves the database current. Combined source/database restore is described below. Source-only human revert currently needs its own lock; overriding another holder's lock remains pending. Combined restore preserves borrowed staging through its durable restore request.

Revert accepts an optional printable 1–128-character `Idempotency-Key`. A durable setting binds the authenticated family (or human session) and key to the canonical selector and exact retained history target. Retrying implicit latest/path undo with the same key therefore never resolves its own new undo history; changed selectors return `409 idempotency_conflict`. This preserves **selection, not the exact HTTP outcome**: an app replay still takes the lock and may create another generation or run hooks/migrations again; a page replay publishes another page history batch. Either can replace later edits. Binding may survive a subsequent staging/authorization failure; a retry keeps its original selection and must independently pass admission. Failed rehearsal retains staging, so repair or POST reload instead of starting another undo. Bindings currently remain in settings without pruning; missing retained content refuses safely. Without a key, every call is a new undo, so do not blindly retry an uncertain response.
A human breaks an observed lock with `POST /_boot/auth/challenge {action:"lock.break",params:{id}}`, then `DELETE /_boot/lock?break=1` (alias `/api/lock?break=1`) with JSON `{id}` and `X-Comms-Assertion`. Both require a live human session and exact Origin. The acquisition UUID binds the proof so a replacement lock survives a stale request. Proof consumption, post-verification session recheck, lock effects and `lock.broken` commit together; semantic refusals consume a valid proof, while storage/event failure rolls the transaction back. Pinned cutovers record pending release and keep competing editors excluded until finalization. Ordinary owner release still uses DELETE without query or assertion.

Schema v10 adds nullable session `last_seen_at`. Successful login and session authentication persist activity; unknown pre-migration activity remains null. Access-token authentication already persists `last_used_at`, aggregated across a family's access tokens so rotation retains presence. Failed authentication never advances it; valid authentication followed by scope or endpoint refusal still counts as activity. These timestamps record admission, not an online guarantee.

Human-only GET `/_boot/enrollments` and GET `/_boot/tokens` return complete `{items}` metadata lists independently of child health. Each is one SQL read ordered by descending lexical ID, with no pagination or query parameters. Enrollment status is the persisted state; `expires_at` lets the caller display expiry without boot rewriting or filtering that state. Token families aggregate retained pairs directly, including families without enrollment. Responses contain display metadata, scopes, expiry/use timestamps and revocation state; never credential hashes, device secrets or receipt material. GETs require a live human session, reject any Authorization header, and do not require a fresh assertion. All query parameters are refused.

Schema v11 adds signed direct token minting: POST `/_boot/tokens` (alias `/api/tokens`) accepts `{agent,label,scopes,long_lived}` and returns the existing access/refresh pair. Names and labels use enrollment's agent/host grammars; scopes are a nonempty duplicate-free selection. Obtain `token.mint` through the existing challenge endpoint with the same fields and optional `idempotency_key`, matching the later Idempotency-Key header. Both routes require a human session and exact Origin. Proof consumption, pair hashes, encrypted receipt and `token.minted` commit together, with the live session checked again after verification and before completion.

Mint retries require the original successful proof, unchanged canonical parameters/key and the same live session. A receipt encrypts the exact pair using the raw session secret with separate mint HKDF/AAD domains; neither a permanent key nor plaintext credentials are stored. Receipts expire at the original session deadline; original proofs can replay after their two-minute challenge TTL. Logout or family revocation refuses replay, changed parameters conflict, and corrupt/missing material never causes another mint. Without an Idempotency-Key, the proof ID identifies the retry. Replay does not stamp token use and may return the original, now-expired access token. Refresh now reads the exact current token pair's durable lifetime tuple rather than requiring an enrollment row, supporting direct mints without synthetic enrollments. Only 24h/30d and 7d/90d pairs are accepted; expired access rows remain valid grant evidence.

Passkey management remains in boot: GET `/_boot/auth/passkeys` lists `{id,label,created_at}` and `can_delete`; POST `/_boot/auth/passkeys/options {label}` returns a session-bound two-minute registration ceremony. Create the new credential, then obtain `passkey.add` with `{registration,label,response}` and finish at POST `/_boot/auth/passkeys/verify {id,label,response}` with the fresh existing-key assertion. The action binds the exact registration bytes and initiating session, and offers only stored keys as authorizers. `passkey.delete {id}` authorizes DELETE `/_boot/auth/passkeys/:id {}`. Both mutations require exact Origin and the same live human session; proof consumption, late session/expiry checks and mutation share one serialized transaction. The last passkey is refused in boot with 409, even under concurrent deletion; missing and duplicate keys return 404/409. Storage failure rolls back proof and mutation; semantic refusal consumes a valid proof. These actions create no new session and deleting a key does not revoke existing sessions. The `/@rahul/passkeys` UI remains a separate slice.

Schema v12 adds nullable backup `published_through` and `generation` metadata. Legacy rows keep null provenance. New hourly backups name the captured live generation; new pre-flip backups name the candidate they precede, preserving that association after the cutover journal is cleared. Their captured publication fence describes the drained app state, before the `backup.taken` event itself. Backup metadata and that event commit together only after the SQLite clone and its containing directory are synced.

The editable app schedules hourly copies using its existing UTC cron parser. Boot has no backup timer or persisted attempt timestamp; ticks missed while the app is stopped or its scheduler is broken are skipped. Pre-flip copies remain boot-owned. The app's scheduling fiber belongs to the application scope, outside extension live scopes and mutation admission, so its channel request can await the freeze/drain operation without blocking that same drain. Child shutdown interrupts its request; a capture that already owns the operation gate still finishes safe release or keeper closure.

POST `/_boot/db/backup {}` returns the completed catalog metadata (`id`, `reason`, `bytes`, `taken_at`, `published_through`, `generation`), never a filesystem path. Human sessions require exact Origin; bearer tokens require `fs`. Authentication is rechecked after acquiring the operation gate. A current live child may call the same endpoint over its secret/Host-protected channel, without holding the channel gate during capture; boot rechecks its exact epoch under the operation gate. Public requests create `manual` backups, app cron calls create `hourly` backups. The endpoint requires a live recoverable app and refuses conflicting recovery intents. It has no replay guarantee: a lost response is uncertain, and another call may create another copy.

On-demand capture shares the supervisor operation gate with cutover/recovery. It freezes app mutation admission and live jobs, drains admitted requests through publication, reconciles the authoritative store with the existing writer epoch, and takes a WAL-inclusive synced online clone. Normal capture resumes the same child. An uncertain lifecycle transition requires keeper-confirmed closure before restarting the same healthy generation; unproven closure remains fail-closed. Failure never restores an older database. The capture emits `backup.taken` only for a cataloged, synced file.

Backup byte admission and protected snapshot/backup pruning are described in [storage.md](storage.md); human database restore is described below. A crash between synced clone creation and catalog registration can leave an uncataloged backup. Such files are never advertised as restorable and need protected retention/recovery cleanup. No Linux physical headroom or machine-power-loss guarantee is added by the scheduler.

Each child attempt now stores the validated Linux `/proc/sys/kernel/random/boot_id` before launch (boot schema v12). Recovery can close an unreceipted attempt only when its recorded kernel UUID and the current valid kernel UUID differ. Same-kernel container/process restarts, unreadable or malformed IDs, unsupported hosts and migrated rows without an ID still require a valid keeper receipt; none are inferred dead. No environment override or process-generated UUID supplies this proof. The identity service is scoped to boot and injectable in tests. Tests simulate kernel identities across real Bun/SQLite restarts; actual Linux reboot evidence and the OS ownership/process-tree boundary remain unverified on the macOS implementation host.
`request-events.ts` records public HTTP dispatches and refusals as `http.request`, including boot-owned auth/enrollment routes and replies while the app is unavailable. It records method, pathname capped at 2048 characters, HTTP status, monotonic duration through response completion, and completion/interruption/failure outcome. The request id is generated by boot and reused when forwarding to the child. Shared authentication supplies verified actor/instance; early auth/enrollment handlers and anonymous refusals conservatively use `boot`/null. Generation is 0 for boot-handled requests and the selected generation for child dispatches. Submitted identities are never trusted. It never records query strings, headers, bodies or exception contents. Long bodies remain streamed; HEAD and disconnected requests finalize once. Health, status, metrics, event feeds (including app SSE), and internal child-protocol calls are excluded to avoid polling/self-logging loops. Existing event queries hide other agents' request records before pagination.

Request finalizers only enqueue a finished record; one boot-scoped writer uses `Events.writeBoot`, preserving the publication fence without holding traffic admission on SQL contention. The queue holds at most 256 pending records plus one in flight. **Diagnostic logging is intentionally lossy:** saturation and storage failures log a static stderr message, failed/uncertain commits are not retried, and pending records can be lost at shutdown or crash. This is a limitation relative to SPEC's every-proxied-request intent; request diagnostics are not an audit receipt or mutation-success condition. Cross-process trace annotations/exporters remain pending.

Human database restore is `POST /_boot/db/restore {backup}` (also accepts `{id}`, never both). Obtain `db.restore` from the existing challenge endpoint with the same selector and live human session; send its `X-Comms-Assertion` and exact Origin. Bearer tokens cannot authorize it. Only cataloged regular backup files with a recorded publication fence are accepted; legacy backups with unknown provenance are refused. The source and pages remain unchanged, and the prior live or latest retained good snapshot is used independently of the backup's generation association.

Boot schema v13 adds durable restore requests. The proof and session authorize one operation before any runtime effects; exact original-proof retries return its terminal outcome even after challenge expiry, require the same still-live session, and never repeat restoration. Optional Idempotency-Key is bounded to 128 printable ASCII characters and must also appear as idempotency_key in the signed challenge parameters. The live human session and key bind the selected backup and first outcome; reusing that key with another selector conflicts, and receipt replay has no new runtime effect. Without a key the original proof identifies the retry. An uncertain operation awaiting recovery returns unavailable; restart resumes the durable record. A failed terminal request needs a fresh assertion to try again.

Restore freezes and drains mutations and jobs, reconciles current app evidence, and catalogs a synced `pre-restore` safety copy. It pins the existing edit lock without consuming staging, or temporarily takes a boot-owned empty lock. App requests then wait in a bounded queue (128 concurrent waiters, ten seconds); overflow or timeout returns unavailable. Credentials and public-page grants are checked again when admission resumes. Boot auth/help/events remain alive, and keeper-confirmed retirement precedes file replacement. Public grants are cleared before replacement and rebuilt before app activation. Borrowed staging survives normal completion and crash recovery; a separately requested break or revocation still applies.

The journal selects the authoritative store: `authorized` retains the current store; `restoring` selects the requested backup; `working` selects the restored candidate's current file; `rollback` selects the fresh safety copy. Startup selects this phase after old-owner closure and before ordinary app reconciliation. A fresh writer epoch fences restored state without rewinding boot sequence allocation. Candidate health must pass before the exact outcome, good tag and `db.restored {backup,restored_to_seq}` commit together; only then do live jobs and traffic resume. Failed candidate health reconciles its evidence and restores the safety copy. `restored` and `failed` are terminal phases and never copy a backup again, preserving later acknowledged writes. Missing closure proof or inconsistent app evidence leaves the app unavailable with its journal intact.

`POST /_boot/revert {generation:n,withDb:true}` (alias `/api/revert`) combines source and database restoration in that same coordinator. Obtain `generation.restore` from `/_boot/auth/challenge` with the same body and optional `idempotency_key`, then send the assertion, same human session and exact Origin. The proof binds generation `n`, its exact retained backup and publication fence; neither bearer `fs` nor an ordinary `db.restore` proof authorizes this action. Mixed file/batch/version selectors are refused.

Boot schema v15 adds `generations.backup_id` and source/fallback/publication references to restore requests. A normal cutover records its pre-flip backup against the candidate generation. Existing rows are backfilled only when exactly one matching pre-flip backup is known; missing or ambiguous provenance is refused. Combined restore copies the validated source of `n` into a new generation, rebuilds dependencies/UI and rehearses against the selected backup before freezing. The new generation retains that backup association. Pages on disk and boot identities remain current; restored topic metadata determines their rebuilt public grants.

The existing phases own both changes. Before acceptance, editable source stays unchanged; candidate failure or cancellation restores the fresh safety database and prior runtime. After candidate health passes, one boot transaction commits the full source publication journal, good generation tag and successful restore receipt/event. This is the irrevocable acceptance boundary. Boot finishes and syncs the bound source journal before activating traffic or live jobs. A crash or publication failure after acceptance completes that journal and preserves the accepted database, never restores the safety copy over it. External third-state source changes remain preserved and block publication until repaired. The restore pin stays held until its bound batch completes; another editor's staging is never deployed or consumed. Terminal retries require the same live session and original proof or bound key and never redo publication over later edits.

This remains SQLite restoration. Remote database adapters, Linux privilege separation and machine power-loss evidence are separate work. Backup files are trusted boot-owned artifacts; same-user filesystem tampering is outside the current local-development isolation boundary.

Shell edits under `DATA_DIR/app` do not trigger deployment or create source history. Use authenticated source edits and reload; restarts still select the saved good snapshot. Boot no longer watches the volume, creates watcher baselines, or adopts external bytes after a reload. Existing watcher history remains readable and explicitly restorable, including structural changes; an existing baseline marker remains excluded from implicit latest-batch undo. No history, retry bindings, or schema columns are removed.

Human-only GET `/_boot/db/backups` returns `{items,next}` with backup catalog metadata: `id`, `reason`, `bytes`, `taken_at`, `published_through` and `generation`. Legacy provenance remains null; filesystem paths are never returned. Each page is one bounded SQL query, sorted by descending `taken_at` and then `id`, with `limit` defaulting to 100 and capped at 200. Pass the returned opaque `next` token as `before`; ties are stable, and continuing does not depend on the cursor row still existing. This is keyset pagination rather than a cross-request snapshot: newer insertions are seen on a fresh first page. Unknown/duplicate parameters and malformed, oversized or invalid cursors are rejected.

The catalog is served by boot after authentication storage opens, independently of child health or cutover recovery. It requires a live human session, refuses any Authorization header, and needs no fresh passkey assertion. Responses use `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. Listing neither reads backup files nor verifies their existence, integrity or compatibility; a catalog entry is not a promise that a future restore will succeed. Uncataloged files are omitted.

Boot checks durable source publication, cutover, database restore and topic-move intents in one SQL snapshot before any startup recovery selects or modifies authoritative data. Conflicting operations leave authentication and backup inventory available but app admission and publication unavailable. New reload, move, restore, page publication and maintenance operations refuse an unfinished durable owner.

`storage-volume.ts` retains only a bounded free-space probe for the volume's capacity and caller-available bytes. Boot no longer scans allocation categories or samples/caches a storage dashboard, and `/_boot/status` omits `storage`. The probe is wired to the admission safeguards in [storage.md](storage.md).

Boot probes the live child once per second over its authenticated private channel, with a five-second response deadline. An unresponsive event loop is terminated through the existing keeper, independently of the cutover operation gate; reconciliation and restart remain serialized. Closure receipts are still required before another database owner starts. This cancels the whole child, including other in-flight requests, and never treats a timeout as proof that a write rolled back. It does not impose a memory limit.

GET `/_boot/metrics` serves Prometheus text from a private Effect metric registry owned by each boot instance, including when the app child is down. It uses status's existing authorization: a live human session or an access token with `fs` scope. Read-only tokens and anonymous callers are refused; responses are not cached. This is the narrow access policy for this endpoint, with no new metrics permission.

The four unlabelled measurements are `comms_requests_total` (all requests reaching the boot listener, including internal child calls and scrapes), `comms_swap_duration_seconds` (a histogram from source proposal preparation through reload completion or failure recovery, excluding check-only and requests refused before preparation), `comms_freeze_queue_depth` (the current number of app mutations waiting for a freeze to end), and `comms_lock_waits_total` (edit requests refused because another editor holds the lock or a cutover pins it). The lock counter measures contention refusals because edit admission does not wait. Counters and observations reset when boot restarts; no dashboard, persistent metric storage, or labels are added.

Lifecycle audit records use `Events.writeBoot` synchronously inside the owning boot transaction. Source publication commits one `fs.write` per changed path with version history, the published batch marker and journal cleanup; bytes and file contents are not included. An event-storage failure retains the publishing journal, so recovery finishes it before admission and writes no duplicate committed event. Generation starting, healthy, failed and recovery state transitions commit their event with the state change. A failed third startup attempt carries `reason: startup_failures` and `attempts: 3`; successful source rehearsal writes a durable `generation.rehearsed` checkpoint. The current child health response does not yet report suppressed external calls, so SPEC §7.9's `{suppressed}` report remains unimplemented.

Boot audit writes can allocate above an outstanding app reservation, but queries expose them only once the existing publication fence advances. Audit writes are not queued or best effort: failure rolls back the associated SQL transition, or retains the source journal for recovery. SQL rollback defects remain failures; neither a timeout nor an event-write error is treated as proof that a source operation did not commit.
`POST /_boot/restart {}` requires a human session, exact Origin and a fresh `boot.restart` assertion obtained with `params: {}`. It returns `202 {status:"restarting"}` and exits boot through graceful cleanup. Already admitted mutations get five seconds to finish and publish; new public work is refused. A stalled admitted request or child shutdown hook is retired through the keeper, preserving closure evidence and the current app store. A timed-out request has an uncertain outcome, not an implied rollback; normal startup reconciles committed publication evidence. The container supervisor must bring boot back (`--restart unless-stopped` in the deployment example); local server and UI development commands exit and require relaunching. Restart reuses the newest known-good snapshot through normal recovery. A lost response is uncertain; the single-use assertion cannot authorize another restart.

The pinned `@effect/platform-bun` patch bounds final listener shutdown using its existing grace period, then closes remaining sockets directly. This avoids Bun's unresolved `stop(false)` → `stop(true)` escalation when a client leaves a response unread. Boot finishes keeper-backed owner cleanup before listener teardown; the patch does not bypass that durability boundary. Remove the patch when the pinned adapter supplies equivalent verified behavior.
`route-discovery.ts` owns the immutable public boot route descriptors. The proxy merges them into successful GET `/api` and `/.well-known/agent.json` responses; boot wins its reserved paths, and app/extension paths and components remain intact. Descriptors state methods, descriptions and `x-comms-auth` / `x-comms-scopes`; action-specific proof requirements remain explicit in descriptions. Private child IPC is not advertised. Discovery JSON is bounded to 2 MiB and five seconds, with malformed responses refused as app unavailable; ordinary proxy responses still stream. The documents still require a healthy app, and `/init` continues hashing only its editable text.
